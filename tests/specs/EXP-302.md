# Test Spec: EXP-302 — Service-Task Migration to Effect Emit-and-Wait

**Requirement:** EXP-302 — SERVICE_TASK node migration: service tasks now emit effects instead of performing inline I/O, and instance state transitions to EFFECT_WAIT until result re-entry  
**Priority:** MUST  
**Test layers:** integration

## Requirement Summary

The SERVICE_TASK node in the execution engine has been migrated from inline I/O (performing HTTP calls during transition) to async effects (emitting effect_emitted events that the background worker delivers). The instance transitions from RUNNING → EFFECT_WAIT when a SERVICE_TASK is activated. When the effect result re-enters via EFFECT_COMPLETED or EFFECT_FAILED, the instance continues from EFFECT_WAIT.

An optional `sync_inline: true` flag on the SERVICE_TASK node routes to synchronous delivery (backwards compatibility path) instead of async queuing.

## Test Cases

### TC-EXP-302-01: SERVICE_TASK Node Emits Effect on Activation (Path A: Async Default)
**Given:** a process definition with a SERVICE_TASK node configured with HTTP endpoint and method  
**When:** a token activates the SERVICE_TASK node via normal transition  
**Then:**
  - A `PendingEvent.effect_emitted` is created (not inline HTTP call)
  - An `EFFECT_EMITTED` event is inserted into the event log
  - The `effects_outbox` row is inserted with the HTTP spec
  - The instance remains ACTIVE while the token is parked on the SERVICE_TASK node
  - No HTTP request is made during the transition

**Acceptance criteria mapped:** SERVICE_TASK activated → emits effect instead of inline I/O

### TC-EXP-302-02: Instance Transitions to EFFECT_WAIT State
**Given:** a SERVICE_TASK has emitted an effect  
**When:** the transition completes and the projection is persisted  
**Then:**
  - The token remains parked on the SERVICE_TASK node
  - The outbox row exists for the emitted effect
  - The wait descriptor is the persistence representation of the wait state

**Acceptance criteria mapped:** Instance wait is represented by the parked token plus wait/outbox rows

### TC-EXP-302-03: Instance Continues After EFFECT_COMPLETED Re-entry
**Given:** an instance waiting at EFFECT_WAIT after a SERVICE_TASK effect emission  
**When:** the effect worker delivers the effect and calls `reenterEffectResult(succeeded=true, response_body)`  
**Then:**
  - An `EFFECT_COMPLETED` event is inserted
  - The transition function is invoked with this event
  - The instance token advances from the SERVICE_TASK to the next node in the graph
  - The instance advances to the next node in the graph
  - The response body is merged into instance variables
  - The wait descriptor is resolved

**Acceptance criteria mapped:** Re-entry on success continues instance from EFFECT_WAIT

### TC-EXP-302-04: Instance Routes to Error Node on EFFECT_FAILED
**Given:** an instance waiting at EFFECT_WAIT after a SERVICE_TASK effect  
**When:** the effect worker exhausts retries and calls `reenterEffectResult(succeeded=false, error_detail)`  
**Then:**
  - An `EFFECT_FAILED` event is inserted with error details
  - The transition function is invoked with this event
  - The instance transitions to ERROR when no catch route exists
  - The wait descriptor is resolved

**Acceptance criteria mapped:** Re-entry on failure routes to error node

### TC-EXP-302-05: Optional sync_inline:true Flag Routes to Synchronous Delivery (Path B)
**Given:** a SERVICE_TASK node with `sync_inline: true` attribute  
**When:** the token activates the SERVICE_TASK  
**Then:**
  - The effect is not emitted asynchronously
  - No `EFFECT_EMITTED` event is inserted
  - The token remains on the SERVICE_TASK node within the same transition

**Acceptance criteria mapped:** sync_inline flag bypasses async emission at the transition layer

### TC-EXP-302-06: HTTP Response Body Captured in EFFECT_COMPLETED Payload
**Given:** a SERVICE_TASK effect completes with an HTTP 200 response containing JSON body  
**When:** the effect worker re-enters the result  
**Then:**
  - The `response_body` (HTTP response body) is captured and stored in the `EFFECT_COMPLETED` event
  - The response body is available in the effect-completed re-entry payload
  - The token can use the response to update instance variables

**Acceptance criteria mapped:** Response body captured and available for process continuation

### TC-EXP-302-07: Multiple SERVICE_TASK Nodes in Sequence
**Given:** a process definition with two sequential SERVICE_TASK nodes  
**When:** token completes the first SERVICE_TASK and awaits the result  
**Then:**
  - Upon EFFECT_COMPLETED re-entry, the token advances to the second SERVICE_TASK
  - The second SERVICE_TASK emits a new effect
  - Two distinct `EFFECT_EMITTED` events and two distinct effect specs exist
  - Each effect is processed independently by the worker

**Acceptance criteria mapped:** Multiple effects are correctly sequenced and re-entered

### TC-EXP-302-08: SERVICE_TASK Within Parallel Branches
**Given:** a process definition with a parallel gateway splitting into two branches, each with a SERVICE_TASK  
**When:** tokens reach both SERVICE_TASK nodes and both emit effects  
**Then:**
  - Two effects are emitted from the parallel branches
  - Each effect has a distinct correlation_key
  - Both can be delivered concurrently by the worker
  - Both re-entries are processed and both tokens advance

**Acceptance criteria mapped:** Effects within parallel branches are correctly isolated and re-entered

## Integration Test Requirements

- Tests use `TestHarness` for PostgreSQL provisioning
- All correlation keys and instance IDs are unique per test
- Tests verify instance state transitions (RUNNING → EFFECT_WAIT → RUNNING/ERROR)
- Tests verify event log entries (EFFECT_EMITTED, EFFECT_COMPLETED, EFFECT_FAILED)
- sync_inline path tests verify no outbox row is created (or is marked inline)
- No HTTP mocking for async tests; stub responses or real servers only
- Response body capture is verified in test assertions
