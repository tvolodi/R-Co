# Test Spec: XC-01 — Trace Propagation

**Requirement:** XC-01 — Every action originating from a REST request, scheduler firing, or future tool invocation carries a unique trace ID through all subsystems and database writes.  
**Priority:** MUST  
**Test layer:** integration

---

## Overview

Trace propagation enables end-to-end request tracing across all platform subsystems. A trace ID is either:
- Extracted from the `X-Trace-Id` request header if present, or  
- Generated as a UUID v4 if missing

The trace ID flows through:
- Thread-local `trace_context` (available to all modules)
- Structured log entries (JSON field `trace_id`)
- Audit log entries (column `trace_id`)
- HTTP response headers (`X-Trace-Id`)

All trace IDs for a single request and all operations triggered by that request must be queryable together via the trace_id value.

---

## Test Cases

### TC-XC-01-01: Missing X-Trace-Id header generates UUID v4

**Given:** An API request with no `X-Trace-Id` header.

**When:** The request is processed through the trace middleware.

**Then:**
- A UUID v4 is generated (36-character format: 8-4-4-4-12)
- The generated trace ID is stored in thread-local `trace_context`
- The response includes `X-Trace-Id: <generated-uuid>` header
- All downstream operations (log entries, audit records) carry this trace_id

**Acceptance:**
- Response header contains valid UUID v4 in `X-Trace-Id`
- Querying audit_log where trace_id matches response header returns all audit entries for this request

**Layer:** integration  
**Fixtures:** None (no prior state needed)

---

### TC-XC-01-02: Supplied X-Trace-Id header is propagated end-to-end

**Given:** An API request with `X-Trace-Id: my-custom-trace-id-123`.

**When:** The request is processed.

**Then:**
- The supplied trace ID `my-custom-trace-id-123` is stored in thread-local `trace_context`
- The response includes `X-Trace-Id: my-custom-trace-id-123` header
- All audit entries for this request have `trace_id = 'my-custom-trace-id-123'`
- Structured logs (if emitted) include `"trace_id": "my-custom-trace-id-123"`

**Acceptance:**
- Response header echoes the supplied trace ID exactly (no transformation)
- Audit query by trace_id returns all entries from this request
- Non-UUID trace IDs are accepted and propagated as-is (propagation is non-validating)

**Layer:** integration  
**Fixtures:** None

---

### TC-XC-01-03: Trace ID flows through audit chain

**Given:** An API request with `X-Trace-Id: trace-123` that triggers state-changing operations.

**When:** The request is processed and audit entries are recorded.

**Then:**
- All audit entries carry `trace_id = 'trace-123'`
- Audit rows in the same transaction have identical `trace_id`
- Querying `SELECT * FROM audit_log WHERE trace_id = 'trace-123'` returns all entries for this request in order

**Acceptance:**
- Number of returned audit rows matches expected operation count
- All rows have `trace_id = 'trace-123'`
- Timestamp ordering is monotonic (microsecond precision per ES-01)

**Layer:** integration  
**Fixtures:**
- Fresh instance created via API call with known trace_id

---

### TC-XC-01-04: Scheduler tasks generate distinct trace IDs

**Given:** A background scheduler task (e.g., timer firing) initiated by the platform.

**When:** The scheduler task executes.

**Then:**
- A new trace ID (UUID v4) is generated for the task
- This trace ID is distinct from any request's trace ID
- All operations within the task (audit writes, logs) carry this trace_id
- The task-generated trace ID does not collide with concurrent request trace IDs

**Acceptance:**
- Scheduler task trace_id is unique per task invocation
- Querying audit_log by scheduler-generated trace_id returns only entries from that task
- Concurrent requests and scheduler tasks have different trace_id values

**Layer:** integration  
**Fixtures:**
- Active timer in an instance
- System configured to fire timers at predictable intervals

---

### TC-XC-01-05: Trace context is thread-local (isolated per request)

**Given:** Concurrent API requests on separate threads.

**When:** Both requests execute simultaneously.

**Then:**
- Request A's trace ID is isolated to its thread
- Request B's trace ID is isolated to its thread
- No cross-thread trace_id leakage occurs
- Each request's audit entries carry only its own trace_id

**Acceptance:**
- Concurrent requests do not interfere with each other's trace_context
- Each request's final trace_id is correct and distinct

**Layer:** integration (requires concurrent test harness)  
**Fixtures:** None

---

### TC-XC-01-06: Trace ID is immutable post-generation

**Given:** A trace ID has been generated and stored in thread-local context.

**When:** Modules attempt to read trace_id via `trace_context.get()`.

**Then:**
- The returned value is always the same throughout the request lifecycle
- No module can accidentally overwrite or corrupt the trace_id
- `trace_context.clear()` is only called after response is fully sent

**Acceptance:**
- Multiple calls to `trace_context.get()` within a request return identical bytes
- Audit entries from different operations within the same request share the same trace_id

**Layer:** integration  
**Fixtures:** None

---

### TC-XC-01-07: Trace ID is included in HTTP error responses (4xx, 5xx)

**Given:** An API request that results in an error (e.g., 401, 422, 500).

**When:** The error response is generated.

**Then:**
- The response includes `X-Trace-Id` header with the request's trace_id
- Error response body (RFC 9457 Problem Details) may include trace_id field
- Downstream error tracking systems can correlate error by trace_id

**Acceptance:**
- All error responses (4xx, 5xx, etc.) include X-Trace-Id header
- Trace ID in header matches trace ID in audit entries for this request

**Layer:** integration  
**Fixtures:** None
