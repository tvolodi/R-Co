# ISS-502 Test Specification: SPT Cutover Transaction

## Requirement
ISS-502: SPT cutover transaction flips storage_mode after verified copy

## Test Cases

### TC-ISS502-01: Cutover copies all rows and flips storage_mode
- **Layer:** Integration
- **Precondition:** Tenant in LEGACY_RLS mode with seeded test data in public schema. Tenant schema exists and has tables.
- **Steps:**
  1. Count rows in each business table for the tenant
  2. Call executeSptCutover()
  3. Verify storage_mode is now 'SCHEMA'
  4. Verify row counts in tenant schema match original public row counts
- **Expected:** CutoverResult.already_migrated = false. Row counts match. storage_mode = 'SCHEMA'.

### TC-ISS502-02: Cutover is idempotent (re-run is no-op)
- **Layer:** Integration
- **Precondition:** Tenant already in SCHEMA mode (after TC-ISS502-01)
- **Steps:**
  1. Call executeSptCutover() on already-migrated tenant
  2. Verify result
- **Expected:** CutoverResult.already_migrated = true. No rows copied. No errors.

### TC-ISS502-03: Failure rolls back leaving tenant LEGACY_RLS
- **Layer:** Integration
- **Precondition:** Tenant in LEGACY_RLS mode. A row in tenant schema will cause a PK conflict.
- **Steps:**
  1. Manually insert a conflicting row in the tenant schema
  2. Call executeSptCutover()
  3. Check storage_mode
- **Expected:** Function returns CopyFailed error. storage_mode stays 'LEGACY_RLS'. Transaction rolled back.

### TC-ISS502-04: Row count mismatch is detected
- **Layer:** Integration
- **Precondition:** Tenant in LEGACY_RLS mode.
- **Steps:**
  1. Call executeSptCutover() with a table list that expects different counts
  2. Check result
- **Expected:** RowCountMismatch error if counts differ.
