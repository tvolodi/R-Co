# Test Spec: XC-05 — Deterministic Replay

**Requirement:** XC-05 — Given an instance's event log and snapshotted definition and script versions, replaying Tier 1, 2, and 3 nodes produces identical state at every step. Tier 4 (LLM) nodes replay from recorded outputs.  
**Priority:** MUST  
**Test layer:** integration

---

## Overview

Deterministic replay enables state reconstruction at any point in an instance's history. The engine's `reconstructInstancePointInTime()` function replays events from a specified sequence number or timestamp and produces state identical to the original execution.

**Preconditions:**
- Event log is complete and immutable (ES-01, ES-02)
- Definition is snapshotted at instance creation (PD-08)
- Archived events remain queryable (ADP-11)
- Kernel is deterministic (XC-04)

**Result:**
- Replaying an instance with events 1..N at any point produces state equivalent to the original execution
- Multiple replays of the same instance history produce bit-identical state

---

## Test Cases

### TC-XC-05-01: Point-in-time reconstruction produces state matching original execution

**Given:** An instance with 10 events appended sequentially.

**When:** `reconstructInstancePointInTime(instance_id, up_to_sequence = 5)` is called.

**Then:**
- The function replays events 1–5 through the pure transition function
- Final state (variables, active tokens, status) matches the state that existed after event 5 in original execution
- Instance projections table (or equivalent materialized view) contains the same state

**Acceptance:**
- Reconstructed instance state equals expected state after 5 events
- All instance variables match
- Active token set matches
- Instance status matches

**Layer:** integration  
**Fixtures:**
- Instance with known event sequence and expected state snapshots

---

### TC-XC-05-02: Repeated reconstruction of same point produces bit-identical state

**Given:** An instance with 20 events.

**When:** `reconstructInstancePointInTime(instance_id, up_to_sequence = 10)` is called three times independently.

**Then:**
- All three reconstructions produce identical state
- State hashes (JSON serialization) are byte-for-byte identical
- No randomness or non-determinism is introduced

**Acceptance:**
- Multiple reconstructions produce identical variable values
- Serialized instance state is bit-identical across runs

**Layer:** integration  
**Fixtures:**
- Instance with predictable event sequence

---

### TC-XC-05-03: Reconstruction with timestamp parameter works correctly

**Given:** An instance with events timestamped at T1, T2, ..., T10.

**When:** `reconstructInstancePointInTime(instance_id, up_to_timestamp = T5)` is called.

**Then:**
- All events with `created_at <= T5` are replayed
- Final state matches the state at time T5
- Events after T5 are not included

**Acceptance:**
- Timestamp-based reconstruction matches sequence-based reconstruction (if timestamps are monotonic)
- State at time T5 is correct

**Layer:** integration  
**Fixtures:**
- Instance with events timestamped at regular intervals

---

### TC-XC-05-04: Archived events are included in point-in-time reconstruction

**Given:** An instance with 100 events, where events 1–50 have been archived (moved to events_archive per ADP-11).

**When:** `reconstructInstancePointInTime(instance_id, up_to_sequence = 75)` is called.

**Then:**
- The function queries both `events` (live) and `events_archive` (archived)
- Archived events 1–50 are replayed as if they were in the live table
- Final state includes effects of all archived events
- State reconstruction query joins live + archive correctly

**Acceptance:**
- Reconstructed state matches baseline (before archival)
- No events are skipped
- Query correctly merges live and archive tables

**Layer:** integration  
**Fixtures:**
- Instance with some events archived, some live
- Baseline state snapshot before archival

---

### TC-XC-05-05: Reconstruction accuracy across instance timeline

**Given:** An instance with 50 events, and expected state snapshots at events 10, 20, 30, 40, 50.

**When:** Point-in-time reconstruction is called for each snapshot event.

**Then:**
- Reconstruction at event 10 matches snapshot_10
- Reconstruction at event 20 matches snapshot_20
- ... (all intermediate snapshots match)
- Reconstruction at event 50 matches final state

**Acceptance:**
- All intermediate reconstructions are accurate
- No drift or accumulating error across replay steps

**Layer:** integration  
**Fixtures:**
- Instance with 50 events and 5 expected state snapshots

---

### TC-XC-05-06: Service task outputs are replayed from recorded events (not re-invoked)

**Given:** An instance with a SERVICE_TASK node that has been executed once, creating a `service_task_output` event with recorded response.

**When:** The instance is replayed and the SERVICE_TASK is encountered.

**Then:**
- The `service_task_output` event is read from the log
- The recorded service response is used (no HTTP call is made)
- External service is NOT re-invoked
- Final state uses the recorded response value

**Acceptance:**
- Service task output is deterministic (from recorded event)
- No external API call is made during replay
- Recorded output value is correctly applied to instance state

**Layer:** integration  
**Fixtures:**
- Instance with SERVICE_TASK node and recorded output event

---

### TC-XC-05-07: Reconstruction of empty instance (zero events) returns initial state

**Given:** A newly created instance with zero events appended.

**When:** `reconstructInstancePointInTime(instance_id, up_to_sequence = NULL)` is called.

**Then:**
- Function returns initial instance state (all default variables, tokens at start node, status=ACTIVE)
- No errors are raised
- State matches the empty-instance baseline

**Acceptance:**
- Empty instance reconstruction works correctly
- Initial state is as expected from instance creation

**Layer:** integration  
**Fixtures:**
- Newly created instance with no events

---

### TC-XC-05-08: Reconstruction fails gracefully for non-existent instance

**Given:** An instance ID that does not exist.

**When:** `reconstructInstancePointInTime(instance_id, ...)` is called.

**Then:**
- Function returns error: `InstanceNotFound` (HTTP 404)
- No NULL pointer dereference or panic occurs
- Error is logged with trace_id

**Acceptance:**
- Graceful error handling
- Proper HTTP status code
- Trace ID included in error audit

**Layer:** integration  
**Fixtures:**
- Non-existent instance ID

## Success Criteria

1. All test cases pass
2. Replay produces deterministic, bit-identical state across runs
3. Archived events are correctly included in replay
4. Service task outputs are recorded and replayed (not re-invoked)
5. No test.skip entries
6. Tests use per-test UUIDs and clean up after themselves
7. Tests fail clearly if BPM_TEST_DB_URL is absent
8. Replay time for instances with up to 10,000 events is < 5 seconds (NFR-04)

---

## Dependencies

- **ES-01, ES-02, ES-06:** Event append, ordering, point-in-time query
- **EE-11:** State reconstruction engine
- **PD-08:** Definition snapshot immutability
- **ADP-11:** Replay-safe retention policy (archived events queryable)
- **XC-04:** Kernel determinism (transition function is pure)
- **Service task design:** Recording of service outputs in event log

---

## Notes

**Tier 4 (LLM) nodes:** When Tier 4 is implemented, LLM responses will be recorded in `llm_response` events. Replay will read these recorded outputs rather than re-invoking the LLM. This test spec is forward-compatible with that design (see TC-XC-05-06 for SERVICE_TASK example pattern).
