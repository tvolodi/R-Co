# Test Spec: WASM-01-14 — Wasm Module Execution

**Requirements:** WASM-01 through WASM-14  
**Test Layer:** Integration (real backend + real database)  
**Priority:** MUST / SHOULD (as specified per requirement)

This specification covers all 14 Wasm-related requirements: runtime integration, module ABI, compilation pipeline, capability sandboxing, resource limits, host API parity with Lua, and module lifecycle management.

---

## WASM-01 — Wasmtime Integration

**Requirement:** WASM-01 — Wasmtime is embedded via C API, linked statically into the platform binary.  
**Priority:** MUST

### AC-1.1: Static linking verified

| Setup | No external Wasmtime library dependency |
|---|---|
| Verification | Run `ldd` (on Linux) or equivalent on the platform binary |
| Expected | Output does NOT reference any `libwasmtime.so` or equivalent shared library |

### AC-1.2: Wasmtime engine initialization succeeds

| Setup | Attempt to initialize Wasmtime engine at platform startup |
|---|---|
| Execution | Platform start: `BPM_DB_URL=postgresql://... BPM_DB_POOL_SIZE=10 ./platform` |
| Expected | Platform starts without error; engine is ready for module loading |

## WASM-02 — Module ABI Contract

**Requirement:** WASM-02 — Every module MUST export: `init`, `execute`, `deinit`, `get_capabilities`.  
**Priority:** MUST

### TC-WASM-02-01: Valid module with all required exports passes registration

| Setup | Compile a minimal Wasm module with all four exports; attempt to register |
|---|---|
| Execution | POST /api/v1/wasm/modules with compiled `.wasm` bytes and manifest |
|Expected | HTTP 201 with module_id; module is registered and ready for use |
| Acceptance Criterion Mapped | AC-2.1: All four exports present → registration succeeds |

### TC-WASM-02-02: Missing `execute` export → registration rejected

|---|---|
| Execution | POST /api/v1/wasm/modules with incomplete module |
| Expected | HTTP 422 with RFC 9457 error detailing missing `execute` export |
| Acceptance Criterion Mapped | AC-2.2: Missing required export → structured error |

### TC-WASM-02-03: Missing `get_capabilities` export → registration rejected

| Setup | Compile Wasm module with `init`, `execute`, `deinit` only (no `get_capabilities`) |
|---|---|
| Execution | POST /api/v1/wasm/modules with incomplete module |
| Expected | HTTP 422 with RFC 9457 error listing missing export |
| Acceptance Criterion Mapped | AC-2.1: All four exports required |

### TC-WASM-02-04: Module with extra unspecified exports succeeds

| Setup | Compile Wasm module with all four required exports plus additional custom exports |
|---|---|
| Execution | POST /api/v1/wasm/modules with the module |
| Expected | HTTP 201; module registered successfully — extra exports are ignored |
| Acceptance Criterion Mapped | AC-2.1: Four required exports; extras permitted |

### TC-WASM-02-05: Invalid ABI version → registration rejected

| Setup | Compile Wasm module with correct exports but `get_capabilities()` returns unsupported version field |
|---|---|
| Execution | POST /api/v1/wasm/modules; attempt instantiation and call `get_capabilities()` |
| Expected | HTTP 422 during ABI validation; module rejected as incompatible |
| Acceptance Criterion Mapped | AC-2.3: ABI version validation |

## WASM-03 & WASM-04 — Compilation Pipeline and Caching

**Requirement:** WASM-03 — Source compilation job; WASM-04 — Compile caching  
**Priority:** MUST

### TC-WASM-03-01: Compilation job creation returns job ID

| Setup | Submit Zig source code for a Wasm module via compilation API |
|---|---|
| Execution | POST /api/v1/wasm/compile with `source = "<zig source>"` |
| Expected | HTTP 202 with `job_id` (UUID); job is enqueued |
| Acceptance Criterion Mapped | WASM-03 AC-1: Compilation request returns job ID |

### TC-WASM-03-02: Compilation completes out-of-band

| Setup | Submit compilation job; poll for completion |
|---|---|
| Execution | POST → job_id; then poll GET /api/v1/wasm/compile/:job_id until status = COMPLETED |
| Expected | After ~1–5 seconds, status becomes COMPLETED with `artifact_hash` (SHA-256 of `.wasm` binary) |
| Acceptance Criterion Mapped | WASM-03 AC-2: Completion notification with artifact hash; does not block request handler |

### TC-WASM-03-03: Compilation failure captured in job result

| Setup | Submit Zig source with syntax error |
|---|---|
| Execution | POST /api/v1/wasm/compile with invalid source; poll for completion |
| Expected | status = FAILED; `error_message` contains compiler diagnostic; no `.wasm` artifact created |
| Acceptance Criterion Mapped | WASM-03 AC-3: Error handling; out-of-band processing |

### TC-WASM-04-01: Identical source twice — cache hit on second

| Setup | Submit Zig source for module A; wait for COMPLETED status; submit same source again |
|---|---|
| Execution | First submission: POST /api/v1/wasm/compile → job_id_1; wait for COMPLETED; second: POST → job_id_2 |
| Expected | Second submission returns immediately (or very quickly) with `cached = true` and same `artifact_hash` as first |
| Acceptance Criterion Mapped | WASM-04 AC-1: Identical source not recompiled; cache hit |

### TC-WASM-04-02: Source hash + toolchain version keying

| Setup | Compile source S with toolchain V1; change toolchain to V2; recompile same source |
|---|---|
| Execution | Track the `toolchain_version` field in compilation requests; observe cache behavior |
| Expected | Changing toolchain version causes recompilation (different cache key); same source + same toolchain = cache hit |
| Acceptance Criterion Mapped | WASM-04 AC-2: Keying by source hash + toolchain version |

### TC-WASM-04-03: Artifact retrieved from cache is byte-identical

| Setup | Compile source S twice (via cache hit); retrieve both artifacts and compare binary content |
|---|---|
| Execution | First compile → artifact_1 (binary bytes); second compile → artifact_2 (from cache) |
| Expected | `artifact_1 bytes == artifact_2 bytes` (SHA-256 hash identical) |
| Acceptance Criterion Mapped | WASM-04 AC-3: Cache coherence |

## WASM-08 — Memory Isolation

**Requirement:** WASM-08 — Modules execute in isolated linear memory; host validates all pointers.  
**Priority:** MUST

### TC-WASM-08-01: Valid pointer dereference succeeds

| Setup | Module exports a function that accepts a pointer and length, reads data from its linear memory, and calls a host function with the data |
|---|---|
| Execution | Invoke module function with pointer to valid buffer in module's linear memory |
| Expected | Host successfully reads the pointer-referenced data; no crash; data is correct |
| Acceptance Criterion Mapped | WASM-08 AC-1: Valid pointers are dereferenced correctly |

### TC-WASM-08-02: Out-of-bounds pointer → structured trap

| Setup | Module function attempts to pass a pointer beyond the module's linear memory bounds (e.g., pointer = 1MB, linear memory size = 64KB) |
|---|---|
| Execution | Host code validates the pointer before dereferencing; attempt to read the out-of-bounds data |
| Expected | Structured error (trap) returned; no host memory corruption; no crash |
| Acceptance Criterion Mapped | WASM-08 AC-2: Out-of-bounds pointers trap cleanly |

### TC-WASM-08-03: Null pointer validation

| Setup | Module attempts to pass pointer = 0 to a host function |
|---|---|
| Execution | Host validates pointer = 0 before dereferencing |
| Expected | Error returned (null pointer is invalid); no segfault |
| Acceptance Criterion Mapped | WASM-08 AC-3: Null pointers are rejected |

### TC-WASM-08-04: Negative length parameter

| Setup | Module function passes a valid pointer but length = -1 (or very large unsigned value) |
|---|---|
| Execution | Host validates (pointer, length) pair before allocation/copy |
| Expected | Error returned; no memory corruption; no allocation of gigabyte buffer |
| Acceptance Criterion Mapped | WASM-08 AC-4: Invalid length parameters are caught |

## WASM-09 — Fuel-Based Execution Limit

**Requirement:** WASM-09 — Host enables fuel mechanism; per-invocation fuel budget; exhaustion terminates with error.  
**Priority:** MUST

### TC-WASM-09-01: Infinite loop terminates on fuel exhaustion

| Setup | Module source contains `while (true) { /* no fuel-consuming instructions */ }` infinite loop; fuel budget = 1000 units |
|---|---|
| Execution | Invoke module with fuel budget set to 1000; let loop run |
| Expected | Execution terminates within ~1 second (before infinite loop runs forever); error indicates fuel exhaustion |
| Acceptance Criterion Mapped | WASM-09 AC-1: Infinite loop terminates within fuel budget |

### TC-WASM-09-02: Fuel exhaustion produces structured error

| Setup | Module consuming high fuel count; low fuel budget |
|---|---|
| Execution | Invoke module with fuel budget = 100; expect exhaustion |
| Expected | Error structure includes: module_id, reason = "fuel_exhausted", remaining_fuel = 0 |
| Acceptance Criterion Mapped | WASM-09 AC-2: Error is structured and identifies the limit |

### TC-WASM-09-03: Legitimate computation completes before fuel runs out

| Setup | Module function sums 1..1000 (known fuel cost); fuel budget = 10000 |
|---|---|
| Execution | Invoke module function |
| Expected | Function completes successfully; result is correct; fuel remaining > 0 |
| Acceptance Criterion Mapped | WASM-09 AC-3: Legitimate work completes |

### TC-WASM-09-04: Per-invocation fuel budget isolation

| Setup | Invoke the same module function twice with different fuel budgets: first with budget = 10000, second with budget = 100 |
|---|---|
| Execution | First invocation completes normally; second invocation exhausts fuel and terminates |
| Expected | First and second invocations have independent fuel budgets; one exhaustion does not affect the other |
| Acceptance Criterion Mapped | WASM-09 AC-4: Fuel budgets are per-invocation |

**Requirement:** WASM-13 — Pool instances per module for amortized instantiation cost.  
**Priority:** SHOULD

### TC-WASM-13-01: Pooled instance reuse reduces cold startup latency

| Execution | Invoke M1 five times sequentially; measure latency of each invocation |

| Acceptance Criterion Mapped | WASM-13 AC-1: Pooling reduces p50 latency |

### TC-WASM-13-02: Memory reset between pooled invocations

| Setup | Module M1 with explicit memory layout; first invocation writes data to offset 100; second invocation reads offset 100 |
|---|---|
| Execution | Invoke M1 twice; second invocation checks memory at offset 100 |
| Expected | Second invocation reads zero (or initial state); no leftover data from first invocation |

|---|---|
| Execution | Invoke M1 twice from pool; second invocation checks the global |

| Acceptance Criterion Mapped | WASM-13 AC-3: State isolation per invocation |

## WASM-14 — Hot Reload

**Requirement:** WASM-14 — New module version activation does not interrupt in-flight invocations.  
**Priority:** MUST

### TC-WASM-14-01: In-flight invocation completes with old version after new version activates

| Acceptance Criterion Mapped | WASM-14 AC-1: In-flight invocations not interrupted |

|---|---|
| Execution | POST /api/v1/wasm/modules/M1/invoke after v2.0 activation |
| Expected | New invocation uses v2.0 (can verify via internal version marker in module or different behavior) |
| Acceptance Criterion Mapped | WASM-14 AC-2: New invocations use new version |

### TC-WASM-14-03: Version metadata tracks active version

| Setup | Activate M1 v1.0; check active version; activate M1 v2.0; check active version again |
|---|---|
| Execution | GET /api/v1/wasm/modules/M1 before and after activation |
| Expected | Before: `active_version = "1.0"`; after: `active_version = "2.0"` |
| Acceptance Criterion Mapped | WASM-14 AC-3: Version management state is consistent |

### TC-WASM-14-04: Multiple concurrent invocations maintain version isolation

| Setup | Start 5 concurrent invocations of M1 v1.0; mid-execution of each, activate M1 v2.0; wait for all to complete |
|---|---|
| Execution | Launch 5 async tasks, each invoking M1; after ~2 seconds (before completion), activate v2.0; wait for all to finish |
| Expected | All 5 in-flight invocations complete with v1.0; no interference; no concurrent version mixing |
| Acceptance Criterion Mapped | WASM-14 AC-4: Concurrent invocation isolation during hot reload |

## Integration Test Notes

### Test Database Setup

All integration tests execute against a real PostgreSQL database (bpm_test). Each test:
1. Starts with a clean database (or transaction-wrapped state)
2. Creates necessary definitions, module artifacts, and instances via API or internal functions
3. Executes the test scenario
4. Verifies state via direct DB queries or API calls
5. Rolls back to initial state (no permanent side effects)

### Module Artifacts

Test modules are pre-compiled minimal Wasm binaries (fixture files in `tests/fixtures/wasm/`) covering:
- `valid_full_abi.wasm` — all four exports, empty implementation
- `missing_execute.wasm` — init, deinit, get_capabilities only
- `with_service_call.wasm` — includes `platform_call_service` import
- `with_file_access.wasm` — attempts `wasi:filesystem/types` import
- `infinite_loop.wasm` — while(true) loop for fuel/timeout tests
- `memory_allocator.wasm` — allocates memory up to cap
- `time_calls.wasm` — calls `platform.now()` multiple times
- `state_writer.wasm` — writes to memory at known offsets

### No Mocks

Per DIRECTIVE T-1: all integration tests execute against the real backend server and real PostgreSQL database. No Wasmtime mocking, no in-memory runtime stubs. The test verifies actual Wasmtime behavior.
