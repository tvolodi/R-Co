# Test Spec: PD-UI-09 through PD-UI-12 — Process Designer Canvas

## PD-UI-09 — Visual graph canvas

**Requirement:** The canvas MUST render the process definition graph using React Flow. Nodes are represented as labelled cards; directed edges are represented as arrows with optional condition labels.

---

### TC-PDUI09-01: Canvas renders with existing definition graph

**Given:** A DRAFT definition exists with a non-trivial graph (multiple nodes and edges)
**When:** A PROCESS_DESIGNER user opens the definition editor page at `/definitions/{id}`
**Then:** Screen shows a React Flow canvas containing all nodes from the definition graph positioned as labelled cards, and all edges as directed arrows between the correct source and target nodes
**Layer:** e2e
**Acceptance criterion mapped:** Visual graph canvas renders definition graph

---

### TC-PDUI09-02: Canvas shows all edges between nodes

**Given:** A definition exists with edges connecting multiple nodes
**When:** The user opens the definition editor
**Then:** Screen shows directed arrow edges from each source node to each target node; edges are visible as solid lines with arrow markers
**Layer:** e2e
**Acceptance criterion mapped:** Directed edges rendered as arrows

---

### TC-PDUI09-03: Read-only mode shows non-interactive canvas for ACTIVE definitions

**Given:** A definition with status ACTIVE exists
**When:** A user opens the definition editor page
**Then:** Screen shows a read-only banner "This definition is ACTIVE. Open a DRAFT version to edit."; the React Flow canvas is visible with `nodesDraggable=false`, `nodesConnectable=false`; nodes are still clickable (property panel opens in read-only mode); the node palette is hidden; the Save button is hidden
**Layer:** e2e
**Acceptance criterion mapped:** Read-only mode for non-DRAFT definitions

---

### TC-PDUI09-04: JSON textarea fallback visible via debug drawer toggle

**Given:** The definition editor page is open for a DRAFT definition
**When:** The user clicks the "Show Raw JSON" toggle in the toolbar
**Then:** A collapsible drawer opens at the bottom showing the current `DefinitionGraph` as pretty-printed JSON in a read-only `<textarea>`
**Layer:** e2e
**Acceptance criterion mapped:** JSON textarea fallback accessible via debug drawer

---

## PD-UI-10 — Node palette

**Requirement:** A sidebar palette MUST list all supported node types: START, END, HUMAN_TASK, EXCLUSIVE_GATEWAY, PARALLEL_GATEWAY (and SERVICE_TASK, TIMER, SUB_PROCESS when supported). Nodes are added to the canvas by drag-and-drop or double-click.

---

### TC-PDUI10-01: Node palette is visible listing supported node types

**Given:** The definition editor page is open for a DRAFT definition
**When:** The page loads
**Then:** Screen shows a left sidebar node palette containing draggable entries for node types: START, END, HUMAN_TASK, EXCLUSIVE_GATEWAY, PARALLEL_GATEWAY (and SERVICE_TASK, TIMER, SUB_PROCESS if the backend supports them)
**Layer:** e2e
**Acceptance criterion mapped:** Node palette visible with all supported types

---

### TC-PDUI10-02: Double-clicking a palette item adds a node to the canvas

**Given:** The definition editor page is open with a DRAFT definition
**When:** The user double-clicks a palette item (e.g. HUMAN_TASK)
**Then:** A new node of the corresponding type appears on the canvas at a reasonable default position; the canvas now shows the new node alongside existing nodes
**Layer:** e2e
**Acceptance criterion mapped:** Double-click palette adds node to canvas

---

### TC-PDUI10-03: Deleting a node removes it from the canvas

**Given:** The canvas has at least one node (existing or newly added)
**When:** The user selects a node (click) and presses the Delete key
**Then:** The node is removed from the canvas; the associated edges are also removed
**Layer:** e2e
**Acceptance criterion mapped:** Delete node removes it and connected edges

---

## PD-UI-11 — Edge creation

**Requirement:** The user MUST connect two nodes by dragging from a source handle to a target handle. Edges from EXCLUSIVE_GATEWAY nodes MUST prompt for a CEL condition expression or a "default edge" toggle on creation.

---

### TC-PDUI11-01: Dragging from source handle to target handle creates an edge

**Given:** The canvas has at least two nodes that can be connected (e.g., START with a source handle and HUMAN_TASK with a target handle)
**When:** The user drags from the source handle of one node to the target handle of another node
**Then:** A new directed edge appears connecting the two nodes; the edge has `type: 'condition'` and default data `{ condition: undefined, isDefault: false }`
**Layer:** e2e
**Acceptance criterion mapped:** Edge created by drag from source to target handle

---

### TC-PDUI11-02: ConditionDialog appears for EXCLUSIVE_GATEWAY edge creation

**Given:** An EXCLUSIVE_GATEWAY node and another node (e.g., HUMAN_TASK) exist on the canvas
**When:** The user drags from a source handle of the EXCLUSIVE_GATEWAY to the target handle of the other node
**Then:** A ConditionDialog appears with title "Edge Condition", a CEL expression text input with placeholder "e.g. status == 'approved'", and a "Default edge (no condition)" checkbox; the edge is created only after the user confirms
**Layer:** e2e
**Acceptance criterion mapped:** ConditionDialog appears for EXCLUSIVE_GATEWAY source edges

---

### TC-PDUI11-03: Edge deletion removes the edge from the canvas

**Given:** An edge exists between two nodes on the canvas
**When:** The user clicks the edge to select it and presses the Delete key
**Then:** The edge is removed from the canvas; nodes remain unaffected
**Layer:** e2e
**Acceptance criterion mapped:** Edge deletion

---

## PD-UI-12 — Node properties panel

**Requirement:** Clicking a node MUST open an inline properties panel where the user can set all required and optional attributes for that node type (e.g. `assignee_type`, `assignee_ref`, `form_schema`, `escalation_timer_duration` for HUMAN_TASK).

---

### TC-PDUI12-01: Clicking a node opens the property panel

**Given:** The definition editor page is open
**When:** The user clicks a node on the canvas (e.g., a HUMAN_TASK node)
**Then:** A right-side property panel slides in (width: 400px) showing the node type icon and label at the top; a "Name" text input with the node's current name; a "Description" textarea; type-specific attribute fields appropriate for the node type (e.g., `assignee_type` select, `assignee_ref` input for HUMAN_TASK)
**Layer:** e2e
**Acceptance criterion mapped:** Property panel opens on node click

---

### TC-PDUI12-02: Editing a property updates node data locally

**Given:** The property panel is open for a HUMAN_TASK node with name "Task 1"
**When:** The user changes the name in the property panel to "Updated Task"
**Then:** The node on the canvas reflects the updated name; no API call is made (dirty flag set); the canvas remains in edit mode
**Layer:** e2e
**Acceptance criterion mapped:** Property edits update local state immediately

---

### TC-PDUI12-03: Saving the definition persists property changes

**Given:** The user has edited a node property (e.g., changed the name) and the canvas is dirty
**When:** The user clicks the Save button in the toolbar
**Then:** The graph is serialized and sent via `PUT /definitions/:id`; a success toast "Definition saved" appears; after reloading the page, the canvas shows the updated property value
**Layer:** e2e
**Acceptance criterion mapped:** Save persists property changes via PUT; changes survive page reload

---

### TC-PDUI12-04: Property panel shows correct fields per node type

**Given:** The canvas has nodes of different types (HUMAN_TASK, SERVICE_TASK, TIMER, EXCLUSIVE_GATEWAY)
**When:** The user clicks each node type
**Then:** The property panel shows the appropriate fields for that type: HUMAN_TASK shows `assignee_type`, `assignee_ref`, `form_schema`, `escalation_timer_duration`; SERVICE_TASK shows `service_type`, `service_config`, `input_mapping`, `output_mapping`; TIMER shows `timer_type`, `timer_duration`; EXCLUSIVE_GATEWAY shows no node-level attributes
**Layer:** e2e
**Acceptance criterion mapped:** Type-specific attribute fields in property panel

---

## Save workflow (derived)

**Requirement:** Save button calls PUT with full graph replacement; success toast; unsaved changes guard.

---

### TC-SAVE-01: Modified canvas saves via PUT and reload shows changes

**Given:** A DRAFT definition with a simple graph (START→END)
**When:** The user adds a HUMAN_TASK node via the palette and clicks Save; then reloads the page
**Then:** The canvas shows the updated graph with the HUMAN_TASK node between START and END (with connecting edges)
**Layer:** e2e
**Acceptance criterion mapped:** Modified canvas persists via PUT; changes survive reload

---

### TC-SAVE-02: Unsaved changes dialog on navigation away

**Given:** The user has made changes on the canvas (dirty flag is set)
**When:** The user attempts to navigate away from the definition editor page
**Then:** A confirmation dialog appears: "You have unsaved changes. Discard them?"; confirming discards stays on page or closes; cancelling aborts navigation
**Layer:** e2e
**Acceptance criterion mapped:** Unsaved changes guard with confirmation dialog
