# Test Spec: LUA-01-05 — Lua Script Execution Sandbox

**Requirements:** LUA-01, LUA-02, LUA-03, LUA-04, LUA-05  
**Priority:** MUST  
**Test layer:** unit (binary verification, state isolation, stdlib checks, capability enforcement)

---

## 1. Overview

This specification covers comprehensive testing for LuaJIT integration with the BPM platform. Tests verify:

1. **LUA-01:** Static linking — no runtime Lua library dependencies
2. **LUA-02:** State isolation — scripts cannot see globals from previous executions
3. **LUA-03:** Stdlib restrictions — only math, string, table are available; dangerous functions removed
4. **LUA-04:** Bytecode rejection — source text only; binary `.lc` files are rejected
5. **LUA-05:** Host API and capability enforcement — platform.* functions check capabilities before executing

---

## 2. Test Suite: LUA-01 — Binary Dependency Verification

### TC-LUA-01-01: Platform binary has no Lua .so dependency (Linux/macOS)

**Given:** The compiled `bpm` binary  
**When:** `ldd ./zig-cache/bin/bpm` or equivalent binary inspection is run  
**Then:** Output contains no reference to `lua`, `luajit`, `.so`, or dynamic Lua libraries  
**Layer:** unit (binary inspection)  
**Acceptance criterion mapped:** LUA-01 requirement: "no external Lua shared library at runtime"

**Test setup:**
- Build the platform: `zig build`
- Capture binary path: `./zig-cache/bin/bpm`

**Test action:**
```bash
ldd ./zig-cache/bin/bpm | grep -i lua || echo "OK: No Lua shared library found"
```

**Expected:** Output is empty or shows "OK" message (no Lua library listed)

**Edge cases:**
- Cross-platform: On Windows, inspect with `objdump -p` or `dumpbin /imports` instead
- Fallback: Use `nm -D` to check for undefined dynamic symbols; no `lua_` symbols should be unresolved

---

### TC-LUA-01-02: Lua C-interop bindings compile correctly

**Given:** Lua FFI bindings in `src/lua/luajit_bindings.zig`

**Layer:** unit (compilation)

## 3. Test Suite: LUA-02 — State Isolation

### TC-LUA-02-01: First script sets global, second script sees undefined

**Given:** Script execution context with fresh Lua state  
**When:** Script A sets `globalVar = 42; return "done"` and executes  
**And:** Script B reads `if globalVar == nil then return "undefined" else return globalVar end` and executes separately  
**Then:** Script A returns success with value `"done"` and Script B returns success with value `"undefined"`  
**Layer:** unit (state isolation)  
**Acceptance criterion mapped:** LUA-02: "Setting a global in one execution does not affect another"

**Test setup:**
```
Initialize CapabilitySet with no capabilities
Create ExecutionContext with instance_id = "inst-001"
```

**Test action:**
```
1. Execute script: `globalVar = 42; return "done"`
   - Capture result: success = true, value = ScriptValue.string("done")
2. Execute script (in new invocation): `if globalVar == nil then return "undefined" else return globalVar end`
   - Capture result: success = true, value = ScriptValue.string("undefined")
```

**Expected:**
- First script: `success = true`, `value.string = "done"`
- Second script: `success = true`, `value.string = "undefined"` (globalVar is not visible)

**Edge cases:**
- Empty first script (no globals set): second script still sees `globalVar = nil`
- Complex global object: `t = { x = 1 }; return "set"` does not leak `t` to next invocation

---

### TC-LUA-02-02: Concurrent script executions maintain isolated state

**Given:** Three concurrent execution requests to the same platform instance  
**When:** 
- Script A: `x = 1; return x` (concurrent thread 1)
- Script B: `x = 2; return x` (concurrent thread 2)
- Script C: `return x or "nil"` (concurrent thread 3)  
**Then:** Each script executes in its own Lua state and returns its isolated result  
**Layer:** unit (concurrency)  
**Acceptance criterion mapped:** LUA-02: "State MUST NOT leak between script invocations"

**Test setup:**
```
Spawn 3 concurrent execution tasks
Each task has a unique ExecutionContext
No shared Lua state between tasks
```

**Test action:**
```
1. Launch Script A: returns 1
2. Launch Script B: returns 2
3. Launch Script C: returns nil (or "nil" if nil is returned as string)
   Wait for all 3 to complete
```

**Expected:**
- Script A returns: `success = true, value = 1`
- Script B returns: `success = true, value = 2`
- Script C returns: `success = true, value = "nil"` (x is not defined in C's state)

**Edge cases:**
- Scripts complete in arbitrary order
- All three scripts complete successfully despite concurrent execution
- No race conditions or memory corruption

## 5. Test Suite: LUA-04 — Bytecode Rejection

### TC-LUA-04-01: Bytecode script is rejected with magic number detection

**Given:** Lua bytecode starting with magic 0x1b4c7561  
**When:** `executeScript(context, bytecode_data)` is called  
**Then:** Execution fails with error message "Bytecode is not allowed" or similar  
**Layer:** unit (bytecode detection)  
**Acceptance criterion mapped:** LUA-04: "refused to load Lua bytecode"

**Test setup:**
```
Create bytecode sample with magic [0x1b, 0x4c, 0x75, 0x61] ("ESC L u a")
Create ExecutionContext
```

**Test action:**
```
1. Create test bytecode: byte sequence = [0x1b, 0x4c, 0x75, 0x61, ...]
2. Call executeScript(context, bytecode_bytes)
3. Capture result
```

**Expected:**
- `success = false`
- `error_message` contains "Bytecode" or "not allowed" or "source text"

**Edge cases:**
- Bytecode exactly 4 bytes: still rejected
- Bytecode 3 bytes (not full magic): does not trigger rejection (tries to compile as source, fails later)
- Binary data that is not Lua bytecode but starts with 0x1b: rejected as suspected bytecode

---

## 10. Notes for TEST-RUNNER

When executing these tests:

1. **Binary verification (TC-LUA-01-01):** Run once per platform build. Can be skipped on rebuild if build command unchanged.
2. **State isolation (TC-LUA-02-*):** Verify `lua_close()` is called after each test to ensure cleanup.
3. **Stdlib tests (TC-LUA-03-*):** All negative tests should verify the error message clearly indicates the module/function is unavailable.
4. **Bytecode rejection (TC-LUA-04-*):** Use real Lua bytecode generated by `luac` for authenticity.
5. **Capability checks (TC-LUA-05-*):** Each test must use a CapabilitySet explicitly missing the required capability.
6. **Concurrency (TC-LUA-02-02, TC-LUA-EDGE-06):** Use task spawning (e.g., std.Thread) to verify true parallel execution safety.
7. **Memory safety:** Run all unit tests under valgrind or ASAN to detect leaks and races.
