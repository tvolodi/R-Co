# ISS-204 Test Spec: Audit log inside state-change transaction

**Requirement:** ISS-204 — Write audit_log inside the state-change transaction
**Test layer:** Integration (requires PostgreSQL)
**Design artefact:** src/design/iss204_audit_in_transaction.md

---

## MUST test cases

### TC-ISS204-01: Audit row committed in same transaction as event

Given: A running BPM instance
When: A state-changing API call is made (instance create, task complete, etc.)
Then: The audit row and the event row are both committed atomically
Evidence: Query events and audit_entries for the same instance_id — both rows exist with timestamps within the same transaction window

### TC-ISS204-02: Rollback leaves no orphan audit row

Given: A handler transaction that will fail (e.g., duplicate correlation key)
When: The transaction rolls back
Then: No audit row is written for the failed operation
Evidence: Query audit_entries for the resource — no matching row exists

### TC-ISS204-03: before_state/after_state captured correctly

Given: An instance with known variables before a task completion
When: A task is completed with new output variables
Then: The audit row records before_state (pre-completion variables) and after_state (post-completion variables)
Evidence: Parse before_state and after_state JSON — they differ by the new variable values
