# Test Spec: EXP-301 — Async Effects Subsystem

**Requirement:** EXP-301 — Async effects subsystem: transactional effects outbox, background worker polling with retry/backoff, result re-entry into execution engine  
**Priority:** MUST  
**Test layers:** integration

## Requirement Summary

The effects subsystem decouples all outbound I/O from the execution engine. The engine emits `EFFECT_EMITTED` events (pure data) when activating SERVICE_TASK or EFFECT nodes; a background worker polls the `effects_outbox` table for due effects, attempts delivery via the configured executor (HTTP, email, stub), and re-enters the result via `EFFECT_COMPLETED` or `EFFECT_FAILED` events into the instance.

## Test Cases

### TC-EXP-301-01: Effects Outbox Insert and Query for Due Effects
**Given:** a tenant and instance provisioned in the test database  
**When:** `insertEffectInTx()` is called within a transaction with a valid `EffectSpec`  
**Then:** 
  - An `effects_outbox` row is inserted with `status='pending'`, `attempt_count=0`, `next_attempt_at=NOW()+5s`
  - The assigned `effect_delivery_id` is returned and is a valid UUID
  - Subsequent query `SELECT * FROM effects_outbox WHERE status='pending' AND next_attempt_at <= now()` returns zero rows (because next_attempt_at is in the future)

**Acceptance criteria mapped:** Outbox transactional insert with default backoff

### TC-EXP-301-02: Worker Sweeps and Finds Due Effects
**Given:** an effect has been inserted with `next_attempt_at` in the past  
**When:** the worker performs `sweepOnce()` (or equivalent poll query)  
**Then:**
  - The row is selected via `SELECT ... WHERE status='pending' AND next_attempt_at <= now() FOR UPDATE SKIP LOCKED`
  - The effect is available for execution

**Acceptance criteria mapped:** Worker polling / selection of due effects

### TC-EXP-301-03: HTTP Delivery Success — 200 OK Response
**Given:** an effect in the outbox with `status='pending'` pointing to a valid HTTP endpoint  
**When:** the worker executes the HTTP effect via adapter and receives a 200 response  
**Then:**
  - `markDelivered()` is called, setting `status='delivered'`, `last_http_status=200`
  - `reenterEffectResult()` is called with `succeeded=true`, which:
    - Inserts an `EFFECT_COMPLETED` event into the event log
    - Drives the transition function with `effect_completed` input event
    - Instance state reflects the token moving to the catch-event node (or next node in the graph)
    - `instance_waits` row (if present) is deleted/updated

**Acceptance criteria mapped:** Success path: mark delivered, emit EFFECT_COMPLETED, re-enter

### TC-EXP-301-04: HTTP Delivery Retriable Failure — 5xx Response
**Given:** an effect with `status='pending'`, `attempt_count < max_attempts`, `next_attempt_at` in the past  
**When:** the worker executes the HTTP effect and receives a 500 response  
**Then:**
  - `markRetry()` is called, incrementing `attempt_count` and setting `next_attempt_at = NOW() + backoff_interval`
  - For the first retry (attempt 1→2), the backoff interval is `30 seconds`
  - The effect remains `status='pending'` for future polling
  - No `EFFECT_COMPLETED` event is emitted yet

**Acceptance criteria mapped:** Retry path: mark for retry, push next_attempt_at forward per backoff schedule

### TC-EXP-301-05: Backoff Schedule Verification — All 5 Attempts
**Given:** the runtime backoff helper is evaluated for retry counts 0 through 5  
**When:** the helper returns the delay for each count  
**Then:** the schedule matches the implemented table:
  - 0 → 5s
  - 1 → 30s
  - 2 → 2min
  - 3 → 10min
  - 4 and beyond → 30min cap

**Acceptance criteria mapped:** Backoff schedule helper matches the runtime table

### TC-EXP-301-06: Max Retries Exhausted — Dead-Letter Queue
**Given:** an effect with `attempt_count=5` (max), `status='pending'`, `next_attempt_at` in the past  
**When:** the worker attempts delivery and receives a 5xx response or the attempt count check fires  
**Then:**
  - `status` is set to `'dead_lettered'`
  - `reenterEffectResult()` is called with `succeeded=false`
  - An `EFFECT_FAILED` event is inserted
  - The transition function is driven with `effect_failed` input, routing to the error/catch node
  - A `dlq_items` row (if present) may be created

**Acceptance criteria mapped:** DLQ path: mark dead-lettered after max retries, emit EFFECT_FAILED

### TC-EXP-301-07: Idempotency via effect_event_id Header
**Given:** an HTTP effect with a known `effect_event_id` (the UUID of the EFFECT_EMITTED event)  
**When:** the worker delivers the effect through the HTTP adapter  
**Then:**
  - The outgoing HTTP request contains `Idempotency-Key: <effect_event_id>`
  - The value is captured from a live local HTTP server, not a mock

**Acceptance criteria mapped:** HTTP adapter injects Idempotency-Key on the real request path

### TC-EXP-301-08: Idempotent Effect Append via Event Store Deduplication
**Given:** an instance that appends an `EFFECT_EMITTED` event with an idempotency key  
**When:** the same append is executed twice with the same key  
**Then:**
  - The first append persists a new event
  - The second append is reported as a duplicate
  - The event log contains one committed row for that key

**Acceptance criteria mapped:** Idempotent append is enforced by the event store

### TC-EXP-301-09: Email Adapter (Stub — Placeholder for EXP-501)
**Given:** an effect of kind `email` with spec containing `to`, `subject`, `body`  
**When:** the worker executes the effect via the email adapter  
**Then:**
  - The worker exercises the email delivery path
  - The adapter returns the deterministic `SecretResolutionFailed` error
  - The outbox row remains retryable and records the failure reason

**Acceptance criteria mapped:** Email adapter path is exercised without SMTP I/O

### TC-EXP-301-10: Worker Skips Dead-Lettered and Delivered Effects
**Given:** effects_outbox contains rows with `status='dead_lettered'` and `status='delivered'`  
**When:** the worker queries for due effects via `SELECT ... WHERE status='pending' ...`  
**Then:**
  - Neither `dead_lettered` nor `delivered` rows are selected
  - Only `pending` rows are included

**Acceptance criteria mapped:** Worker query filters by status='pending'

### TC-EXP-301-11: EFFECT_COMPLETED Event Drives Transition
**Given:** an instance waiting at a catch-event node after emitting an effect  
**When:** `reenterEffectResult(succeeded=true, response_body, http_status)` is called  
**Then:**
  - An `EFFECT_COMPLETED` event is inserted with the response body and status
  - The transition function is invoked with this event as input
  - The instance state reflects the token advancing from the catch node to the next node
  - Pending events generated by the transition are persisted

**Acceptance criteria mapped:** Success re-entry drives transition and advances instance state

### TC-EXP-301-12: EFFECT_FAILED Event Drives Catch Error Node
**Given:** an instance waiting at a catch-event node after emitting an effect  
**When:** `reenterEffectResult(succeeded=false, error_detail)` is called after max retries exhausted  
**Then:**
  - An `EFFECT_FAILED` event is inserted with error details
  - The transition function is invoked with this event as input
  - The instance state reflects the token advancing to an error/recovery node (if modeled) or ERROR state
  - A `dlq_items` row is created if applicable

**Acceptance criteria mapped:** Failure re-entry drives error handling and DLQ

## Integration Test Requirements

- Tests use `TestHarness` for PostgreSQL provisioning and cleanup
- All effect UUIDs are generated fresh per test (no static IDs)
- All correlation keys and instance IDs are unique per test
- Worker behavior is tested via simulated polling (call `sweepOnce()` or equivalent directly)
- No HTTP mocking; tests use a real `http.Client` or a local test HTTP server
- Email adapter tests verify stub behavior (no SMTP calls)
