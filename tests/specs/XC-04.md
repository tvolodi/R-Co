# Test Spec: XC-04 — Kernel Determinism

**Requirement:** XC-04 — The core execution kernel (event append, state transitions, scheduler, task activation, audit writes) contains no LLM calls and is deterministic by design.  
**Priority:** MUST  
**Test layer:** static analysis + unit tests + integration

---

## Overview

XC-04 is a **design constraint** enforced through static analysis and code review, not a functional feature requiring E2E tests. The kernel modules are:

- `src/event_store/store.zig` — event append logic
- `src/engine/transition.zig` — pure state transition (zero I/O)
- `src/scheduler/scheduler.zig` — timer polling and firing
- `src/tasks/manager.zig` — task lifecycle
- `src/obs/audit.zig` — audit chain hash computation
- `src/db/pool.zig`, `src/db/migrations.zig` — database access

The constraint is:
1. **No LLM API patterns** in kernel modules (verified by grep)
2. **Pure transition function** in `src/engine/transition.zig` (no I/O, no randomness, no time calls)
3. **Deterministic scheduler** firing (timer order is reproducible)

---

## Test Cases

### TC-XC-04-01: Static analysis — no LLM API patterns in kernel modules

**Given:** The kernel module source files listed above.

**When:** A grep search is performed for LLM API patterns (e.g., "llm", "openai", "anthropic", "model_inference", "claude").

**Then:**
- Zero matches are found in kernel module files
- Matches in comments or documentation are allowed
- Non-kernel modules (api/routes, tier4/, future Lua/Wasm contexts) are exempt

**Acceptance:**
- `grep -r "llm|openai|anthropic|model_inference" src/event_store src/engine src/scheduler src/tasks src/obs/audit src/db` returns no matches (or only in comments)
- Code review verifies no indirect LLM calls via function pointers or callbacks

**Layer:** static analysis  
**Fixtures:** Source code only

---

### TC-XC-04-02: Pure transition function — no I/O, no randomness, no time calls

**Given:** The `src/engine/transition.zig` module with the `transition()` function.

**When:** The function is inspected for side effects.

**Then:**
- No `std.fs` (file I/O) calls
- No `std.net` (network I/O) calls
- No `std.http` calls
- No `std.crypto.random` calls (random number generation)
- No `std.time` calls (time-dependent behavior)
- No external function calls that might perform I/O (all callees are also pure)
- All parameters and return values are data-only (no allocators passed)

**Acceptance:**
- Code review confirms pure semantics
- Unit tests exercise the function with identical inputs and verify identical outputs (no randomness)

**Layer:** static analysis + unit tests  
**Fixtures:**
- Known event and instance state pairs

---

### TC-XC-04-03: Deterministic scheduler — timers fire in reproducible order

**Given:** A set of scheduled timers with known due dates.

**When:** The scheduler queries due timers twice (independent runs with same state).

**Then:**
- Both runs return timers in identical order
- Order is determined by due date (timestamp), with ties broken by sequence number (deterministic)
- No randomness in query result ordering

**Acceptance:**
- `SELECT * FROM timers WHERE due_at <= NOW() ORDER BY due_at, sequence_number` produces deterministic results
- Scheduler task ordering is reproducible

**Layer:** integration  
**Fixtures:**
- Multiple timers with known due dates

---

### TC-XC-04-04: Audit chain hash computation is deterministic (no randomness)

**Given:** An audit entry with known fields.

**When:** The audit chain hash function is called twice with identical input.

**Then:**
- Both calls produce the same 64-character hex string
- Hash is stable across platform restarts
- No randomness is introduced in hash computation

**Acceptance:**
- SHA-256 implementation in kernel is deterministic by nature
- No CSPRNG or nondeterministic functions are used in hash path

**Layer:** unit test  
**Fixtures:**
- Known audit entry fields

---

### TC-XC-04-05: Event append preserves ordering without randomness

**Given:** Multiple concurrent append requests to the same instance.

**When:** Events are appended.

**Then:**
- Each event receives a deterministic sequence number
- Sequence numbers are monotonically increasing
- Tie-breaking (same microsecond timestamp) uses deterministic sequence, not random ID

**Acceptance:**
- Event ordering is reproducible (no randomness in sequence assignment)
- Replay of same events produces same sequence numbers

**Layer:** integration  
**Fixtures:**
- Concurrent appends to same instance

## Success Criteria

1. Static analysis (grep) confirms zero LLM API patterns in kernel modules
2. Code review confirms pure transition function (no I/O, no randomness)
3. Deterministic scheduler test passes
4. Audit hash stability test passes
5. Event sequence reproducibility test passes
6. All unit tests for pure functions pass with identical-output guarantee
7. No test.skip entries
8. Tests use per-test UUIDs and clean up after themselves
9. Tests fail clearly if BPM_TEST_DB_URL is absent

## Notes

XC-04 is **NOT a functional requirement** that can be tested end-to-end like other MUST requirements. It is a **design constraint** enforced via:
1. **Static analysis:** grep for LLM patterns
2. **Code review:** verify pure function semantics
3. **Unit/integration tests:** verify determinism outputs (identical runs produce identical results)

Violation of XC-04 would manifest as:
- Non-deterministic instance state (different final state given same event log) — caught by XC-05 replay tests
- Kernel-tier LLM calls — caught by grep and code review
- Randomness in event ordering or audit hashing — caught by determinism tests

The platform's XC-05 (Deterministic Replay) test suite serves as a secondary check: if kernel is truly deterministic, replay produces identical state every time.
