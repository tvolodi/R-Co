# Test Spec: EE-10 — Execution Error Handling

**Requirement:** EE-10 — If the engine encounters an unresolvable condition (no matching
gateway edge and no default edge, schema violation on variable merge), it SHALL set the
instance to ERROR status, record an `EXECUTION_ERROR` event with a structured reason, and
halt progression. The instance remains in ERROR status until an operator retries or discards
it via the dead letter API (see OBS-05).

**Priority:** MUST

**Test layer:** integration (all test cases)

---

## Test Cases

### TC-EE-10-01: Gateway no-match triggers ERROR

**Given:** A running process instance whose execution token is at an EXCLUSIVE_GATEWAY
where no outgoing edge condition evaluates to true and no default edge is defined.

**When:** The task preceding the gateway is completed, driving the token into the gateway;
all edge conditions evaluate to false.

**Then:**
- `instance_projections.status` is set to `'ERROR'`.
- An `EXECUTION_ERROR` event is appended to the event store for this instance.
- The event payload contains `error_type = "NO_MATCHING_EDGE"`.
- The event payload contains a non-empty `affected_node` field identifying the gateway node.
- The event payload contains a non-empty `reason` string.
- The event payload contains a `variable_state` field that is a valid JSON object
  (snapshot of variables at error time).
- No further state change is visible after the error is set.

**Layer:** integration

**Acceptance criterion mapped:** "GIVEN an unresolvable condition (no matching gateway
edge + no default edge), WHEN detected, THEN status is set to ERROR and an EXECUTION_ERROR
event is appended."

---

### TC-EE-10-02: Schema violation triggers ERROR

**Given:** A running process instance with a variable `amount` that has a registered
JSON Schema requiring `type: integer, minimum: 0`. The instance has a HUMAN_TASK pending.

**When:** The task is completed with `output_variables = {"amount": -5}`, which fails
the registered schema validation.

**Then:**
- `instance_projections.status` is set to `'ERROR'`.
- An `EXECUTION_ERROR` event is appended to the event store.
- The event payload contains `error_type = "SCHEMA_VIOLATION"`.
- The event payload contains a non-empty `affected_field` field identifying the
  variable key that violated the schema.
- The event payload contains a non-empty `reason` string.
- The event payload contains a `variable_state` field that is a valid JSON object.
- The merge is NOT applied: the original `amount` value remains in
  `instance_projections.variables`; the violating value is absent.

**Layer:** integration

**Acceptance criterion mapped:** "GIVEN an unresolvable condition (schema violation on
variable merge), WHEN detected, THEN status is set to ERROR and an EXECUTION_ERROR event
is appended."

---

### TC-EE-10-03: ERROR instance rejects task completion with HTTP 409

**Given:** A process instance whose `status` is already `'ERROR'` (forced via
`setInstanceError`) and which has a task row in `PENDING` status.

**When:** `completeTask` is called for the pending task (or an attempt is made via the
task completion path).

**Then:**
- `completeTask` returns `CompleteTaskError.InstanceInError`.
- `instance_projections.status` remains `'ERROR'` — no status change.
- No new events are appended after the rejected completion attempt.

**Layer:** integration

**Acceptance criterion mapped:** "GIVEN an instance in ERROR status, WHEN a task
completion is attempted, THEN HTTP 409 is returned."

---

### TC-EE-10-04: ERROR transition is atomic

**Given:** A running ACTIVE process instance.

**When:** `setInstanceError` is called, setting the instance to ERROR status and
appending an EXECUTION_ERROR event.

**Then:**
- After the call completes, BOTH the EXECUTION_ERROR event row in the event store
  AND the `status = 'ERROR'` in `instance_projections` are visible in the same
  SELECT from outside any transaction — there is no state where one write is
  committed but the other is not.
- Before the call completes (i.e. no partial observation during execution), neither
  write is visible (enforced by transaction isolation).

**Layer:** integration

**Acceptance criterion mapped:** "The transition to ERROR and the EXECUTION_ERROR event
append MUST be atomic (single transaction)."

---

### TC-EE-10-05: Concurrent ERROR race — exactly one EXECUTION_ERROR event appended

**Given:** A running ACTIVE process instance.

**When:** Two concurrent goroutines each call `setInstanceError` for the same instance
simultaneously.

**Then:**
- Exactly one EXECUTION_ERROR event exists in the event store for this instance
  after both calls complete.
- `instance_projections.status` is `'ERROR'`.
- One call returns success (`void`) and the other returns `SetInstanceErrorError.AlreadyTerminal`.

**Layer:** integration

**Acceptance criterion mapped:** "Two concurrent operations that both trigger EE-10 on
the same instance: the first to commit wins; the second sees status = ERROR and its
operation is rejected with HTTP 409."

---

### TC-EE-10-06: EXECUTION_ERROR event payload completeness

**Given:** A running process instance that is transitioned to ERROR via `setInstanceError`
with a NO_MATCHING_EDGE error type.

**When:** The EXECUTION_ERROR event is inspected in the event store.

**Then:**
- The `payload` JSON object contains all four required fields: `error_type`,
  `affected_node`, `reason`, and `variable_state`.
- `error_type` is a non-empty string (`"NO_MATCHING_EDGE"` or `"SCHEMA_VIOLATION"`).
- `affected_node` (for NO_MATCHING_EDGE) is a non-empty string identifying the
  gateway node.
- `reason` is a non-empty human-readable string.
- `variable_state` is a valid JSON object (may be `{}` for empty variable maps).
- No required field is null or absent.

**Layer:** integration

**Acceptance criterion mapped:** "EXECUTION_ERROR events MUST carry sufficient context
for an operator to diagnose the root cause without replaying the instance."
