# Test Spec: XC-02 — Audit Immutability

**Requirement:** XC-02 — Audit entries are append-only with cryptographic chaining (SHA-256) so post-insertion tampering is detectable.  
**Priority:** MUST  
**Test layer:** integration

---

## Overview

Audit entries form a cryptographically chained sequence per tenant. Each entry (after migration to XC-02) includes:
- `chain_hash`: SHA-256 hex of a canonical audit payload + predecessor hash
- `prev_chain_hash`: Hash of the immediate predecessor in tenant-scoped order

The chain is immutable: once persisted, no UPDATE or DELETE can modify committed audit rows. Tampering is detectable by recomputing chain hashes and detecting the first mismatch.

---

## Test Cases

### TC-XC-02-01: Audit entries are append-only (no UPDATE/DELETE allowed)

**Given:** An audit entry has been persisted in audit_log.

**When:** An attempt is made to UPDATE or DELETE the row.

**Then:**
- The UPDATE/DELETE is rejected by a database trigger or constraint
- The audit entry remains unchanged
- No error is silently swallowed

**Acceptance:**
- Direct SQL UPDATE on audit_log fails with a constraint violation
- Trigger `trg_audit_entries_no_update` enforces immutability
- Rows are permanently immutable after INSERT

**Layer:** integration  
**Fixtures:**
- One persisted audit entry

---

### TC-XC-02-02: Chain hash is deterministically computed

**Given:** An audit entry with canonical fields: actor_id, action, resource_type, resource_id, timestamp, before_state, after_state, trace_id.

**When:** The chain hash is computed for this entry twice (independently).

**Then:**
- Both computations produce the same 64-character hex string (SHA-256)
- The hash is stable across re-runs
- Reordering JSON fields in before_state or after_state does not change the hash (canonical form)

**Acceptance:**
- `bpm_audit_compute_chain_hash()` produces identical output for semantically equal inputs
- Hash is exactly 64 lowercase hex characters

**Layer:** integration  
**Fixtures:**
- Known audit payload values

---

### TC-XC-02-03: Each new entry links to its predecessor

**Given:** N audit entries have been persisted (N ≥ 2) for the same tenant in sequence.

**When:** Rows are queried in insertion order.

**Then:**
- Entry 1: `prev_chain_hash = NULL` (boundary entry)
- Entry 2: `prev_chain_hash = chain_hash of Entry 1`
- Entry 3: `prev_chain_hash = chain_hash of Entry 2`
- Entry N: `prev_chain_hash = chain_hash of Entry N-1`

**Acceptance:**
- Each entry's `prev_chain_hash` matches its predecessor's `chain_hash`
- Boundary entry (first in tenant) has `prev_chain_hash = NULL`

**Layer:** integration  
**Fixtures:**
- 5 audit entries appended sequentially to same tenant

---

### TC-XC-02-04: Per-tenant chains do not cross-reference

**Given:** Two different tenants, each with 3 audit entries.

**When:** Chains for both tenants are examined.

**Then:**
- Tenant A's entries reference only other Tenant A entries (or NULL for boundary)
- Tenant B's entries reference only other Tenant B entries (or NULL for boundary)
- Entries from Tenant A do not link to entries from Tenant B

**Acceptance:**
- Tenant scoping is enforced in chain linkage
- Querying audit entries for one tenant and validating the chain does not involve entries from other tenants

**Layer:** integration  
**Fixtures:**
- 2 tenants, each with 3 audit entries

---

### TC-XC-02-05: Tampering detection — modified entry breaks chain

**Given:** A chain of 5 audit entries in the database.

**When:** An attacker (via direct SQL) modifies entry #3's `after_state` field.

**Then:**
- Running chain validation on this tenant detects a mismatch at entry #3
- Entry #3's computed hash no longer matches its stored `chain_hash`
- All entries after #3 are marked as suspect (descendants of the tampered entry)
- The validation report identifies entry #3 as the first tampered entry

**Acceptance:**
- `bpm_audit_validate_chain()` returns a report listing:
  - `tampered_entries`: [entry #3]
  - `suspect_entries`: [entries #4, #5]
  - `first_mismatch_at`: entry #3

**Layer:** integration  
**Fixtures:**
- 5 audit entries with established chain hashes
- Method to bypass audit immutability trigger for testing (restore normal trigger afterward)

---

### TC-XC-02-06: Legacy (pre-migration) entries coexist with chained entries

**Given:** The audit_log table has:
- Entry 1 (legacy): `chain_hash = NULL`, `prev_chain_hash = NULL`, no trigger applied
- Entry 2 (post-migration): `chain_hash = <hash>`, `prev_chain_hash = NULL`
- Entry 3 (post-migration): `chain_hash = <hash>`, `prev_chain_hash = chain_hash of Entry 2`

**When:** Chain validation is run.

**Then:**
- Legacy entries (Entry 1) are accepted as pre-chain history
- Chain validation begins at Entry 2 (first non-null chain_hash)
- Entry 2 is treated as a boundary entry (prev_chain_hash = NULL)
- Entries 2 and 3 form a valid sub-chain

**Acceptance:**
- Validation report indicates legacy entries and post-migration chains are compatible
- No false-positive tampering detected across legacy/migration boundary

**Layer:** integration  
**Fixtures:**
- Mixed legacy and chained entries in test tenant

---

### TC-XC-02-07: Chain hash incorporates all audit fields

**Given:** Two otherwise identical audit entries with different trace_id values.

**When:** Chain hashes are computed.

**Then:**
- The two entries produce different chain hashes
- Changing any single field (actor_id, timestamp, trace_id, etc.) produces a different hash

**Acceptance:**
- All audit fields participate in hash computation
- Single-bit changes result in completely different hashes (SHA-256 avalanche effect)

**Layer:** integration  
**Fixtures:**
- Two audit entries differing only in trace_id or another field

---

### TC-XC-02-08: Chain validation is computationally efficient

**Given:** 10,000 audit entries in a chain for a single tenant.

**When:** `bpm_audit_validate_chain()` is called for that tenant.

**Then:**
- Validation completes in reasonable time (< 2 seconds)
- Database does not exhaust memory or resources
- Query uses efficient index (`idx_audit_entries_tenant_chain_lookup`)

**Acceptance:**
- Validation time is sub-second for typical chain sizes
- Performance scales linearly or better with chain length

**Layer:** integration  
**Fixtures:**
- Large chain (5,000–10,000 entries)
