# Test Spec: ISS-101 — Allow `FAILED` in `timers.status` CHECK constraint

**Requirement:** ISS-101 — The platform SHALL allow `timers.status` to be set to `FAILED`. Migration 081 replaces the existing CHECK constraint `(pending, fired, cancelled)` with `(pending, fired, cancelled, failed)`. The migration MUST be idempotent and apply cleanly to every existing tenant schema.  
**Priority:** MUST  
**Test layer:** integration

---

## Acceptance Criteria (verbatim from requirement)

1. New migration alters `timers.status` CHECK to include `'FAILED'`.
2. Migration is idempotent and applies cleanly to every existing tenant schema.
3. Updating a timer to `FAILED` (lowercase `'failed'`) succeeds; the row reflects the new status.
4. Updating a timer to `FAILED` (uppercase `'FAILED'`) also succeeds — the CHECK uses `lower()`.
5. Pre-existing valid status values (`pending`, `fired`, `cancelled`) still pass the constraint after migration.
6. An invalid status value (e.g. `'BOGUS'`) is rejected by the CHECK constraint with a PG error 23514.

---

## Test Cases

### TC-ISS-101-01: Update timer status to lowercase `failed` succeeds

**Given:** A tenant schema with migration 081 applied; an `instance_projections` row and a `timers` row with `status = 'pending'`.  
**When:** `UPDATE timers SET status = 'failed' WHERE id = $timer_id`.  
**Then:**
- The UPDATE completes without error.
- `SELECT status FROM timers WHERE id = $timer_id` returns `'failed'`.

**Layer:** integration  
**Acceptance criterion mapped:** AC-1, AC-3  
**Implemented by:** `tests/integration/iss101_timers_failed_status_test.zig` — test `iss101_timers_failed_status: update_timer_to_failed_succeeds`

---

### TC-ISS-101-02: Update timer status to uppercase `FAILED` succeeds (CHECK uses `lower()`)

**Given:** A tenant schema with migration 081 applied; an `instance_projections` row and a `timers` row with `status = 'pending'`.  
**When:** `UPDATE timers SET status = 'FAILED' WHERE id = $timer_id`.  
**Then:**
- The UPDATE completes without error.
- `SELECT status FROM timers WHERE id = $timer_id` returns `'FAILED'` (stored as-is; CHECK normalises with `lower()` for evaluation only).

**Layer:** integration  
**Acceptance criterion mapped:** AC-4  
**Implemented by:** `tests/integration/iss101_timers_failed_status_test.zig` — test `iss101_timers_failed_status: update_timer_to_failed_uppercase_succeeds`

---

### TC-ISS-101-03: Invalid status `BOGUS` is rejected by CHECK constraint

**Given:** A tenant schema with migration 081 applied; an `instance_projections` row and a `timers` row with `status = 'pending'`.  
**When:** `UPDATE timers SET status = 'BOGUS' WHERE id = $timer_id` is issued inside a SAVEPOINT.  
**Then:**
- The UPDATE fails with PG `error.ServerError` (constraint violation 23514).
- After `ROLLBACK TO SAVEPOINT`, the timer row still has `status = 'pending'`.

**Layer:** integration  
**Acceptance criterion mapped:** AC-6  
**Implemented by:** `tests/integration/iss101_timers_failed_status_test.zig` — test `iss101_timers_failed_status: invalid_status_still_rejected`

---

### TC-ISS-101-04: Pre-existing status values (`pending`, `fired`, `cancelled`) remain valid after migration

**Given:** A tenant schema with migration 081 applied.  
**When:** Three timer rows are inserted with `status = 'pending'`, `status = 'fired'`, and `status = 'cancelled'` respectively.  
**Then:**
- All three inserts succeed without error.
- Querying by the three timer IDs returns exactly three rows with statuses `cancelled`, `fired`, `pending` (alphabetical order).

**Layer:** integration  
**Acceptance criterion mapped:** AC-5  
**Implemented by:** `tests/integration/iss101_timers_failed_status_test.zig` — test `iss101_timers_failed_status: existing_statuses_remain_valid`

## Coverage Gap: DLQ Entry Creation

**Note (MINOR):** The ISS-101 test plan in the backlog doc specifies: _"assert DLQ entry (`dead_letter_items` row with `source_type=TIMER`) created."_ This DLQ assertion is NOT covered by the integration test written in this batch.

Rationale: DLQ entry creation on exhausted retries is the responsibility of ISS-303 (`src/scheduler/scheduler.zig`), which depends on ISS-101. The migration constraint fix (ISS-101) and the scheduler-side routing to FAILED + DLQ (ISS-303) are separate issues with a declared dependency. The DLQ path cannot be exercised until the scheduler code in ISS-303 is implemented.

The current test suite fully covers the schema constraint change (the acceptance criteria of ISS-101 itself). DLQ coverage will be included in the ISS-303 test spec and integration test.

## Notes

- All tests connect to real PostgreSQL via `BPM_TEST_DB_URL` (DIRECTIVE T-1). If `BPM_TEST_DB_URL` is unset, `helpers.TestHarness.init()` returns an error and tests are skipped with a clear message.
- Each test block uses its own distinct per-test UUIDs to prevent inter-test interference.
- Fixture rows (`instance_projections`, `timers`) are inserted inside the `TestHarness` transaction, which is rolled back on `h.deinit()`, so no persistent state is left in the database.

- This requirement is a pure schema/migration change with no UI interaction. No pipeline test step is needed.
