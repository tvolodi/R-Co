### TC-SBX-01-04: Both agent realm roles → conflicting_agent_roles absent from audit (SEC-MINOR-01 known-gap doc test)

**Context (SEC-MINOR-01):** `conflicting_agent_roles` is enforced by
`authenticate()` before any handler is invoked. The handler and audit code
are therefore unreachable in this path. This test documents the known gap:
no `TaskSpecSubmissionRejected` audit entry is written for the
`conflicting_agent_roles` rejection. The handler itself would succeed if
somehow reached with both roles present and a valid scope.

**Preconditions:** Auth context built with both
`agent_realm_roles = [.tenant_orchestrator, .tenant_implementer]` and
full scope. Call handler directly (simulates what would happen if the
middleware conflict check were bypassed — documents that the handler
itself does not write a rejection audit in this scenario).

**Steps:**
1. Record current audit count for this user_id / tenant.
2. Call `handleSubmitTaskSpec` directly with both roles + scope.
3. Query `audit_entries` for `conflicting_agent_roles` events for this actor.

**Expected:**
- No `audit_entries` row with event_name containing `conflicting_agent_roles`
  exists for this actor (the handler does not produce such an entry)
- Handler returns HTTP 201 (it reaches the task-spec path because the
  conflict check is absent from `requireOrchestratorSubmit`)
- Known gap documented: the reject + audit entry for conflicting roles
  must be covered by auth middleware tests, not by this handler test

## SBX-02 Test cases

### TC-SBX-02-01: No orchestrator_principal in body → server sets token subject

**Preconditions:** Valid orchestrator AuthContext with `user_id = "orch-a-<uuid>"`.
Body has no `orchestrator_principal` key.

**Steps:** Call `handleSubmitTaskSpec`.

**Expected:**
- HTTP 201
- `task_specs` row has `orchestrator_principal = "orch-a-<uuid>"`

---

### TC-SBX-02-02: orchestrator_principal in body is silently discarded

**Preconditions:** Same AuthContext (`user_id = "orch-a-<uuid>"`).
Body contains `"orchestrator_principal": "orch-b-bogus"`.

**Steps:** Call `handleSubmitTaskSpec`.

**Expected:**
- HTTP 201 (no error returned for the discarded field)
- `task_specs` row has `orchestrator_principal = "orch-a-<uuid>"` (not orch-b-bogus)

---

### TC-SBX-02-03: Two orchestrators same body → different spec_hash values

**Preconditions:** Two different AuthContexts (`user_id = "orch-a"` and `"orch-b"`).
Both submit the same body (same `rng_seed`, same payload).

**Steps:** Call `handleSubmitTaskSpec` twice (once per auth).

**Expected:**
- Both return HTTP 201
- The two `spec_hash` values differ (different principals produce different canonical forms)
- Two rows exist in `task_specs`

---

### TC-SBX-02-05: Body carries orch-b; spec_hash is computed over token orch-a

**Preconditions:** AuthContext with `user_id = orch-a`. Body contains
`"orchestrator_principal": "orch-b"`.

**Steps:**
1. Call `handleSubmitTaskSpec` with body naming orch-b. Record returned `spec_hash`
   as `hash_a` and `task_spec_id` as `id_a`.
2. Query `task_specs` for `orchestrator_principal` of `id_a`.
3. Call `handleSubmitTaskSpec` as orch-b with the same body (no orchestrator_principal
   override). Record returned `spec_hash` as `hash_b`.

**Expected:**
- Both submissions return HTTP 201
- `task_specs` row for `id_a` has `orchestrator_principal = orch-a` (not orch-b)
- `hash_a != hash_b` — proves `hash_a` was computed over orch-a
- A client that pre-computed its hash over orch-b would receive HTTP 409
  `spec_hash_mismatch` on artifact submission (covered by AGT-03 tests)

---

### TC-SBX-02-04: TaskSpecSubmitted audit entry has correct principal

**Preconditions:** Valid orchestrator auth with known `user_id`.

**Steps:**
1. Call `handleSubmitTaskSpec`.
2. Query `audit_entries` for `task_spec.submitted` event.

**Expected:**
- An `audit_entries` row exists with `event_name = 'task_spec.submitted'`
  and `actor_id = auth.user_id`
