# Test Spec: REPO-01–13 — Platform Repository Module

**Requirements:** REPO-01 through REPO-13 (all MUST)  
**Priority:** MUST  
**Test layer:** integration

---

## Overview

This test spec covers the entire Platform Repository module (Stage 10):

- **REPO-01 (Content addressing):** Artifacts deduplicate by SHA-256 hash of canonical content.
- **REPO-02 (Immutability):** Artifacts cannot be updated; changes produce new versions.
- **REPO-03 (Versioning):** Multiple versions per artifact with parent linkage and chronological ordering.
- **REPO-04 (Canonical serialisation):** JSON canonicalisation ensures content equality regardless of whitespace/key order.
- **REPO-05 (Form schema indexing):** Form schemas indexed by field type for agent queries.
- **REPO-06 (Event type registry):** Event types registered with producing definitions.
- **REPO-07 (Service catalog):** Services registered with endpoint, auth, request/response schemas.
- **REPO-08 (Atomic activation):** All artifacts in an activation group activate together in one transaction.
- **REPO-09 (Per-tenant activation):** Activations scoped per tenant; independent per-tenant versions.
- **REPO-10 (Activation history):** Complete audit trail of all activations with timestamp, activator, and rationale.
- **REPO-11 (Create artifact):** POST /repository/artifacts with roundtrip GET and deduplication.
- **REPO-12 (List versions):** GET /repository/{kind}/{name}/versions with pagination and parent linkage.
- **REPO-13 (Tenant activations):** GET /tenants/{id}/activations returns active versions per artifact per tenant.

All tests use real PostgreSQL via `BPM_TEST_DB_URL`. Every test creates per-test UUIDs for tenant, user, and artifact IDs. All tests clean up via transaction rollback in TestHarness.deinit().

---

## Test Isolation & Cleanup Strategy

1. **Per-test fixture generation:**
   - Each test generates unique UUIDs for tenant_id, user_id, artifact IDs using `std.crypto.random`.
   - No hardcoded IDs; isolation is deterministic.

2. **Transaction rollback cleanup:**
   - Every test wraps in `TestHarness.init()` / `defer h.deinit()`.
   - TestHarness.deinit() always rolls back the transaction, leaving zero test data.
   - No manual DELETE statements required.

3. **BPM_TEST_DB_URL validation:**
   - All tests skip gracefully (with `error.SkipZigTest`) if `BPM_TEST_DB_URL` is not set.
   - Tests fail clearly with a logged error message.

---

## Database Dependencies

Required tables (created by migrations):

- `repository_artifacts` — content_hash PRIMARY KEY, immutability enforced
- `artifact_versions` — version tracking with parent_version_id linkage
- `artifact_activations` — current active version per (tenant_id, artifact_kind, artifact_name)
- `artifact_activation_history` — audit trail of all activations
- `form_schema_registry` — indexed form field metadata
- `event_type_registry_producers` — link between event types and producing definitions
- `service_catalog` — registered external services
- `event_type_registry` (ES-05) — base event type registry

All tables must be indexed per the repository.md design. Tests verify indexes exist via schema metadata queries.

## Test Cases

### TC-REPO-01-01: Content addressing — identical content deduplicates

**Given:** Two POST /repository/artifacts requests with identical JSON content.  
**When:** Both are appended to the test database.  
**Then:** Both return the same content_hash; the second has is_duplicate=true.  
**Layer:** integration  
**Acceptance criterion mapped:** REPO-01 deduplication guarantee.

**Test steps:**
1. Create a test artifact definition (JSON).
2. POST to /repository/artifacts with kind="definition", name="order_process", content=JSON, created_by=test_user.
3. Capture artifact_id, version_id, content_hash.
4. POST again with identical content, same kind, same name.
5. Verify response is_duplicate=true, version_number=2, same content_hash.

### TC-REPO-02-01: Immutability — attempt to update artifact fails

**Given:** An active artifact with a stored hash.  
**When:** An attempt to "update" the artifact (e.g., via a hypothetical PUT to artifact_id directly) is made.  
**Then:** The operation fails with ImmutableViolation.  
**Layer:** integration  
**Acceptance criterion mapped:** REPO-02 immutability enforcement.

**Test steps:**
1. Create artifact 1, capture artifact_id.
2. Query `repository_artifacts` for the artifact_id; verify immutability (content_hash is PRIMARY KEY, no UPDATE allowed).
3. Attempt to update via SQL (should fail); verify DB constraint violation is caught.

### TC-REPO-03-01: Versioning — list versions in chronological order with parent linkage

**Given:** Five artifact versions created sequentially, each with parent linkage.  
**When:** listVersions() is called for the artifact.  
**Then:** Versions are returned in chronological order (creation_at ASC) with parent_version_id populated correctly.  
**Layer:** integration  
**Acceptance criterion mapped:** REPO-03 parent linkage and REPO-12 list versions.

**Test steps:**
1. Create version 1: parent_version_id = NULL.
2. Create version 2: parent_version_id = v1.version_id.
3. Create version 3: parent_version_id = v2.version_id.
4. Create version 4: parent_version_id = v3.version_id.
5. Create version 5: parent_version_id = v4.version_id.
6. Call listVersions(kind="definition", name="order_process").
7. Verify order: [v1, v2, v3, v4, v5] (creation_at ascending).
8. Verify parent linkage: v2.parent=v1.id, v3.parent=v2.id, ..., v5.parent=v4.id.
9. Verify v1.parent_version_id is NULL.

### TC-REPO-03-02: Versioning — list versions supports pagination

**When:** listVersions() is called with limit=3.  
**Then:** Exactly 3 versions are returned; subsequent calls with cursor return the next batch.  
**Layer:** integration

### TC-REPO-04-01: Canonical serialisation — whitespace variance produces same hash

**Given:** Two JSON representations with identical content but different whitespace/key order.  
**When:** Both are canonicalised and hashed.  
**Then:** Both produce the same SHA-256 hash.  
**Layer:** integration  
**Acceptance criterion mapped:** REPO-04 deterministic canonicalisation.

**Test steps:**
1. content_1 = `{"name":"order","version":1}` (compact).
2. content_2 = `{\n  "version": 1,\n  "name": "order"\n}` (indented, keys reordered).
3. Canonicalise both.
4. Hash both.
5. Verify hash[0] == hash[1].
6. Create artifact with content_1, capture artifact_id.
7. Create artifact with content_2, verify is_duplicate=true, same artifact_id.

---

### TC-REPO-04-02: Canonical serialisation — number normalisation

**Given:** JSON with different number representations (integer vs. float, exponent notation).  
**When:** Canonicalised.  
**Then:** Numbers are normalised: `1.0` → `1`, `1e0` → `1`, etc.  
**Layer:** integration  
**Acceptance criterion mapped:** REPO-04 number form normalization.

**Test steps:**
1. content_1 = `{"amount":100}` (integer).
2. content_2 = `{"amount":100.0}` (float).
3. content_3 = `{"amount":1e2}` (exponent).
4. Verify all three produce the same canonical form and hash.
5. Verify is_duplicate=true for versions 2 and 3 when artifact 1 already exists.

### TC-REPO-09-01: Per-tenant activation — activations are tenant-scoped
