# Test Spec: XC-03 — Configuration in Repository

**Requirement:** XC-03 — Platform configuration (capability defaults, tier selections, budget limits, monitoring thresholds) is stored as versioned artifacts in the repository and activated like any other artifact.  
**Priority:** MUST  
**Test layer:** integration

---

## Overview

Configuration artifacts are stored in the repository with the same versioning, immutability, and audit trail as process definitions. Configuration can be:
- Uploaded as a new artifact version via `POST /repository/artifacts`
- Activated per-tenant via `POST /tenants/{tenant_id}/activate`
- Read on-demand at runtime via configuration loader
- Queried per-tenant to determine active configuration version

Configuration categories include:
- `capabilities`: node timeout settings
- `tier_rules`: LLM model selection rules
- `budget_limits`: token/call limits
- `monitoring_config`: alerting thresholds
- `oidc_config`: identity provider configuration

---

## Test Cases

### TC-XC-03-01: Configuration artifact can be uploaded and versioned

**Given:** A valid JSON configuration object (e.g., `monitoring_config` with alerting thresholds).

**When:** Configuration is uploaded via `POST /repository/artifacts` with kind="config".

**Then:**
- Response status is 201 Created
- Response includes `version_id` (UUID)
- Configuration is stored in repository_artifacts (same as process definitions)
- Artifact is immutable after creation
- Content hash is computed and stored per REPO-02

**Acceptance:**
- `GET /repository/artifacts/{version_id}` returns the exact configuration JSON
- Configuration version can be listed alongside definition versions
- Multiple versions of the same configuration can coexist

**Layer:** integration  
**Fixtures:** None

---

### TC-XC-03-02: Configuration schema is validated on upload

**Given:** A malformed JSON configuration (e.g., missing required fields for `monitoring_config`).

**When:** Configuration is uploaded.

**Then:**
- Response status is 422 Unprocessable Entity
- Error body (RFC 9457 Problem Details) lists validation failures
- Configuration is NOT stored in repository

**Acceptance:**
- Schema validation enforces presence of expected fields
- Schema validation accepts unknown fields (forward compatibility)
- All validation errors are reported in a single response

**Layer:** integration  
**Fixtures:**
- Sample invalid configuration artifacts

---

### TC-XC-03-03: Configuration is activated per-tenant atomically

**Given:** A configuration artifact version ID and a tenant.

**When:** Configuration is activated via `POST /tenants/{tenant_id}/activate` with target_version_id.

**Then:**
- Response status is 200 OK
- The configuration is atomically marked as active for this tenant
- Previous active configuration version (if any) is replaced
- Activation is recorded in audit_log with action="configuration.activate"
- No partial state is visible

**Acceptance:**
- Querying active configuration for this tenant returns the newly activated version
- Audit entry for activation is present
- Activating a different version atomically replaces the previous one

**Layer:** integration  
**Fixtures:**
- Two configuration versions of the same kind (e.g., two `monitoring_config` versions)

---

### TC-XC-03-04: Different tenants can have different active configurations

**Given:** Two tenants (Tenant A and Tenant B) and two configuration versions (V1 and V2).

**When:** Tenant A activates V1 and Tenant B activates V2.

**Then:**
- Each tenant sees only its own active configuration
- Configuration change in Tenant A does not affect Tenant B
- Querying active configuration for Tenant A returns V1
- Querying active configuration for Tenant B returns V2

**Acceptance:**
- Tenant-scoped configuration isolation is enforced
- No cross-tenant leakage

**Layer:** integration  
**Fixtures:**
- 2 tenants
- 2 configuration versions

---

### TC-XC-03-05: Configuration is read on-demand at runtime

**Given:** An active configuration version for a tenant.

**When:** A module calls `loadActiveConfig(tenant_id, pool)` at runtime.

**Then:**
- The active configuration is fetched from repository_artifacts
- Configuration is parsed and validated (schema check)
- Returned configuration object is usable immediately
- Reading configuration does NOT require platform restart

**Acceptance:**
- Configuration can be changed and read dynamically without restart
- Multiple consecutive reads return consistent configuration
- Error handling for missing or invalid configuration is graceful

**Layer:** integration  
**Fixtures:**
- Active configuration artifact

---

### TC-XC-03-06: Missing or inactive configuration fails gracefully

**Given:** A tenant with no active configuration version.

**When:** A module calls `loadActiveConfig(tenant_id, pool)`.

**Then:**
- Function returns a default/fallback configuration with sensible defaults
- OR function returns an error if configuration is mandatory
- No NULL pointer dereference or panic occurs

**Acceptance:**
- Missing configuration does not crash the platform
- Behavior is explicit (documented in error or default handling)

**Layer:** integration  
**Fixtures:**
- Tenant with no active configuration

---

### TC-XC-03-07: Configuration artifact immutability is enforced

**Given:** A configuration version has been activated.

**When:** An attempt is made to modify the artifact content (via direct SQL or API).

**Then:**
- Modification is rejected
- Artifact remains unchanged
- To change configuration, a new version must be created and activated

**Acceptance:**
- Configuration immutability matches definition immutability (REPO-02)
- New version creation is the only way to update configuration

**Layer:** integration  
**Fixtures:**
- Activated configuration artifact

---

### TC-XC-03-08: Configuration artifact activation is audited

**Given:** A configuration activation operation.

**When:** Configuration is activated for a tenant.

**Then:**
- An audit entry is recorded with:
  - `action = "configuration.activate"`
  - `resource_type = "configuration"`
  - `resource_id = <tenant_id>`
  - `after_state` = activated configuration version details
  - `trace_id` from current request
- Audit entry is chained (XC-02) if applicable

**Acceptance:**
- Configuration changes are fully audited
- Audit trail shows who activated which configuration version and when
- Audit entry follows XC-01 (trace ID) and XC-02 (chain) requirements

**Layer:** integration  
**Fixtures:**
- Configuration activation operation with known trace_id

---

### TC-XC-03-09: Configuration artifact follows repository artifact versioning (REPO-03)

**Given:** A configuration artifact and its parent version.

**When:** A new version of the same configuration is created.

**Then:**
- The new version includes a `parent_version_id` linking to the previous version
- Artifact content hash is unique per version (REPO-02)
- Artifact kind, name, and parent form a version chain

**Acceptance:**
- Version history can be traversed backwards from any version
- Each version is uniquely identified by content hash
- No duplicate versions exist (content hash uniqueness)

**Layer:** integration  
**Fixtures:**
- Two sequential versions of the same configuration
