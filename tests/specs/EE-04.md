# Test Spec: EE-04 — Complete task

**Requirement:** EE-04 — An authorised caller SHALL complete an active task by submitting an output variables map. The engine evaluates outgoing edge conditions, activates the next node(s), and records a `TASK_COMPLETED` event.  
**Priority:** MUST  
**Test layer:** unit, integration

## Test Cases

| Test Case ID | Acceptance Criterion | Description |
|--------------|---------------------|-------------|
| TC-EE-04-01 | PENDING task + non-empty output_variables → HTTP 200, full side-effects committed | POST /tasks/:id/complete with a PENDING task and a non-empty output_variables map succeeds: HTTP 200, task COMPLETED, variables merged, next node activated, TASK_COMPLETED event appended — all in one transaction. |
| TC-EE-04-02 | Empty output_variables `{}` is valid | POST /tasks/:id/complete with `output_variables = {}` returns HTTP 200 (no output is acceptable). |
| TC-EE-04-03 | Completing a task that leads to an END node transitions instance to COMPLETED | When the only outgoing edge from the completed task leads to an END node, the instance status becomes COMPLETED. |
| TC-EE-04-04 | Non-existent task_id → HTTP 404, error = TASK_NOT_FOUND | POST /tasks/:id/complete where task_id does not match any row returns HTTP 404 with `TASK_NOT_FOUND`. |
| TC-EE-04-05 | Already-COMPLETED task → HTTP 409, error = TASK_ALREADY_TERMINATED | POST /tasks/:id/complete where the task status is already COMPLETED returns HTTP 409 with `TASK_ALREADY_TERMINATED`. |
| TC-EE-04-06 | CANCELLED task → HTTP 409, error = TASK_ALREADY_TERMINATED | POST /tasks/:id/complete where the task status is CANCELLED returns HTTP 409 with `TASK_ALREADY_TERMINATED`. |
| TC-EE-04-07 | `output_variables = null` → HTTP 422, error = INVALID_INPUT | POST /tasks/:id/complete with a JSON body where `output_variables` is null returns HTTP 422 with `INVALID_INPUT`. |
| TC-EE-04-08 | Malformed task_id (not a UUID) → HTTP 422 | POST /tasks/:id/complete where `:id` is not a valid UUID returns HTTP 422. |
| TC-EE-04-09 | DB failure mid-transaction → full rollback, no partial state | Simulated DB failure after `completeInTx` but before COMMIT leaves the task PENDING, no TASK_COMPLETED event in the event log, and instance state unchanged. |

### TC-EE-04-01: Complete PENDING task with non-empty output_variables — all side-effects committed atomically

**Preconditions:**
- A process definition exists with the shape: START → HUMAN_TASK(`node_A`) → HUMAN_TASK(`node_B`).
- A process instance is running with a PENDING task `T1` on `node_A` (`task_id = T1`).
- `instance_projections` shows `current_nodes = ["node_A"]`, `variables = {}`, `status = ACTIVE`.

**Steps:**
1. POST `/api/v1/tasks/{T1}/complete` with body `{ "output_variables": { "approved": true } }`.

**Expected result:**
- HTTP 200; response body: `{ "status": "ok", "task_id": "<T1>" }`.
- `tasks` row for `T1`: `status = COMPLETED`, `output_variables = {"approved": true}`, `completed_at` is non-null.
- `events` table: one new row with `event_type = TASK_COMPLETED` referencing `T1` and the instance.
- `instance_projections`: `current_nodes` includes `node_B`, `variables = {"approved": true}`, `status = ACTIVE`.
- A new `tasks` row for `node_B` exists with `status = PENDING`.
- All of the above changes are visible in a single subsequent read (committed atomically).

**Layer:** integration  
**Acceptance criterion mapped:** GIVEN an authorised caller submits `POST /tasks/:id/complete` with an `output_variables` JSON object, WHEN the task is PENDING, THEN the platform merges output variables, evaluates outgoing edge conditions, activates the next node(s), appends a `TASK_COMPLETED` event, and returns HTTP 200. Task status change, variable merge, state transition, and `TASK_COMPLETED` event MUST all commit in a single transaction.

### TC-EE-04-02: Complete PENDING task with empty output_variables — HTTP 200

**Preconditions:**
- A process instance is running with a PENDING task `T2` on a HUMAN_TASK node with one outgoing edge to another HUMAN_TASK node.

**Steps:**
1. POST `/api/v1/tasks/{T2}/complete` with body `{ "output_variables": {} }`.

**Expected result:**
- HTTP 200; response body: `{ "status": "ok", "task_id": "<T2>" }`.
- `tasks` row for `T2`: `status = COMPLETED`, `output_variables = {}`.
- No error is returned; an empty output variables object is treated as valid.

**Layer:** integration  
**Acceptance criterion mapped:** `output_variables` may be an empty object `{}`; this is valid (task completed with no output).

### TC-EE-04-03: Completing a task whose next node is END transitions instance to COMPLETED

**Preconditions:**
- A process definition with the shape: START → HUMAN_TASK(`node_final`) → END.
- A process instance is running with a PENDING task `T3` on `node_final`.
- `instance_projections`: `status = ACTIVE`, `current_nodes = ["node_final"]`.

**Steps:**
1. POST `/api/v1/tasks/{T3}/complete` with body `{ "output_variables": {} }`.

**Expected result:**
- HTTP 200; response body: `{ "status": "ok", "task_id": "<T3>" }`.
- `tasks` row for `T3`: `status = COMPLETED`.
- `instance_projections`: `status = COMPLETED`, `current_nodes = []` (or the END node, per implementation).
- No new PENDING task row is created (END node does not produce a task).
- `TASK_COMPLETED` event appended to `events`.

**Layer:** integration  
**Acceptance criterion mapped:** GIVEN the next node is an END node, THEN instance status transitions to COMPLETED. (Derived from EE-04 AC1 + EE-03 requirement that END nodes do not create Task records.)

### TC-EE-04-04: Non-existent task_id → HTTP 404, TASK_NOT_FOUND

**Preconditions:**
- No task row exists for UUID `00000000-0000-0000-0000-000000000099`.

**Steps:**
1. POST `/api/v1/tasks/00000000-0000-0000-0000-000000000099/complete` with body `{ "output_variables": {} }`.

**Expected result:**
- HTTP 404.
- Response body contains `"error": "TASK_NOT_FOUND"`.
- No rows are inserted or updated in `tasks`, `events`, or `instance_projections`.

**Layer:** integration  
**Acceptance criterion mapped:** GIVEN the task does not exist, THEN HTTP 404 is returned.

### TC-EE-04-05: Already-COMPLETED task → HTTP 409, TASK_ALREADY_TERMINATED

**Preconditions:**
- Task `T5` exists with `status = COMPLETED`.

**Steps:**
1. POST `/api/v1/tasks/{T5}/complete` with body `{ "output_variables": {} }`.

**Expected result:**
- HTTP 409.
- Response body contains `"error": "TASK_ALREADY_TERMINATED"`.
- No additional rows are inserted in `events`; the task row is not modified.

**Layer:** integration  
**Acceptance criterion mapped:** GIVEN the task has status ≠ PENDING (already COMPLETED or CANCELLED), THEN HTTP 409 is returned.

### TC-EE-04-07: output_variables = null → HTTP 422, INVALID_INPUT

**Preconditions:**
- Task `T7` exists with `status = PENDING`.

**Steps:**
1. POST `/api/v1/tasks/{T7}/complete` with body `{ "output_variables": null }`.

**Expected result:**

### TC-EE-04-08: Malformed task_id (not a UUID) → HTTP 422

**Preconditions:**
- None (no DB state required).

**Steps:**
1. POST `/api/v1/tasks/not-a-uuid/complete` with body `{ "output_variables": {} }`.

**Expected result:**
- HTTP 422.
- Response body contains an error indicating the task ID is not a valid UUID (e.g. `"error": "INVALID_INPUT"`).
- No DB reads or writes are performed.

**Layer:** integration  
**Acceptance criterion mapped:** Edge case — malformed path parameter is rejected before any DB access. (Derived from EE-04 handler design: `parseUuid` returns 422 on invalid input.)

### TC-EE-04-09: DB failure mid-transaction → full rollback, no partial state

**Preconditions:**
- Task `T9` exists with `status = PENDING` on a HUMAN_TASK node with one outgoing edge.
- A fault injection mechanism is configured to fail after `completeInTx` succeeds (task row updated to COMPLETED) but before the `TASK_COMPLETED` event INSERT commits (step j in `InstanceStore.completeTask`).

**Steps:**
1. Inject a DB failure that will trigger on the event INSERT inside the open transaction.
2. POST `/api/v1/tasks/{T9}/complete` with body `{ "output_variables": {} }`.

**Expected result:**
- The HTTP response is an error (HTTP 500 or 503).
- `tasks` row for `T9`: `status = PENDING` (the UPDATE from `completeInTx` was rolled back).
- `events` table: no `TASK_COMPLETED` event row for `T9`.
- `instance_projections`: `current_nodes` and `variables` are unchanged from before the request.
- The `errdefer conn.rollback()` in `InstanceStore.completeTask` ensures all in-transaction writes are undone atomically.

**Layer:** integration (requires test-double or fault-injection harness for DB connection)  
**Acceptance criterion mapped:** The task status change, variable merge, state transition, and `TASK_COMPLETED` event MUST all commit in a single transaction. (Atomicity invariant: if any step in h–m fails, ROLLBACK is issued and the caller observes no change at all.)
