## Test Cases

### TC1: event committed → webhook_deliveries row in same tx

**Precondition:**
1. Create an active webhook subscription for event type `task.completed`.
2. Begin a DB transaction.

**Action:**
- Inside the transaction: call `insertWebhookDeliveriesInTx(conn, event_type, ...)`.
- COMMIT the transaction.

**Expected:**
- `webhook_deliveries` table contains exactly one row for the subscription.
- Row has `status='pending'`, `attempt_count=0`.
- `next_attempt_at > NOW()` (approximately NOW + 5s).

**Also verify (rollback path):**
- If the transaction is rolled back AFTER `insertWebhookDeliveriesInTx` but before commit,
  no rows appear in `webhook_deliveries`.

---

### TC2: orphan survival — delivery created, no dispatch before "restart" → swept on next call

**Precondition:**
1. Create subscription and insert a `webhook_deliveries` row manually with
   `status='pending'`, `next_attempt_at=NOW()-1s` (already due).

**Action:** Call `sweepOrphanedDeliveries(pool)`.

**Expected:**
- The delivery row is processed (attempt made, status updated to 'success', 'failed', or 'exhausted').
- Demonstrates that the sweep drains rows regardless of how they got there.

---

### TC3: 5 failures → subscription paused

**Precondition:**
1. Create an active webhook subscription pointing to a URL that always returns 500.
2. Insert a `webhook_deliveries` row with `status='pending'`, `attempt_count=4`,
   `max_attempts=5`, `next_attempt_at=NOW()-1s`.

**Action:** Call `dispatchDueWebhookAttempts(pool)`.

**Expected:**
- Delivery row updated: `status='exhausted'`, `attempt_count=5`.
- Subscription updated: `status='PAUSED'`, `paused_at IS NOT NULL`.

## Test Infrastructure

- Real PostgreSQL via `BPM_TEST_DB_URL`.
- Per-test UUIDs for subscription_id, delivery_id.
- Each test block creates its own fixtures and cleans up via `defer`.
- No mocks or stubs.
- TC2/TC3 use a loopback HTTP server or simply verify DB state without actual HTTP delivery.
- If `BPM_TEST_DB_URL` is absent, all tests skip cleanly.
