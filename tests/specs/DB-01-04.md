# Test Spec: DB-01–DB-04 — Database Layer (Schema, Pool, Transactions, Health)

---

## DB-01 — Schema initialisation

**Requirement:** DB-01 — The platform SHALL include idempotent SQL migration scripts that create all required tables, indexes, and constraints on a fresh PostgreSQL 15+ database.  
**Priority:** MUST  
**Test layer:** integration, unit

### TC-DB-01-01: Fresh database migration applies all schemas

**Given:** A fresh PostgreSQL 15+ database with no application schema and the BPM migrations directory  
**When:** `Migrations.run()` is called with the migrations directory  
**Then:** `schema_migrations` contains one entry per `.sql` file in the directory; `zig build migrate` exits 0; all tables expected by the application exist in the database  
**Layer:** integration  
**Acceptance criterion mapped:** Fresh DB, all migrations applied in order, platform starts without error

### TC-DB-01-02: Re-applying migrations is idempotent

**Given:** A database where all migrations have already been applied  
**When:** `Migrations.run()` is called again with the same directory  
**Then:** `Migrations.run()` returns without error; the row count in `schema_migrations` is unchanged; no duplicate entries are inserted  
**Layer:** integration  
**Acceptance criterion mapped:** Re-applied migrations complete without error and leave schema unchanged

### TC-DB-01-03: Out-of-order migration returns OutOfOrderMigration

**Given:** A `schema_migrations` table that already contains version `"005_instances.sql"` but not `"004_definitions.sql"`  
**When:** `Migrations.run()` attempts to apply `"004_definitions.sql"`  
**Then:** `Migrations.run()` returns `MigrationError.OutOfOrderMigration`; no new migration is applied; `schema_migrations` is unchanged  
**Layer:** unit  
**Acceptance criterion mapped:** Applying migration N+1 before N fails with a clear error

### TC-DB-01-04: Failed migration SQL is fully rolled back

**Given:** A migration SQL file whose body contains a syntax error or invalid statement  
**When:** `Migrations.run()` executes that file  
**Then:** `Migrations.run()` returns `MigrationError.MigrationFailed`; the database is in the same state as before the migration was attempted (no partial schema change is observable); `schema_migrations` does not contain the failed version  
**Layer:** integration  
**Acceptance criterion mapped:** Mid-execution failure rolls back entire migration; DB left in pre-migration state

### TC-DB-01-05: PostgreSQL version below 15 returns UnsupportedPgVersion

**Given:** A pool whose cached `pg_version` is 140000 (PostgreSQL 14)  
**When:** `Migrations.run()` is called  
**Then:** `Migrations.run()` returns `MigrationError.UnsupportedPgVersion`; no SQL files are executed  
**Layer:** unit  
**Acceptance criterion mapped:** Platform MUST log fatal error and refuse to start on PostgreSQL < 15

## DB-02 — Connection pooling

**Requirement:** DB-02 — All database access SHALL go through a connection pool. Pool size MUST be configurable via environment variable, subject to bounds defined in NFR-06. An exhausted pool MUST return an error immediately, not block indefinitely.  
**Priority:** MUST  
**Test layer:** unit, integration

### TC-DB-02-01: Pool init with pool_size below lower bound returns InvalidPoolSize

**Given:** A `PoolConfig` with `pool_size = 1` and a valid `url`  
**When:** `Pool.init()` is called  
**Then:** `Pool.init()` returns `PoolError.InvalidPoolSize`; no connections are opened  
**Layer:** unit  
**Acceptance criterion mapped:** Pool size < 2 causes fatal startup error

### TC-DB-02-02: Pool init with pool_size above upper bound returns InvalidPoolSize

**Given:** A `PoolConfig` with `pool_size = 201` and a valid `url`  
**When:** `Pool.init()` is called  
**Then:** `Pool.init()` returns `PoolError.InvalidPoolSize`; no connections are opened  
**Layer:** unit  
**Acceptance criterion mapped:** Pool size > 200 causes fatal startup error (NFR-06)

### TC-DB-02-03: Fully exhausted pool returns ExhaustedPool; release restores availability

**Given:** A pool with `pool_size = 2` connected to the test database (`BPM_TEST_DB_URL`)  
**When:**
1. Both connections are acquired (pool is fully exhausted)
2. A third `pool.acquire()` call is made
3. One connection is released, then `pool.acquire()` is called again  

**Then:**
- The third `pool.acquire()` returns `PoolError.ExhaustedPool` immediately (no blocking, no retry)
- After releasing one connection, `pool.acquire()` succeeds and returns a valid `*Conn`  

**Layer:** integration  
**Acceptance criterion mapped:** Exhausted pool returns error immediately; connections return to idle pool correctly after release

### TC-DB-02-04: Pool.init with out-of-range pool_size returns InvalidPoolSize; boundary values succeed

**Given:** A `PoolConfig` with various `pool_size` values  
**When:** `Pool.init()` is called  
**Then:**
- `pool_size = 1` → returns `PoolError.InvalidPoolSize` (no network call made)
- `pool_size = 201` → returns `PoolError.InvalidPoolSize` (no network call made)
- `pool_size = 2` → succeeds; pool is created and connectable
- `pool_size = 200` → succeeds; pool is created and connectable  

**Layer:** integration  
**Acceptance criterion mapped:** Pool size < 2 or > 200 causes fatal startup error (NFR-06); boundary values 2 and 200 are accepted

## DB-03 — Transactional integrity

**Requirement:** DB-03 — Event append and any associated state-table update MUST occur within a single database transaction. Partial writes MUST NOT be observable.  
**Priority:** MUST  
**Test layer:** integration

### TC-DB-03-01: Successful transaction commits both event row and state update atomically

**Given:** A running database with a valid instance row in `instance_projections`  
**When:** `Store.append()` completes successfully  
**Then:** Both the `events` row and the `instance_projections.last_event_seq` update are visible in the same committed transaction; no reader can observe the event row without the state update  
**Layer:** integration  
**Acceptance criterion mapped:** Both writes committed — no partial write observable

### TC-DB-03-02: Failed state-table update causes full transaction rollback

**Given:** A running database where the state-table update is forced to fail (e.g. constraint violation injected)  
**When:** `Store.append()` encounters the failure  
**Then:** `Store.append()` returns `StoreError.TransactionFailed`; the `events` table contains no new row; `instance_projections` is unchanged  
**Layer:** integration  
**Acceptance criterion mapped:** State-table update failure rolls back event log row; neither write is committed

## DB-04 — Health check query

**Requirement:** DB-04 — The platform SHALL expose an internal function that verifies database reachability and returns latency, used by the health endpoint (see API-12).  
**Priority:** MUST  
**Test layer:** integration, unit

### TC-DB-04-01: Health check returns latency_ms on successful SELECT 1

**Given:** A pool with at least one idle connection and a reachable database  
**When:** `pool.healthCheck()` is called  
**Then:** `pool.healthCheck()` returns `HealthResult` with `latency_ms >= 0`; no data rows are inserted, updated, or deleted; the pool idle count is restored after the call  
**Layer:** integration  
**Acceptance criterion mapped:** DB reachable → success result with round-trip latency; read-only query

### TC-DB-04-02: Health check returns ExhaustedPool when all connections are in use

**Given:** A pool with `pool_size = 2` where both connections are acquired and not released  
**When:** `pool.healthCheck()` is called  
**Then:** `pool.healthCheck()` returns `PoolError.ExhaustedPool`; no new connection is opened  
**Layer:** unit  
**Acceptance criterion mapped:** Pool exhausted → health check reports failure; MUST NOT open a separate connection
