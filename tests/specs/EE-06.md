# Test Spec: EE-06 — Parallel Gateway (split)

**Requirement:** EE-06 — A PARALLEL_GATEWAY SHALL activate all outgoing edges simultaneously, creating concurrent execution tokens. Each token progresses independently.  
**Priority:** MUST  
**Test layer:** unit (AC1–AC3), integration (AC4 — DB-03 transaction)

---

## Acceptance Criteria

| ID | Criterion |
|---|---|
| AC1 | GIVEN a token reaches a PARALLEL_GATEWAY with N outgoing edges, WHEN evaluated, THEN N independent execution tokens are created simultaneously, one per outgoing edge. |
| AC2 | Each token progresses independently; task completions on one branch do not block other branches. |
| AC3 | The split event MUST be recorded in the event log (`PARALLEL_SPLIT` event appended to `InstanceState.pending_events`). |
| AC4 | All N tokens are created in a single transaction (DB-03): the pure `transition()` function returns all N tokens + the `PARALLEL_SPLIT` event together; the caller persists them atomically. |

---

## Test Case Summary

| Test Case ID | Layer | Acceptance Criterion | Description |
|---|---|---|---|
| TC-EE-06-01 | unit | AC1, AC3 | 2-way split: 2 tokens created and 1 PARALLEL_SPLIT event appended |
| TC-EE-06-02 | unit | AC1, token uniqueness | 3-way split: 3 tokens created with mutually distinct `branch_id` values |
| TC-EE-06-03 | unit | AC1 | Arriving token is removed: result has N (not N+1) tokens |
| TC-EE-06-04 | unit | AC1 | Each new token targets the correct next node per definition edges |

| TC-EE-06-06 | unit | AC1 (degenerate) | PARALLEL_GATEWAY with 1 outgoing edge acts as pass-through — no PARALLEL_SPLIT event |
| TC-EE-06-07 | unit | AC1, AC2 | Split where one branch immediately activates a HUMAN_TASK and the other hits a nested PARALLEL_GATEWAY |
| TC-EE-06-08 | integration | AC4 | Caller persists all N tokens and PARALLEL_SPLIT event in a single DB transaction (DB-03) |

## Detailed Test Cases

### TC-EE-06-01: 2-way parallel split creates 2 tokens and 1 PARALLEL_SPLIT event

**Source:** `src/engine/transition.zig` — `"TC-EE-06-01: PARALLEL_GATEWAY split with 2 edges creates 2 tokens and 1 PARALLEL_SPLIT event"`

**Given:**
- A `DefinitionGraph` with nodes: `PARALLEL_GATEWAY("gw")`, `HUMAN_TASK("t1")`, `HUMAN_TASK("t2")`.
- Edges: `e1` (gw → t1), `e2` (gw → t2).
- An `InstanceState` with one token on `"gw"`, `status = ACTIVE`, `pending_events = []`.

**When:**
- `processNodeEntry(allocator, graph, state, "gw")` is called.

**Then:**
- `result.tokens.len == 2`.
- `result.pending_events.len == 1`.
- `result.pending_events[0]` has active tag `.parallel_split`.

**Layer:** unit  
**Acceptance criterion mapped:** AC1 — N tokens created for N outgoing edges; AC3 — PARALLEL_SPLIT event appended.

### TC-EE-06-02: 3-way parallel split creates 3 tokens with unique branch_ids

**Source:** `src/engine/transition.zig` — `"TC-EE-06-02: PARALLEL_GATEWAY split with 3 edges creates 3 tokens with unique branch_ids"`

**Given:**
- A `DefinitionGraph` with nodes: `PARALLEL_GATEWAY("gw")`, `HUMAN_TASK("t1")`, `HUMAN_TASK("t2")`, `HUMAN_TASK("t3")`.
- Edges: `e1` (gw → t1), `e2` (gw → t2), `e3` (gw → t3).
- An `InstanceState` with one token on `"gw"`, `pending_events = []`.

**When:**
- `processNodeEntry(allocator, graph, state, "gw")` is called.

**Then:**
- `result.tokens.len == 3`.
- All three `branch_id` values are pairwise distinct:
  - `tokens[0].branch_id ≠ tokens[1].branch_id`
  - `tokens[0].branch_id ≠ tokens[2].branch_id`
  - `tokens[1].branch_id ≠ tokens[2].branch_id`

**Layer:** unit  
**Acceptance criterion mapped:** AC1 — N tokens for N edges; token uniqueness — all branch_ids are globally distinct within a split.

### TC-EE-06-03: Original arriving token removed after split — result has exactly N tokens (not N+1)

**Source:** `src/engine/transition.zig` — `"TC-EE-06-03: original arriving token removed after parallel split"`

**Given:**
- A `DefinitionGraph` with nodes: `PARALLEL_GATEWAY("gw")`, `HUMAN_TASK("t1")`, `HUMAN_TASK("t2")`.
- Edges: `e1` (gw → t1), `e2` (gw → t2).
- An `InstanceState` with exactly one token on `"gw"` (branch_id `"arriving"`), `pending_events = []`.

**When:**
- `processNodeEntry(allocator, graph, state, "gw")` is called.

**Then:**
- `result.tokens.len == 2` (not 3 — the gateway token is removed, not retained).
- No token in `result.tokens` has `node_id == "gw"`.

**Layer:** unit  
**Acceptance criterion mapped:** AC1 — arriving token is consumed and replaced by N new tokens; the total active token count does not grow by more than N−1.

### TC-EE-06-04: Each new token targets the correct next node per definition edges

**Source:** `src/engine/transition.zig` — `"TC-EE-06-04: each new token targets correct next node per definition edges"`

**Given:**
- A `DefinitionGraph` with nodes: `PARALLEL_GATEWAY("gw")`, `HUMAN_TASK("ta")`, `HUMAN_TASK("tb")`.
- Edges: `e1` (gw → ta), `e2` (gw → tb).
- An `InstanceState` with one token on `"gw"`, `pending_events = []`.

**When:**
- `processNodeEntry(allocator, graph, state, "gw")` is called.

**Then:**

- One token has `node_id == "ta"`.
- One token has `node_id == "tb"`.

**Layer:** unit  
**Acceptance criterion mapped:** AC1 — each new token is placed on the target node of its corresponding outgoing edge.

### TC-EE-06-05: PARALLEL_SPLIT event records correct metadata

**Source:** `src/engine/transition.zig` — `"TC-EE-06-05: PARALLEL_SPLIT event records correct source_node_id and edge_count"`

**Given:**
- A `DefinitionGraph` with nodes: `PARALLEL_GATEWAY("gw2")`, `HUMAN_TASK("n1")`, `HUMAN_TASK("n2")`.
- Edges: `e1` (gw2 → n1), `e2` (gw2 → n2).
- An `InstanceState` with one token on `"gw2"`, `pending_events = []`.

**When:**
- `processNodeEntry(allocator, graph, state, "gw2")` is called.

**Then:**
- `result.pending_events.len == 1`.
- `payload = result.pending_events[0].parallel_split` (active tag must be `.parallel_split`).
- `payload.source_node_id == "gw2"`.
- `payload.edge_count == 2`.
- `payload.token_ids.len == 2`.
- `payload.target_node_ids.len == 2`.
- For every token `t` in `result.tokens`, `t.branch_id` appears in `payload.token_ids`.

**Layer:** unit  
**Acceptance criterion mapped:** AC3 — PARALLEL_SPLIT event captures `source_node_id`, `token_ids` (branch_ids of all new tokens), `target_node_ids`, and `edge_count`.

### TC-EE-06-06: PARALLEL_GATEWAY with 1 outgoing edge (degenerate split) — pass-through, no PARALLEL_SPLIT event

**Given:**
- A `DefinitionGraph` with nodes: `PARALLEL_GATEWAY("gw")`, `HUMAN_TASK("next")`.
- Exactly one edge: `e1` (gw → next).
- An `InstanceState` with one token on `"gw"`, `pending_events = []`.

**When:**
- `processNodeEntry(allocator, graph, state, "gw")` is called.

**Then:**
- `result.tokens.len == 1`.
- The single token has `node_id == "next"`.
- `result.pending_events.len == 0` — no `PARALLEL_SPLIT` event is generated because the split condition `outgoing_count > 1` is not met.

**Notes:**
- Per design §OQ-EE06-2, a `PARALLEL_GATEWAY` with exactly 1 outgoing edge is treated as a pass-through, not a split. No `PARALLEL_SPLIT` event is appended.
- If PD-02 structural validation (`graph.zig`) rejects single-outgoing-edge `PARALLEL_GATEWAY` nodes at definition creation time, this test verifies that the runtime's fallback behaviour is safe for any gap in definition validation.

**Layer:** unit  
**Acceptance criterion mapped:** AC1 — token count is correct for N=1 edge; AC3 — no spurious `PARALLEL_SPLIT` event emitted for a non-split.

### TC-EE-06-07: Split where one branch activates a HUMAN_TASK and the other immediately enters a nested PARALLEL_GATEWAY

**Given:**
- A `DefinitionGraph` with nodes:
  - `PARALLEL_GATEWAY("gw1")` — outer split
  - `HUMAN_TASK("task_a")` — branch A resting node
  - `PARALLEL_GATEWAY("gw2")` — nested split on branch B
  - `HUMAN_TASK("task_b1")`, `HUMAN_TASK("task_b2")` — targets of nested split
- Edges:
  - `e1` (gw1 → task_a)
  - `e2` (gw1 → gw2)
  - `e3` (gw2 → task_b1)
  - `e4` (gw2 → task_b2)
- An `InstanceState` with one token on `"gw1"`, `pending_events = []`.

**When:**
- `processNodeEntry(allocator, graph, state, "gw1")` is called.

**Then:**
- `result.tokens.len == 3` — one token on `"task_a"`, one on `"task_b1"`, one on `"task_b2"`.
- No token has `node_id == "gw1"` or `node_id == "gw2"` (neither gateway retains a token).
- `result.pending_events.len == 2` — one `PARALLEL_SPLIT` for the outer split (gw1) and one for the nested split (gw2).
- At least one `pending_events[i].parallel_split.source_node_id == "gw1"`.
- At least one `pending_events[j].parallel_split.source_node_id == "gw2"`.
- The `task_a` token's `branch_id` is NOT equal to the `task_b1` token's `branch_id` and NOT equal to the `task_b2` token's `branch_id`.
- The `task_b1` and `task_b2` tokens have distinct `branch_id` values.

**Notes:**
- This test validates the recursive token activation in design §2 Step f: when a newly created token lands on another `PARALLEL_GATEWAY`, `processNodeEntry` is called recursively, accumulating all `pending_events` in the returned state.
- Token independence (AC2) is verified by the fact that tokens land on separate `HUMAN_TASK` nodes with no shared state between them.

**Layer:** unit  
**Acceptance criterion mapped:** AC1 — recursive split activates all branches; AC2 — branches land on independent nodes; AC3 — both PARALLEL_SPLIT events are captured in `pending_events`.

### TC-EE-06-08: All N tokens and the PARALLEL_SPLIT event are persisted in a single DB transaction (DB-03)

**Given:**
- A running BPM instance with an active token on a `PARALLEL_GATEWAY` node with 2 outgoing edges.
- A test database (`bpm_test`) with migrations applied; test wrapped in a rolled-back transaction (`TestHarness`).

**When:**
- The engine endpoint processes the PARALLEL_GATEWAY evaluation:
  1. `transition()` is called — returns `InstanceState` with 2 new tokens and 1 `PARALLEL_SPLIT` pending event.
  2. The caller persists both token records and the `PARALLEL_SPLIT` event row to `event_store`, all within one DB transaction.
  3. The transaction commits.

**Then:**
- Both token rows exist in the instance projection table.
- Exactly one `PARALLEL_SPLIT` event row exists in `event_store` for this instance, with `payload.source_node_id` matching the gateway node ID and `payload.edge_count == 2`.
- If the transaction is rolled back before commit, neither token rows nor the event row exist.

**Notes:**
- This test cannot be covered by a pure unit test; it requires the DB-layer caller.
- DB-03 compliance is the caller's responsibility; `transition.zig` itself performs zero I/O.

**Layer:** integration (requires real PostgreSQL via `TestHarness`)  
**Acceptance criterion mapped:** AC4 — all N tokens and the PARALLEL_SPLIT event are created atomically in a single transaction.
