## Scope

AGT-01: Artifact envelope with kind discrimination, closed per-kind payload schemas, and schema catalog endpoint.
AGT-02: Non-production environment enforcement — `staging` schema only, 403 on production, `ArtifactSubmissionRejected` audit event.
AGT-03: Submission idempotency on `(tenant_id, task_spec_id, attempt_count)` via `INSERT … ON CONFLICT … RETURNING xmax`.
AGT-04: Immutable task specs, RFC 8785 canonical JSON spec_hash, attempt-count regression guard.

All tests use `BPM_TEST_DB_URL` and call handler functions directly. Every test uses per-test UUID fixtures. All fixtures are cleaned up via `defer` regardless of test outcome.

## AGT-01 Test Cases

### TC-AGT-01-01: kind=test_report valid payload → 201 + kind stored in DB

**Preconditions:**
- A task spec is registered under DEFAULT_TENANT_ID (provides `spec_hash`).
- Staging schema and `staging.agent_artifacts` table are present (migration 1171).

**Steps:**
1. Register a task spec with a unique rng_seed; record `spec_hash` and `task_spec_id`.
2. Build an envelope with `kind = "test_report"` and a minimal valid `test_report` payload.
3. Call `handleArtifactSubmit(allocator, &pool, auth, body, false)` (staging mode).

**Expected:**
- HTTP 201.
- Response body contains `artifact_id` (non-empty) and `kind = "test_report"`.
- `SELECT kind FROM staging.agent_artifacts WHERE artifact_id = $1` returns `"test_report"`.

### TC-AGT-01-06: DB query filtered by kind returns only matching rows

**Preconditions:** Task spec registered; staging schema present.

**Steps:**
1. Register task spec → `spec_hash` H, `task_spec_id` TID.
2. Submit artifact with `kind = "test_report"`, `attempt_count = 0` → `artifact_id` A1 (201).
3. Submit artifact with `kind = "scenario_run"`, `attempt_count = 1` → `artifact_id` A2 (201).
4. Query: `SELECT COUNT(*) FROM staging.agent_artifacts WHERE artifact_id = $1 AND kind = 'test_report'` for A1.
5. Query: `SELECT COUNT(*) FROM staging.agent_artifacts WHERE artifact_id = $2 AND kind = 'test_report'` for A2.

**Expected:**
- Step 4 returns 1.
- Step 5 returns 0 (A2 has kind `scenario_run`, not `test_report`).
- Confirms the `kind` index filters correctly without payload parsing.

### TC-AGT-02-06 (SEC-AGT-02): cross-tenant probe and genuine not-found → byte-identical 404

**Preconditions:** Task spec registered with `spec_hash` H; staging schema present.

**Steps:**
1. Register task spec S → `spec_hash` H. Delete the task spec row (simulating H is accessible
   only in another tenant's schema, not the current one).
2. Probe 1: call `handleArtifactSubmit` with spec_hash = H from DEFAULT_TENANT_ID → 404, capture body1.
3. Probe 2: call `handleArtifactSubmit` again with the same spec_hash = H → 404, capture body2.
4. Assert body1 == body2 (byte-for-byte identical: same hash in both probes, same code path).
5. Parse body1; assert `"error" = "task_spec_not_found"`.

**Expected:**
- Both probes return HTTP 404.
- Both response bodies are byte-for-byte identical.
- Error code is `task_spec_not_found` (same structure regardless of whether the hash was
  ever registered elsewhere — proves probe indistinguishability).

## AGT-03 Test Cases

### TC-AGT-03-01: fresh insert → 201, xmax=0 (new artifact_id)

**Preconditions:** Task spec registered; no existing row in `staging.agent_artifacts` for this triple.

**Steps:**
1. Register task spec → `spec_hash` H.
2. Call `handleArtifactSubmit` with a fresh triple (tenant, task_spec_id, attempt_count=0).

**Expected:**
- HTTP 201.
- Response body contains `artifact_id` (non-empty string).
- `SELECT (xmax = 0)::text AS is_new FROM staging.agent_artifacts WHERE artifact_id = $1` returns `"true"`.

---

### TC-AGT-03-02: re-hit with matching spec_hash → 200, same artifact_id, payload byte-identical

**Preconditions:** Task spec registered; one prior submission in `staging.agent_artifacts`.

**Steps:**
1. Register task spec → `spec_hash` H, `task_spec_id` TID.
2. Submit artifact, attempt_count=0 → 201, `artifact_id` A1.
3. Submit same envelope (same kind, same task_spec_id, same attempt_count=0, same spec_hash) → result R2.

**Expected:**
- R2: HTTP 200.
- R2 body contains `artifact_id` = A1 (same as first call).
- `SELECT payload::text FROM staging.agent_artifacts WHERE artifact_id = $1` confirms payload is unchanged.

---

### TC-AGT-03-03: re-hit with different spec_hash → 409 spec_hash_mismatch

**Preconditions:** Task spec registered; staging row inserted directly to force a mismatch scenario.

**Steps:**
1. Register task spec → `spec_hash` H, `task_spec_id` TID.
2. INSERT directly into `staging.agent_artifacts` with `(tenant_id, task_spec_id=TID, attempt_count=0)` and
   `spec_hash = '<all-a-64chars>'` (a deliberately wrong spec_hash — not H).
3. Submit request with spec_hash=H and attempt_count=0 → handler looks up TID via H, attempts conflict insert;
   receives `inserted=false`, compares stored hash `<all-a-64chars>` with submitted H → mismatch.

**Expected:**
- HTTP 409.
- Response body contains `"error": "spec_hash_mismatch"`.
- Response body contains `"stored_spec_hash"` (the injected mismatched hash).
- Response body contains `"submitted_spec_hash"` (the valid hash H).
- Stored row in `staging.agent_artifacts` is unmodified (payload unchanged).

---

### TC-AGT-03-04: retry after timeout → 200, exactly one DB row

**Preconditions:** Task spec registered.

**Steps:**
1. Submit → 201 (first insert).
2. Submit identical envelope → 200 (re-hit matches).
3. Query: `SELECT COUNT(*) FROM staging.agent_artifacts WHERE task_spec_id = $1 AND attempt_count = 0` using TID.

**Expected:**
- First call: HTTP 201.
- Second call: HTTP 200.
- COUNT query returns exactly 1 (no duplicate rows created by idempotency re-hit).

---

### TC-AGT-03-05: attempt_count < max stored → 409 attempt_count_regressed

**Preconditions:** Task spec registered.

**Steps:**
1. Submit with `attempt_count = 2` → 201 (max stored for TID is now 2).
2. Submit with `attempt_count = 1` → should be rejected.

**Expected:**
- First call: HTTP 201.
- Second call: HTTP 409.
- Second call body contains `"error": "attempt_count_regressed"`.
- Second call body contains `"submitted_attempt": 1` and `"max_stored_attempt": 2`.

---

### TC-AGT-03-06: two concurrent same-triple submissions → exactly one 201, one 200-or-409

**Preconditions:** Task spec registered; pool with ≥ 2 connections.

**Steps:**
1. Register task spec → `spec_hash` H, `task_spec_id` TID.
2. Spawn two threads; each thread calls `handleArtifactSubmit` with the identical envelope
   (same kind, same TID, same attempt_count=0, same spec_hash H).
3. Join both threads; collect status codes.

**Expected:**
- Exactly one thread receives HTTP 201.
- The other thread receives HTTP 200 (matching spec_hash re-hit) or HTTP 409 (spec_hash mismatch
  if race results in concurrent insert with different stored hash — not expected for matching envelopes).
- In practice, both envelopes are identical so the second thread always receives HTTP 200.
- `SELECT COUNT(*) FROM staging.agent_artifacts WHERE task_spec_id = $1 AND attempt_count = 0` = 1.

## AGT-04 Test Cases

### TC-AGT-04-01: same doc, different key order → same spec_hash

**Preconditions:** None beyond a registered task spec.

**Steps:**
1. Register spec body `{"rng_seed":42,"task_name":"canon-test","priority":1}` as user U → `spec_hash` H1.
2. Register spec body `{"priority":1,"task_name":"canon-test","rng_seed":42}` (same fields, different order) as user U.

**Expected:**
- First call: HTTP 201.
- Second call: HTTP 409 with `"detail": "task_spec_immutable"`.
- (If second call returned 201, the hashes would differ — that would be a test failure indicating RFC 8785 sort is not applied.)

---

### TC-AGT-04-02: number 1.0 vs 1 → same spec_hash (RFC 8785 normalization)

**Preconditions:** None.

**Steps:**
1. Register spec body `{"rng_seed":7,"count":1}` (integer) as user U → `spec_hash` H1.
2. Register spec body `{"rng_seed":7,"count":1.0}` (float) as user U.

**Expected:**
- First call: HTTP 201.
- Second call: HTTP 409 `task_spec_immutable` (hashes equal after RFC 8785 number normalization).

---

### TC-AGT-04-03: update existing task_spec → 409 task_spec_immutable, row unchanged

**Preconditions:** Task spec already registered.

**Steps:**
1. Register spec body B → `task_spec_id` TID, `spec_hash` H.
2. Attempt to register the exact same spec body B again (same user, same body).

**Expected:**
- Second call: HTTP 409.
- Second call body contains `"detail": "task_spec_immutable"`.
- `SELECT task_spec_id FROM task_specs WHERE spec_hash = $1` still returns TID (row unchanged).

---

### TC-AGT-04-04: one changed field → different spec_hash, both rows accessible

**Preconditions:** None.

**Steps:**
1. Register spec `{"rng_seed":1,"task_name":"v1"}` as user U → TID1, H1.
2. Register spec `{"rng_seed":1,"task_name":"v2"}` (one field changed) as user U → TID2, H2.

**Expected:**
- Both calls: HTTP 201.
- TID1 ≠ TID2.
- H1 ≠ H2.
- `SELECT task_spec_id FROM task_specs WHERE spec_hash = $1` for H1 returns TID1 (still addressable).
- `SELECT task_spec_id FROM task_specs WHERE spec_hash = $1` for H2 returns TID2.

### TC-AGT-04-06: same spec, different orchestrator_principal → different spec_hash

**Preconditions:** Two distinct user UUIDs as orchestrator principals.

**Steps:**
1. Register spec body `{"rng_seed":99,"task_name":"principal-test"}` as user A → `spec_hash` H_A.
2. Register same spec body as user B → `spec_hash` H_B.

**Expected:**
- Both calls: HTTP 201.
- H_A ≠ H_B (because `orchestrator_principal` is merged into the canonical document before hashing).
- `SELECT task_spec_id FROM task_specs WHERE spec_hash = $1` for H_A returns TID_A.
- `SELECT task_spec_id FROM task_specs WHERE spec_hash = $1` for H_B returns TID_B.
- TID_A ≠ TID_B.
