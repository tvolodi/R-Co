# Test Spec: EE-09 — Variable Scoping and Merge

**Requirement:** EE-09 — Instance variables SHALL be a mutable JSON object. Task output variables SHALL be merged into the instance variable map upon task completion per the variable collision policy defined above.  
**Priority:** MUST  
**Test layer:** integration (TC-EE-09-01 through TC-EE-09-08), unit (json_schema validator + mergeVariables fast-path in tests/unit/test_ee09_merge_variables.zig)

---

## Acceptance Criteria (verbatim from spec)

1. GIVEN task completion with `output_variables` containing key K not present in the instance map, WHEN merged, THEN K is inserted into the instance map.
2. GIVEN task completion with `output_variables` containing key K already present, and the new value is schema-compatible (or no schema is defined), WHEN merged, THEN K is overwritten and a `VARIABLE_OVERWRITTEN` event is appended recording the key, old value, and new value.
3. GIVEN task completion with `output_variables` containing key K already present, and a registered variable schema rejects the new value, WHEN merge is attempted, THEN the merge is NOT applied, the instance transitions to ERROR status (EE-10), and an `EXECUTION_ERROR` event is appended.
4. Variable state after merge is immediately accessible to subsequent CEL condition evaluations (EE-05).

**Edge cases:**
- Empty `output_variables = {}`: merge is a no-op; no `VARIABLE_OVERWRITTEN` event is appended.
- Duplicate key in one task completion's JSON object: standard JSON semantics (last value wins in the parsed object before merge).

## Test Cases

### TC-EE-09-01: New key insert — output_variables adds a key absent from the instance map

**Given:**
- An ACTIVE process instance with `variables = {"existing_key": "old_value"}`.
- A PENDING HUMAN_TASK on that instance.
- A variable schema is NOT registered for `"new_key"`.

**When:**
- `InstanceStore.completeTask()` is called with `output_variables = {"new_key": "new_value"}`.

**Then:**
- The function returns without error.
- `instance_projections.variables` contains `"new_key": "new_value"` in addition to `"existing_key"`.
- No `VARIABLE_OVERWRITTEN` event row is created for this instance.
- Exactly one `TASK_COMPLETED` event exists for this instance.

**Layer:** integration  
**Acceptance criterion mapped:** AC-1 (new key inserted; no VARIABLE_OVERWRITTEN event)

---

### TC-EE-09-02: Existing key overwrite (no schema) — new value overwrites old and emits event

**Given:**
- An ACTIVE process instance with `variables = {"score": 42}`.
- A PENDING HUMAN_TASK on that instance.
- No variable schema is registered for `"score"`.

**When:**
- `InstanceStore.completeTask()` is called with `output_variables = {"score": 99}`.

**Then:**
- The function returns without error.
- `instance_projections.variables` contains `"score": 99`.
- Exactly one `VARIABLE_OVERWRITTEN` event row exists for this instance, with payload fields:
  - `event_type = "VARIABLE_OVERWRITTEN"`
  - `key = "score"`
  - `old_value = "42"` (JSON-serialised)
  - `new_value = "99"` (JSON-serialised)
- Instance status remains `ACTIVE`.

**Layer:** integration  
**Acceptance criterion mapped:** AC-2 (existing key overwritten; VARIABLE_OVERWRITTEN event appended with old/new values)

---

### TC-EE-09-03: Existing key overwrite with schema-compatible value — overwrites and emits event

**Given:**
- An ACTIVE process instance with `variables = {"amount": 500}`.
- A PENDING HUMAN_TASK on that instance.
- A variable schema is registered for `"amount"` with `{"type": "integer", "minimum": 0, "maximum": 10000}`.
- New value `1500` satisfies that schema.

**When:**
- `InstanceStore.completeTask()` is called with `output_variables = {"amount": 1500}`.

**Then:**
- The function returns without error.
- `instance_projections.variables` contains `"amount": 1500`.
- Exactly one `VARIABLE_OVERWRITTEN` event row exists with `key = "amount"`, `old_value = "500"`, `new_value = "1500"`.
- Instance status remains `ACTIVE`.

**Layer:** integration  
**Acceptance criterion mapped:** AC-2 + schema-compatible branch (schema exists, value passes — overwrite proceeds normally)

### TC-EE-09-04: Schema violation — merge NOT applied; instance transitions to ERROR; HTTP 422

**Given:**
- An ACTIVE process instance with `variables = {"status": "pending"}`.
- A PENDING HUMAN_TASK on that instance.
- A variable schema registered for `"status"` with `{"type": "string", "enum": ["pending", "approved", "rejected"]}`.
- New value `"unknown_state"` is NOT in the allowed enum.

**When:**
- `InstanceStore.completeTask()` is called with `output_variables = {"status": "unknown_state"}`.

**Then:**
- The function returns `CompleteTaskError.SchemaViolationError`.
- `instance_projections.variables` remains `{"status": "pending"}` (merge was NOT applied).
- `instance_projections.status` is `ERROR`.
- An `EXECUTION_ERROR` event row exists for this instance with a payload containing:
  - `error_type = "SCHEMA_VIOLATION"` (or equivalent structured reason)
  - `affected_field = "status"`
  - `variable_state` containing the pre-merge variable map.
- No `VARIABLE_OVERWRITTEN` event exists for this instance.
- At the HTTP layer, `POST /tasks/:id/complete` returns HTTP 422 with error code `"SCHEMA_VIOLATION"`.

**Layer:** integration  
**Acceptance criterion mapped:** AC-3 (schema violation: merge NOT applied, instance → ERROR, EXECUTION_ERROR event appended)

### TC-EE-09-06: Multiple keys in one completion — new inserts and overwrites handled individually

**Given:**
- An ACTIVE process instance with `variables = {"a": 1, "b": "old"}`.
- A PENDING HUMAN_TASK on that instance.
- No variable schemas registered for any key.

**When:**
- `InstanceStore.completeTask()` is called with `output_variables = {"a": 99, "b": "new", "c": "fresh"}`.

**Then:**
- The function returns without error.
- `instance_projections.variables` contains `{"a": 99, "b": "new", "c": "fresh"}`.
- Exactly two `VARIABLE_OVERWRITTEN` events exist for this instance (one for `"a"`, one for `"b"`).
- No `VARIABLE_OVERWRITTEN` event for `"c"` (it was a new key, not an overwrite).
- Exactly one `TASK_COMPLETED` event exists for this instance.

**Layer:** integration  
**Acceptance criterion mapped:** AC-1 (new key `c`), AC-2 (existing keys `a` and `b` overwritten), one VARIABLE_OVERWRITTEN per overwritten key

### TC-EE-09-07: Merged variables immediately available to CEL — exclusive gateway routes correctly after merge

**Given:**
- An ACTIVE process instance starting execution on a definition:
  `START → HUMAN_TASK("review") → EXCLUSIVE_GATEWAY → HUMAN_TASK("high") / HUMAN_TASK("low")`
  with edge to `"high"` condition `variables.score > 80` and default edge to `"low"`.
- The instance starts with `variables = {"score": 10}`.
- The review task is PENDING.

**When:**
- `InstanceStore.completeTask()` is called for the review task with `output_variables = {"score": 95}`.

**Then:**
- The function returns without error.
- `instance_projections.variables` contains `"score": 95`.
- The token advances through the gateway and lands on `"high"` (condition `variables.score > 95` ... wait, actually `95 > 80` is true so it follows the first matching edge).
- A task row exists for node `"high"` with status `PENDING`.
- No task row exists for node `"low"`.

**Layer:** integration  
**Acceptance criterion mapped:** AC-4 (merged variables are immediately available for CEL gateway evaluation — EE-05 integration)

---

### TC-EE-09-08: Task completion attempt on instance in ERROR status — HTTP 409

**Given:**
- An instance that is in ERROR status (e.g. previously encountered a schema violation per TC-EE-09-04).
- A task row for that instance with status `PENDING`.

**When:**
- `InstanceStore.completeTask()` is called with that task's ID.

**Then:**
- The function returns `CompleteTaskError.TaskAlreadyTerminated` (the instance is non-ACTIVE; the task row on an ERROR instance should have been set appropriately), OR the handler detects instance status = ERROR and returns HTTP 409.

**Implementation note:** EE-10 specifies that an ERROR instance rejects further task completions with HTTP 409. The precise error path depends on whether the task is still PENDING or has been marked CANCELLED when the instance transitioned to ERROR. The test MUST confirm that the API returns HTTP 409 (not 200) when a completion is attempted on an instance already in ERROR.

**Layer:** integration  
**Acceptance criterion mapped:** EE-10 AC-2 (ERROR instance rejects task completion with HTTP 409)
