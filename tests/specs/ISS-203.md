# Test Spec: ISS-203 — Deterministic idempotency keys for engine-emitted cascade events

**Requirement:** ISS-203 — When `transition()` fires cascade events, each emitted event
must carry a deterministic `idempotency_key` string of the form `"engine:<16-hex-digits>"`,
computed from `(instance_id, triggering_event_seq, node_id, event_type_tag, ordinal)` using
FNV-1a 64-bit. Client-supplied keys on trigger events must pass through unchanged. A second
call to `store.append()` with the same key is silently absorbed by `ON CONFLICT DO NOTHING`.  
**Priority:** MUST  
**Test layer:** integration (all 5 cases require real PostgreSQL via `BPM_TEST_DB_URL`)

---

## Test Cases

### TC-ISS-203-01: Single transition — emitted events carry correct deterministic keys

**Given:** A process definition `START → TIMER("PT5M")` whose single node emits a
`timer_created` cascade event when an instance is created. The triggering event
(`instance_started`) is assigned `sequence_number = 1` by the event store.

**When:** An instance is created (which drives `transition()` internally).

**Then:**
- Exactly one event with `event_type = 'instance_started'` exists in the `events` table
  for the instance.
- Exactly one emitted-event idempotency key is present; it starts with `"engine:"`,
  has total length 23 characters, and contains only lowercase hex digits after the prefix.
- The key is stable: computing
  `FNV-1a-64(instance_id_bytes || 0x00 || seq_be || 0x00 || "TIMER_NODE_ID" || 0x00 || "timer_created" || 0x00 || ordinal_be)`
  with `seq = 1` and `ordinal = 0` yields a value whose hex representation matches the
  stored key.

**Layer:** integration  
**Acceptance criterion mapped:** K-1 (key is non-empty, ≤ 23 chars), K-2 (deterministic
inputs only), format invariant (`"engine:<16-hex-digits>"`).

### TC-ISS-203-02: Replay deduplication — second append of same key absorbed silently

**Given:** A process definition `START → TIMER("PT5M")` and a live instance. The
orchestrator persists the trigger event and emitted events once (first pass).

**When:** The same emitted event keys are inserted again via a direct SQL
`INSERT INTO events … ON CONFLICT (idempotency_key) DO NOTHING` (simulating a
retry of the orchestrator step after a crash).

**Then:**
- The `events` table still contains exactly the same number of rows for the instance
  as after the first pass — no duplicate rows.
- The count of rows matching the `"engine:"` prefix on `idempotency_key` for this
  instance is unchanged.

**Layer:** integration  
**Acceptance criterion mapped:** K-6 (ON CONFLICT DO NOTHING absorbs replay), design
section §4 (duplicate detection path).

### TC-ISS-203-03: Client key passthrough — trigger event key stored as-is

**Given:** A process definition `START → HUMAN_TASK` (no emitted events on the trigger).
The API caller supplies an explicit `idempotency_key = "client-supplied-key-abc"` when
creating the instance (triggering `instance_started`).

**When:** The instance is created and the trigger event is persisted.

**Then:**
- The `events` table row for `event_type = 'instance_started'` has
  `idempotency_key = 'client-supplied-key-abc'` (byte-exact match).
- No `"engine:"` prefix appears on the trigger event row.
- The engine does not overwrite, modify, or inspect the client-supplied key at any point.

**Layer:** integration  
**Acceptance criterion mapped:** K-4 (client-supplied keys untouched), design section §5.

---

### TC-ISS-203-04: Different-instance isolation — same transition on two instances yields different keys

**Given:** The same process definition `START → TIMER("PT5M")` instantiated twice,
producing two different instance IDs (per-test UUIDs).

**When:** Both instances are created (both trigger `transition()` internally with the
same graph snapshot and the same `triggering_event_seq = 1`).

**Then:**
- The emitted-event idempotency key stored for instance A is different from the key
  stored for instance B.
- Both keys have the `"engine:"` prefix and are exactly 23 characters long.

**Layer:** integration  
**Acceptance criterion mapped:** K-2 (instance_id is part of hash input), design §1
(FNV-1a formula includes `instance_id` bytes as field 1).

---

### TC-ISS-203-05: Ordinal uniqueness — N emitted events from one transition produce N distinct keys

**Given:** A process definition `START → PARALLEL_GATEWAY(split) → [TIMER_A("PT1M"),
TIMER_B("PT2M")]` where the parallel split fires two `timer_created` emitted events
(ordinal 0 = TIMER_A, ordinal 1 = TIMER_B) plus one `parallel_split` event (ordinal 0
relative to it — but since all events are in the same `emitted_events` slice their ordinals
are 0, 1, 2 in slice order).

**When:** An instance is created causing `transition()` to emit at least 2 cascade events
in a single call.

**Then:**
- The set of `idempotency_key` values for all emitted events stored in the `events` table
  for this instance (rows with key prefix `"engine:"`) has no duplicates.
- The number of distinct keys equals the number of cascade events emitted by `transition()`
  in that single call.

**Layer:** integration  
**Acceptance criterion mapped:** K-2 (ordinal is part of hash formula), design §6
Invariant R-1 (ordinals are stable and 0-based within one transition call).
