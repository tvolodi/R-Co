# Test Spec: XC-06 — Backwards Compatibility

**Requirement:** XC-06 — A new platform version loads and continues instances created by prior versions. Definition format changes are migration-pathed.  
**Priority:** MUST  
**Test layer:** integration

---

## Overview

Backwards compatibility ensures that schema migrations, definition format changes, and event log evolution do not break instances created by prior platform versions. The platform must:

1. Apply schema migrations in sequence (additive, no destructive changes)
2. Migrate definition formats automatically at activation
3. Load and continue old instances without errors
4. Handle legacy fields gracefully (null checks, defaults)
5. Preserve event log integrity across versions

---

## Test Cases

### TC-XC-06-01: Schema migrations are idempotent and additive

**Given:** A set of ordered migration files (001_*.sql, 002_*.sql, ..., NNN_*.sql).

**When:** Migrations are applied to a fresh database.

**Then:**
- Each migration is applied in sequence
- Migrations use `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ADD COLUMN IF NOT EXISTS`
- Idempotency: running migrations twice produces the same schema
- No columns are dropped; all changes are additive

**Acceptance:**
- Running migration suite twice produces identical schema
- All schema changes are backwards compatible (new columns have defaults, nullable)
- Migration state is tracked in schema_migrations table

**Layer:** integration  
**Fixtures:**
- Complete migration suite

---

### TC-XC-06-02: Instance records from prior version can be loaded

**Given:** An instance record created by platform version V1 (prior version).

**When:** Platform version V2 is started and the instance is queried.

**Then:**
- Instance loads without errors
- All legacy fields are read correctly (including NULL values for new columns)
- Instance state is reconstructible
- No corruption or data loss

**Acceptance:**
- Instance can be loaded and queried
- Null values in new columns are handled gracefully
- Defaults are applied where needed

**Layer:** integration  
**Fixtures:**
- Snapshot of a V1 database with instances

---

### TC-XC-06-03: Instance continues normally after schema upgrade

**Given:** An instance from version V1 that has been loaded by version V2.

**When:** New events are appended to the instance.

**Then:**
- Events append successfully with all V2 fields (including new columns like trace_id)
- Instance state continues to evolve correctly
- No conflicts between old and new event formats

**Acceptance:**
- Instance transitions from V1 to V2 state seamlessly
- New events include new fields (trace_id, etc.)
- Instance completes normally

**Layer:** integration  
**Fixtures:**
- V1 instance loaded by V2 platform

---

### TC-XC-06-04: Definition format migration is automatic at activation

**Given:** A definition artifact in V1 format (e.g., missing `escalation_timer_duration` field on nodes).

**When:** The definition is activated in V2 platform (which expects the field).

**Then:**
- Definition is automatically migrated from V1 to V2 format
- Migration adds defaults for missing fields (e.g., escalation_timer_duration = "PT1H")
- Migrated definition is validated and accepted
- Original V1 artifact is unchanged (immutable)

**Acceptance:**
- Definition activation triggers automatic migration
- Migrated definition has all required V2 fields
- Migration is idempotent (migrating twice produces same result)

**Layer:** integration  
**Fixtures:**
- V1-format definition artifact

---

### TC-XC-06-05: Event type evolution is backwards compatible

**Given:** An event type `order.created` (V1) with optional new fields in V2.

**When:** V2 platform reads V1 events of this type.

**Then:**
- V1 events are deserialized correctly
- Missing fields (new in V2) are handled with defaults or null checks
- V2 code does not crash on V1 event payloads

**Acceptance:**
- V1 event payloads are processable by V2 code
- No schema validation errors for V1 events
- Defaults are applied for missing V2 fields

**Layer:** integration  
**Fixtures:**
- Instance with V1-format events, loaded by V2

---

### TC-XC-06-06: Archived events remain queryable after upgrade

**Given:** Events archived (moved to events_archive) in V1, now loaded by V2.

**When:** Point-in-time reconstruction queries archived events.

**Then:**
- Archived events are correctly joined with live events
- Reconstruction includes archived events
- No errors due to schema version mismatch

**Acceptance:**
- Archived events are readable by V2 (schema compatible)
- Reconstruction includes both live and archived

**Layer:** integration  
**Fixtures:**
- Instance with some events archived in V1

---

### TC-XC-06-07: Multi-step schema evolution is supported

**Given:** A chain of schema changes (V1 → V2 → V3 → V4) each adding columns.

**When:** Platform jumps from V1 to V4 (or incrementally applies V2, V3, V4).

**Then:**
- All intermediate migrations are applied in order
- Final schema is V4-compliant
- No data loss or corruption
- Instances created in V1 are loadable by V4

**Acceptance:**
- Multi-version jump is supported
- All instances remain functional
- Data integrity is preserved

**Layer:** integration  
**Fixtures:**
- Database with V1 schema and instances

---

### TC-XC-06-08: Audit log evolution maintains chain integrity

**Given:** Audit entries from V1 (before XC-02 chain columns were added).

**When:** V2 migration adds chain_hash and prev_chain_hash columns.

**Then:**
- V1 audit entries have null chain fields
- V2 entries have populated chain fields
- Chain validation treats V1 entries as legacy (pre-chain history)
- No false-positive tampering detected across V1/V2 boundary

**Acceptance:**
- Legacy audit entries coexist with chained entries (TC-XC-02-06)
- Chain validation works correctly
- V1 entries are accepted as pre-chain history

**Layer:** integration  
**Fixtures:**
- V1 database with audit entries, upgraded to V2

---

### TC-XC-06-09: Backward-compatible defaults prevent runtime errors

**Given:** A column added in V2 with a NOT NULL constraint but a default value.

**When:** V1 instances are loaded by V2.

**Then:**
- Null values in new columns are filled with defaults
- Constraints are satisfied
- No NULL check failures or database errors

**Acceptance:**
- V1 records satisfy V2 constraints without modification
- Defaults are correctly applied

**Layer:** integration  
**Fixtures:**
- V1 instance, new column with default

## Success Criteria

1. All test cases pass
2. No data loss during schema upgrades
3. V1 instances load and continue in V2 without errors
4. Definition format migration is automatic and transparent
5. Legacy audit entries coexist with chained entries without false positives
6. Multi-step schema evolution is supported
7. No test.skip entries
8. Tests use per-test UUIDs and clean up after themselves
9. Tests fail clearly if BPM_TEST_DB_URL is absent

## Notes

**Definition Migration Timing:** Migrations are run either:
1. At startup (all activations migrate automatically), or
2. At activation time (definition-specific migration)

Recommend at-activation-time migration to allow multiple format versions to coexist in the repository.

**Rollback Strategy:** Database rollback is NOT supported within the same transaction (migrations are one-way). Rollback requires restoring a database backup. This is acceptable per the design spec.
