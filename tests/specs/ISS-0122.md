# Test Spec: ISS-0122 — Audit chain TEXT resource_id + non-UTF-8 resilience (GitHub #388)

**Requirement:** ISS-0122 / GitHub #388 — 85 occurrences of PostgreSQL `22021 invalid_byte_sequence_for_encoding "UTF8": 0xaa` in `tests/reports`, originating in the `bpm_audit_apply_chain_hash` BEFORE INSERT trigger on `audit_entries` and propagating back to the originating `INSERT` against a parent table whose primary key is `TEXT`. The fix is migration `1107_fix_audit_chain_text_resource_id.sql` and is already implemented and committed on `feature/WF03-gh388-20260802`.

**Priority:** MUST (ISS-0122 is a BLOCKER for `test-runner` step 4 — the symptoms otherwise pollute every parent-table INSERT that goes through `bpm_audit_on_mutation` while a sibling binary has written a `0xAA`-contaminated row).

**Test layer:** integration (real PostgreSQL via `BPM_TEST_DB_URL`). The four test cases are colocated in a new file `tests/integration/audit_chain_utf8_test.zig` and run against the existing `helpers.TestHarness` (transaction rollback on `deinit`, no mocks, no stubs).

---

## Test cases

### TC-ISS-0122-01 — ASCII row writes through the audit chain trigger without C22021

**Given:**
- `TestHarness` has applied every migration in `migrations/`, including `1107_fix_audit_chain_text_resource_id.sql`.
- A per-test text-PK parent table `parent_iss0122_<uuid>` has been created inside the harness's transaction, with a BEFORE INSERT trigger that delegates to the canonical `bpm_audit_on_mutation()` chain. The test uses a private, per-test resource_type (e.g. `'iss0122.parent.tc01'`) so its rows are trivially distinguishable from any other test's audit history.

**When:**
The test inserts a parent row whose `id` is the pure-ASCII string `'tc01-ascii-row-id'`:
```sql
INSERT INTO parent_iss0122_<uuid> (id, payload) VALUES ('tc01-ascii-row-id', 'ascii');
```

**Then:**
- The `INSERT` MUST succeed (no `C22021`, no `C22P02`, no `42703`, no `P0001` from the chain-trigger exception guard).
- `audit_entries` MUST contain exactly one row whose `resource_type = 'iss0122.parent.tc01'` and `resource_id = 'tc01-ascii-row-id'`; that row's `chain_hash` MUST be a 64-character lowercase hex string (NOT NULL, NOT all-zero — the canonical SHA-256 of the normalised payload).
- `prev_chain_hash` of that row MUST equal the `chain_hash` of the previous row written for the same tenant under `resource_type = 'iss0122.parent.tc01'`, and MUST be NULL when this is the very first such row.

**Layer:** integration. Real PostgreSQL, real `bpm_audit_apply_chain_hash` trigger, real per-tenant advisory lock via `pg_advisory_xact_lock`.

**Acceptance criterion mapped:** happy path of the fix — the new `bpm_audit_chain_canonical_payload` and `bpm_audit_compute_chain_hash` SQL functions accept a pure-ASCII `TEXT` PK unchanged from the GBL-082 baseline. If this test fails, the migration has introduced a regression on the already-supported ASCII path.

**Isolation:** per-test resource_type, per-test table name, per-test tenant UUID. Fixture state is rolled back at `harness.deinit()`.

### TC-ISS-0122-02 — Non-UTF-8 row writes through the audit chain trigger without C22021 propagation

**Given:**
- The trigger from TC-01 is still installed on a per-test parent table whose `id` column is `TEXT`.
- The test constructs a deliberately malformed-UTF-8 byte sequence using the canonical `convert_from(decode('e2aaaa','hex'),'UTF8')` pattern from `src/design/audit_chain_text_resource_id.md` §4: the literal three bytes `0xE2 0xAA 0xAA` are NOT valid UTF-8 (they would start a 3-byte sequence but the trailing `0xAA` is not a valid UTF-8 continuation byte or lead byte in any position). Under the pre-fix code path, feeding this value into `bpm_audit_apply_chain_hash` raised `22021 invalid_byte_sequence_for_encoding "UTF8": 0xaa`, propagated through the trigger and the originating `INSERT`, and surfaced in the API response and `tests/reports`.

**When:**
The test inserts a parent row whose `id` is the conversion expression `convert_from(decode('e2aaaa','hex'),'UTF8')` cast to `TEXT`:
```sql
INSERT INTO parent_iss0122_<uuid> (id, payload)
VALUES (convert_from(decode('e2aaaa','hex'),'UTF8')::text, 'invalid-utf8');
```

**Then:**
- The `INSERT` MUST succeed (no `C22021` propagating from the trigger to the parent INSERT).
- `audit_entries` MUST contain exactly one row whose `resource_type = 'iss0122.parent.tc02'` and whose `resource_id` matches the round-tripped byte sequence (`octet_length(NEW.resource_id) = 3`).
- That audit row's `chain_hash` is allowed to be EITHER a 64-character lowercase hex string (the SHA-256 of the **normalised** canonical payload, where the unsafe bytes were replaced by the `<invalid-utf8:N>` placeholder before hashing) OR `NULL` (the trigger chose to skip rather than risk a hash). What it MUST NOT be is a string that itself raises `C22021` on a later re-read.

**Layer:** integration. Real PostgreSQL. The trigger function installed by migration 1107 is what makes this case non-blocking.

**Acceptance criterion mapped:** the primary ISS-0122 fix. Without migration 1107, this test raises `C22021` and the `INSERT` fails. With migration 1107 applied, the `audit_apply_chain_hash` trigger's per-tenant advisory lock + UTF-8 pre-normalisation + outer `EXCEPTION WHEN OTHERS THEN RETURN NEW;` guard means the row always lands in `audit_entries` and the `INSERT` never propagates an encoding error.

**Isolation:** same as TC-01.

### TC-ISS-0122-03 — Validator returns empty `issues[]` after the non-UTF-8 insert

**Given:**
- TC-02 has completed and the per-test parent row exists.
- All `audit_entries` rows have `tenant_id = $PER_TEST_TENANT` and `resource_type = 'iss0122.parent.tc02'`.

**When:**
The test calls `bpm_audit_validate_chain($PER_TEST_TENANT::uuid, NULL, NULL, false)` and counts the rows in the returned table.

**Then:**
- The `issues[]` rows count MUST be `0`. (The validator legitimately skips rows with `chain_hash IS NULL`, per `chk_audit_entries_chain_hash_format` + the `WHERE chain_hash IS NOT NULL` filter the validator uses internally.)

**Layer:** integration.

**Acceptance criterion mapped:** tamper-evident chain property is preserved. The 64-zero sentinel hash from `bpm_audit_compute_chain_hash`'s `EXCEPTION` block, OR a skipped row with `chain_hash := NULL`, are both indistinguishable to the validator's chain-link integrity check — neither produces an entry in `issues[]`. A non-empty `issues[]` here would indicate the migration's normaliser silently corrupted the SHA-256 input in a way that still matched a previously-written predecessor (which is mathematically impossible but the test guards against it).

**Isolation:** per-test tenant UUID; rows outside this tenant are excluded by the validator's `tenant_id` filter.

### TC-ISS-0122-04 — Concurrent non-UTF-8 inserts do not fork the chain

**Given:**
- TC-02 has established a chain head (`prev_chain_hash IS NOT NULL`) for the per-test tenant under `resource_type = 'iss0122.parent.tc02'`.
- The per-test parent table is identical to TC-02's, and the test fires **multiple concurrent inserts** whose `id` column carries the same invalid-UTF-8 byte sequence `convert_from(decode('e2aaaa','hex'),'UTF8')`. Two `pg.Conn` handles are opened against `BPM_TEST_DB_URL` and each issues three sequential `INSERT`s against a separate row identifier so the chain has at least five rows total to walk.

**When:**
Both connections are interleaved in flight (the test uses `std.Thread.spawn` to start connection B immediately after connection A's first insert is sent but before it has returned — the exact ordering is non-deterministic but the test requires that at least two inserts run concurrently with respect to `pg_advisory_xact_lock`).

**Then:**
- Every `INSERT` MUST succeed (the precondition of TC-02 carries over).
- For every pair of consecutive `audit_entries` rows for this `(tenant_id, resource_type)`, ordered by `(timestamp ASC, audit_id ASC)`, the row's `prev_chain_hash` MUST equal the previous row's `chain_hash`. This is the chain-fork invariant — if it breaks, the per-tenant `pg_advisory_xact_lock(hashtext('bpm.audit.chain.' || tenant_id::text))` inside `bpm_audit_apply_chain_hash` was bypassed or skipped on the exception path.

**Layer:** integration. Real PostgreSQL. Two concurrent connections.

**Acceptance criterion mapped:** the advisory-lock serialisation guarantee from the design §3 step 6 — even if the chain-hash pipeline itself is wrapped in `EXCEPTION WHEN OTHERS`, the lock acquisition happens BEFORE the exception block, so concurrent writers still serialise and a writer that hits an exception never starves a concurrent writer of its `prev_chain_hash` lookup.

**Isolation:** per-test tenant UUID, per-test parent table name, per-test resource_type. Each test instance picks its own tenant UUID via `bpm.uuid.newUuidV4` so concurrent test instances cannot collide.

## Isolation and security contract

- Each test calls `TestHarness.init()` and rolls its transaction back with `defer harness.deinit()`. The harness's `deinit` already runs a best-effort `DELETE FROM audit_entries WHERE resource_id LIKE '<invalid-utf8:%'` pre-rollback sweep (added in the helpers.zig change that ships with the migration), so any `<invalid-utf8:N>` placeholder rows a skipped chain-hash produced are wiped before the next test binary runs.
- Missing `BPM_TEST_DB_URL` returns the explicit `error.MissingTestDatabaseUrl` from `TestHarness.init()` — no test is silently skipped. There is no `error.SkipZigTest` on any test block above (DIRECTIVE T-1 / MUST).
- All fixture SQL uses PostgreSQL placeholders (`$1::uuid`, `$1::text`, etc.) — no string interpolation of user data into SQL.
- Per-test UUIDs (`bpm.uuid.newUuidV4(alloc)`) are used for: the parent-table name suffix, the tenant UUID (per-test isolated tenant — separate from the harness's `DEFAULT_TENANT_ID` so chain forks cannot bleed from other binaries), every audit `actor_id`, every parent `id` that is a UUID. The invalid-UTF-8 byte sequence is reused across rows because that's the whole point of the test, but it lives in a per-test `resource_type` namespace and `tenant_id` namespace.
- No mocks, no stubs, no in-memory database, no `error.SkipZigTest`.
- The pre-rollback sweep in `TestHarness.deinit` is deliberate belt-and-suspenders protection against the same-family state contamination as ISS-0112 / GitHub #375.
