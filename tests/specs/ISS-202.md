# Test Spec: ISS-202 — Two-phase (all-or-nothing) variable merge

**Requirement:** ISS-202 — Variable merge into an instance must be atomic: either all keys are validated and applied together, or none are applied. Phase 1 validates all keys against their JSON schemas without any state change. Phase 2 applies all validated keys and emits VARIABLE_OVERWRITTEN events only if Phase 1 succeeds. On any validation failure in Phase 1, the instance remains unchanged and no events are emitted.

**Priority:** MUST

**Test layer:** unit, integration

## Test Cases

### TC-ISS-202-01: Phase 1 validation succeeds for all valid keys
**Given:** an instance with current variables and a merge request containing only keys that pass schema validation
**When:** the merge is invoked (Phase 1 validation runs)
**Then:** all keys pass validation, Phase 1 completes successfully with no errors, and Phase 2 is allowed to proceed
**Layer:** unit
**Acceptance criterion mapped:** Phase 1 validates all keys without state change
**Implemented by:** `tests/integration/iss202_merge_atomicity_test.zig` (`TC-ISS-202-01`)

### TC-ISS-202-02: Phase 1 fails on first invalid key; no state change, no events
**Given:** an instance with current variables and a merge request with mixed valid and invalid keys (first key invalid)
**When:** the merge is invoked and Phase 1 encounters the invalid key
**Then:** Phase 1 fails immediately, the instance status remains unchanged, no VARIABLE_OVERWRITTEN events are emitted, and variables are identical to pre-merge state
**Layer:** integration
**Acceptance criterion mapped:** Phase 1 failure prevents all state change; no partial application
**Implemented by:** `tests/integration/iss202_merge_atomicity_test.zig` (`TC-ISS-202-02`)

### TC-ISS-202-03: Phase 1 validates all keys before returning failure
**Given:** an instance with current variables and a merge request with multiple invalid keys
**When:** the merge is invoked during Phase 1
**Then:** all keys are validated before any failure is returned (Phase 1 is exhaustive, not early-exit after first key)
**Layer:** unit
**Acceptance criterion mapped:** Phase 1 validates all keys exhaustively
**Implemented by:** `tests/integration/iss202_merge_atomicity_test.zig` (`TC-ISS-202-03`)

### TC-ISS-202-04: Phase 2 applies all keys atomically after Phase 1 succeeds
**Given:** Phase 1 has succeeded with all keys validated
**When:** Phase 2 applies all output variables to the merged map
**Then:** all keys are applied simultaneously, VARIABLE_OVERWRITTEN events are emitted for overwritten keys, and the final merged state is correct
**Layer:** unit
**Acceptance criterion mapped:** Phase 2 applies all keys and emits events only on success
**Implemented by:** `tests/integration/iss202_merge_atomicity_test.zig` (`TC-ISS-202-04`)

### TC-ISS-202-05: Retry after Phase 1 failure preserves pre-merge state
**Given:** a merge has failed in Phase 1, leaving variables unchanged
**When:** the instance is read again after the failed merge
**Then:** variables are in the exact same state as before the failed merge attempt
**Layer:** integration
**Acceptance criterion mapped:** Failure preserves pre-merge state for safe retry
**Implemented by:** `tests/integration/iss202_merge_atomicity_test.zig` (`TC-ISS-202-05`)

### TC-ISS-202-06: Empty merge (zero keys) is a no-op
**Given:** a merge request with no keys (empty output_variables)
**When:** the merge is invoked
**Then:** the merge succeeds with no state change, no events are emitted, and variables remain unchanged
**Layer:** unit
**Acceptance criterion mapped:** Empty merge is safe and idempotent
**Implemented by:** `tests/integration/iss202_merge_atomicity_test.zig` (`TC-ISS-202-06`)

### TC-ISS-202-07: All keys already existing — all detected in Phase 1, applied in Phase 2
**Given:** all output keys already exist in current_vars with different values
**When:** the merge is invoked
**Then:** all collisions are detected in Phase 1, VARIABLE_OVERWRITTEN events are recorded, and all keys are atomically applied in Phase 2
**Layer:** unit
**Acceptance criterion mapped:** Collisions are detected and overwritten atomically
**Implemented by:** `tests/integration/iss202_merge_atomicity_test.zig` (`TC-ISS-202-07`)

### TC-ISS-202-08: Schema mismatch on key triggers Phase 1 failure
**Given:** an output key's value does not match the schema for that variable
**When:** Phase 1 validates the key
**Then:** validation fails, SchemaViolation error is returned, and no state is changed
**Layer:** integration
**Acceptance criterion mapped:** Schema validation failures are caught in Phase 1 before any state change
**Implemented by:** `tests/integration/iss202_merge_atomicity_test.zig` (`TC-ISS-202-08`)

### TC-ISS-202-09: Null value where schema requires non-null
**Given:** an output key has a null value but the schema requires non-null
**When:** Phase 1 validates the key
**Then:** validation fails with SchemaViolation, no state is changed
**Layer:** integration
**Acceptance criterion mapped:** Type mismatches are caught in Phase 1
**Implemented by:** `tests/integration/iss202_merge_atomicity_test.zig` (`TC-ISS-202-09`)

### TC-ISS-202-10: Memory allocation failure during merge
**Given:** a merge operation where memory allocation fails (simulated or actual resource exhaustion)
**When:** mergeVariables attempts to allocate memory for the event or merged map
**Then:** OutOfMemory error is returned, no state is changed, and the instance remains usable for retry
**Layer:** unit
**Acceptance criterion mapped:** OOM failure leaves no partial state
**Implemented by:** `tests/integration/iss202_merge_atomicity_test.zig` (`TC-ISS-202-10`)

### TC-ISS-202-INT-01: Transactional all-or-nothing merge with crash recovery
**Given:** an instance with current variables; Phase 1 succeeds, Phase 2 is about to apply changes
**When:** the process is killed before the transaction commits
**Then:** on restart, the instance remains in ERROR state with pre-merge variables; a retry with corrected input succeeds
**Layer:** integration
**Acceptance criterion mapped:** Crash recovery preserves atomicity
**Implemented by:** `tests/integration/iss202_merge_atomicity_test.zig` (`TC-ISS-202-INT-01`)

### TC-ISS-202-INT-02: Concurrent merge requests on same instance
**Given:** two concurrent requests to merge different keys into the same instance
**When:** both requests execute simultaneously
**Then:** one succeeds and one receives a conflict error (409 or similar); both eventually see the correct final state
**Layer:** integration
**Acceptance criterion mapped:** Concurrent merges are serialized; no lost updates
**Implemented by:** `tests/integration/iss202_merge_atomicity_test.zig` (`TC-ISS-202-INT-02`)

### TC-ISS-202-INT-03: Merge recovery after Phase 2 timeout
**Given:** Phase 1 succeeds but Phase 2 times out before the transaction commits
**When:** the instance is checked after timeout
**Then:** the instance is in ERROR state; a manual retry succeeds with corrected input
**Layer:** integration
**Acceptance criterion mapped:** Timeout does not leave partial state
**Implemented by:** `tests/integration/iss202_merge_atomicity_test.zig` (`TC-ISS-202-INT-03`)

## Execution Notes For TEST-RUNNER

- All integration tests run against real PostgreSQL via `BPM_TEST_DB_URL`.
- Unit tests verify pure logic (Phase 1 validation, Phase 2 application) without DB.
- All tests use per-test UUIDs for instance IDs to ensure isolation.
- Tests clean up instances explicitly (no cascading cleanup due to transaction scope).
- If `BPM_TEST_DB_URL` is absent, integration tests skip with clear message.
- No test.skip on any MUST test — all acceptance criteria are fully covered.
- No mocks, stubs, or in-memory fakes per DIRECTIVE T-1.
