## SH-01 — Token-based login

**Requirement:** The login screen MUST accept a bearer token, validate it via GET /health/ready, decode the JWT payload client-side, and navigate to the workspace on success; display an error message on failure.

---

### TC-SH01-01: Login page renders with token input
**Given:** The application is not authenticated  
**When:** The user navigates to `/login`  
**Then:** Screen shows a page with `data-testid="page-login"`, a `data-testid="login-token-input"` password field, and a `data-testid="login-submit"` button  
**Layer:** e2e  
**Acceptance criterion mapped:** Login screen accepts a bearer token input

---

### TC-SH01-02: Valid token login navigates to workspace
**Given:** The user is on the login page; GET /health/ready returns 200  
**When:** The user types a valid-looking JWT (with roles) into the token field and clicks Sign in  
**Then:** Screen shows the AppShell (sidebar with at least one nav link); the URL is no longer `/login`  
**Layer:** e2e  
**Acceptance criterion mapped:** Valid token + successful health check → workspace displayed

---

### TC-SH01-03: Invalid token (rejected by health endpoint) shows error
**Given:** The user is on the login page; GET /health/ready returns 401  
**When:** The user types any token and clicks Sign in  
**Then:** Screen shows `data-testid="login-error"` with text "Invalid token or access denied."  
**Layer:** e2e  
**Acceptance criterion mapped:** Failed health check → error message shown, user stays on login page

---

### TC-SH01-04: Empty token shows validation error
**Given:** The user is on the login page  
**When:** The user leaves the token field empty and clicks Sign in  
**Then:** Screen shows `data-testid="login-error"` with text "Please enter an API token."  
**Layer:** e2e  
**Acceptance criterion mapped:** Empty submit guarded client-side before any network call

---

### TC-SH01-U01: decodeTokenPayload returns payload for well-formed JWT
**Given:** A three-segment JWT where the middle segment is base64-encoded JSON  
**When:** `decodeTokenPayload(token)` is called  
**Then:** Returns the decoded payload object with correct fields  
**Layer:** unit  
**Acceptance criterion mapped:** Client-side JWT decode works correctly

---

### TC-SH01-U02: decodeTokenPayload returns null for two-segment token
**Given:** A string with only two dot-separated segments  
**When:** `decodeTokenPayload(token)` is called  
**Then:** Returns null (does not throw)  
**Layer:** unit  
**Acceptance criterion mapped:** Malformed token handled gracefully

---

### TC-SH01-U03: decodeTokenPayload returns null for more than three segments
**Given:** A string with four dot-separated segments  
**When:** `decodeTokenPayload(token)` is called  
**Then:** Returns null  
**Layer:** unit

---

### TC-SH01-U04: decodeTokenPayload returns null for invalid base64 in payload segment
**Given:** A three-segment token whose middle segment is not valid base64  
**When:** `decodeTokenPayload(token)` is called  
**Then:** Returns null (does not throw)  
**Layer:** unit

---

### TC-SH01-U05: decodeTokenPayload returns null when payload is valid base64 but invalid JSON
**Given:** A three-segment token whose middle segment decodes to a non-JSON string  
**When:** `decodeTokenPayload(token)` is called  
**Then:** Returns null (does not throw)  
**Layer:** unit

---

### TC-SH01-U06: decodeTokenPayload returns null for empty string
**Given:** An empty string  
**When:** `decodeTokenPayload("")` is called  
**Then:** Returns null  
**Layer:** unit

---

### TC-SH01-U07: decodeTokenPayload handles payload requiring base64 padding
**Given:** A JWT whose payload base64 string has length that is not a multiple of 4  
**When:** `decodeTokenPayload(token)` is called  
**Then:** Returns the correct payload (padding added internally)  
**Layer:** unit

## SH-02 — Session persistence and expiry

**Requirement:** The session token MUST be stored in-memory only (never localStorage/sessionStorage). On page reload the session MUST be gone and the user MUST be redirected to `/login`. On 401 response from any API call, the user MUST be redirected to `/login?reason=session-expired` and shown an expiry banner.

---

### TC-SH02-01: 401 API response triggers session-expired navigation
**Given:** The user has logged in successfully  
**When:** The `auth:session-expired` window event fires (simulating a 401 from any API call)  
**Then:** Screen shows `/login?reason=session-expired`; `data-testid="login-session-expired"` is visible with text "Your session has expired. Please log in again."  
**Layer:** e2e  
**Acceptance criterion mapped:** 401 → session cleared → /login?reason=session-expired banner shown

---

### TC-SH02-02: Navigating to /login?reason=session-expired shows expiry banner
**Given:** Any state  
**When:** The user navigates directly to `/login?reason=session-expired`  
**Then:** Screen shows `data-testid="login-session-expired"` with text "Your session has expired. Please log in again."  
**Layer:** e2e  
**Acceptance criterion mapped:** Banner renders from URL query param alone

---

## SH-03 — Role-aware navigation

**Requirement:** The sidebar navigation MUST show only the items permitted by the user's role(s). Items for unpermitted areas MUST NOT be rendered.

---

### TC-SH03-01: TASK_WORKER role sees only My Tasks
**Given:** The user logs in with roles `["TASK_WORKER"]`  
**When:** The AppShell is rendered  
**Then:** Screen shows exactly one nav link with text "My Tasks"; links "Instances", "Definitions", "DLQ", "Webhooks", "Users", "Groups", "Tokens", "Audit", "Health", "Metrics" are NOT in the DOM  
**Layer:** e2e  
**Acceptance criterion mapped:** TASK_WORKER sees only My Tasks

---

### TC-SH03-02: PLATFORM_ADMIN sees all 11 nav items
**Given:** The user logs in with roles `["PLATFORM_ADMIN"]`  
**When:** The AppShell is rendered  
**Then:** Screen shows exactly 11 nav links: Instances, My Tasks, Definitions, DLQ, Webhooks, Users, Groups, Tokens, Audit, Health, Metrics  
**Layer:** e2e  
**Acceptance criterion mapped:** PLATFORM_ADMIN has full navigation access

---

### TC-SH03-03: PROCESS_DESIGNER sees Instances and Definitions only
**Given:** The user logs in with roles `["PROCESS_DESIGNER"]`  
**When:** The AppShell is rendered  
**Then:** Screen shows nav links "Instances" and "Definitions"; links "My Tasks", "DLQ", "Webhooks" and all admin items are NOT in the DOM  
**Layer:** e2e  
**Acceptance criterion mapped:** PROCESS_DESIGNER scoped to process design views only

---

## SH-04 — Active user indicator

**Requirement:** The sidebar header MUST display the authenticated user's display name and role(s). A logout button MUST be present and MUST clear the session and navigate to /login.

---

### TC-SH04-01: User display name shown in sidebar header
**Given:** The user logs in with `display_name: "Alice Smith"` in the JWT  
**When:** The AppShell is rendered  
**Then:** `data-testid="user-display-name"` shows text "Alice Smith"  
**Layer:** e2e  
**Acceptance criterion mapped:** display_name from JWT shown in header

---

### TC-SH04-02: User roles shown in sidebar header
**Given:** The user logs in with `roles: ["PROCESS_DESIGNER"]` in the JWT  
**When:** The AppShell is rendered  
**Then:** `data-testid="user-roles"` shows text containing "PROCESS_DESIGNER"  
**Layer:** e2e  
**Acceptance criterion mapped:** Roles from JWT shown in header

---

### TC-SH04-03: Logout button clears session and navigates to /login
**Given:** The user is logged in and on the AppShell  
**When:** The user clicks `data-testid="logout-button"`  
**Then:** Screen shows the login page (`data-testid="page-login"`); URL is `/login`  
**Layer:** e2e  
**Acceptance criterion mapped:** Logout clears in-memory session

---

### TC-SH04-U01: resolveDisplayName returns display_name when present
**Given:** JwtPayload with `display_name: "Alice Bob"`  
**When:** `resolveDisplayName(payload)` is called  
**Then:** Returns `"Alice Bob"`  
**Layer:** unit

---

### TC-SH04-U02: resolveDisplayName falls back to name
**Given:** JwtPayload with `name: "Bob"` but no `display_name`  
**When:** `resolveDisplayName(payload)` is called  
**Then:** Returns `"Bob"`  
**Layer:** unit

---

### TC-SH04-U03: resolveDisplayName falls back to preferred_username
**Given:** JwtPayload with `preferred_username: "bsmith"` but no `display_name` or `name`  
**When:** `resolveDisplayName(payload)` is called  
**Then:** Returns `"bsmith"`  
**Layer:** unit

---

### TC-SH04-U04: resolveDisplayName falls back to sub
**Given:** JwtPayload with only `sub: "user-uuid-001"` and `roles: []`  
**When:** `resolveDisplayName(payload)` is called  
**Then:** Returns `"user-uuid-001"`  
**Layer:** unit

---

### TC-SH04-U05: resolveDisplayName returns "Unknown User" when all fields absent
**Given:** JwtPayload with no `display_name`, `name`, `preferred_username`, or `sub`  
**When:** `resolveDisplayName(payload)` is called  
**Then:** Returns `"Unknown User"`  
**Layer:** unit
