# Test Spec: EXP-202 - Entity Command API Event Family

Requirement: EXP-202 - Entity command API -> ENTITY_RECORD_CREATED/UPDATED/DELETED event family
Priority: MUST
Test layer: integration

## Test Cases

### TC-EXP-202-01: create record writes latest projection row
Given: an ACTIVE entity definition and valid record payload
When: createRecord is called with a unique idempotency key
Then: a record is returned and entity_record_latest contains tenant_id, entity_type, and JSON state
Layer: integration
Acceptance criterion mapped: CREATE command path persists entity projection state

### TC-EXP-202-02: update record increments version sequence and updates state
Given: an existing entity record in entity_record_latest
When: updateRecord is called with modified field_values and unique idempotency key
Then: record state is updated and version_seq is greater than prior value
Layer: integration
Acceptance criterion mapped: UPDATE command path persists modified projection state

### TC-EXP-202-03: delete record marks projection row as deleted
Given: an existing entity record in entity_record_latest
When: deleteRecord is called with unique idempotency key
Then: entity_record_latest row is retained and deleted_at is set
Layer: integration
Acceptance criterion mapped: DELETE command path emits event and marks latest projection deleted

### TC-EXP-202-04: idempotent replay returns original record
Given: an existing entity record created via createRecord with idempotency_key K
When: createRecord is called again with the same idempotency_key K (any payload)
Then: the call returns is_duplicate=true with the ORIGINAL record_id; only one row exists in entity_record_latest
Layer: integration
Acceptance criterion mapped: Idempotent replay collapses to original record

### TC-EXP-202-05: idempotent replay does not exhaust pool (ISS-0187 regression)
Given: a Pool configured with pool_size=1 (saturated) and an entity definition with one existing record created with idempotency_key K
When: createRecord is called two MORE times with the same idempotency_key K on the saturated pool
Then: every call succeeds (no StoreError.PoolExhausted); each non-first call returns is_duplicate=true with the ORIGINAL record_id; exactly one row exists in entity_record_latest across all three appends
Layer: integration
Acceptance criterion mapped: Store.append must reuse its held connection for duplicate-lookups instead of acquiring a second pool connection (ISS-0187 / GH #521 — regression test for the nested-acquire pool-exhaustion bug)
Regression: pre-fix the second createRecord returned StoreError.PoolExhausted because the duplicate-detection path acquired a second pool connection while the first was still held by defer release
