# Test Spec: TD-UI-01, TD-UI-02, TD-UI-03 — Per-Tenant Dashboard & Identity Indicator

**Requirements:**
- TD-UI-01 — Tenant-scoped landing page `[MUST]`
- TD-UI-02 — Tenant identity indicator `[MUST]`
- TD-UI-03 — Tenant realm routing `[SHOULD]`

**Priority:** TD-UI-01 MUST · TD-UI-02 MUST · TD-UI-03 SHOULD  
**Test layer:** e2e (Playwright, real backend — no mocks, no MSW)  
**Source file:** `web/tests/e2e/tenant-dashboard.e2e.spec.ts`

---

## Context

After WF-01 the three requirements were finalised:

- **TD-UI-01** — After OIDC login the dashboard **MUST** display the tenant `display_name` as a heading. All data tiles are scoped to the authenticated tenant. An "Unknown workspace" fallback banner MUST appear when the display name cannot be resolved.
- **TD-UI-02** — Every authenticated route **MUST** show the tenant `display_name` in the sidebar/header area. The indicator MUST NOT appear on unauthenticated routes or after logout.
- **TD-UI-03** — The frontend **SHOULD** resolve the tenant context automatically from the token's `iss` claim without presenting a manual "choose organisation" step.

The implementation exposes the following `data-testid` attributes (from the FRONTEND-DEV commit):

| Element | `data-testid` | Condition |
|---|---|---|
| Dashboard `<h1>` | `tenant-dashboard-heading` | Always on `/dashboard` |
| Sidebar tenant label | `tenant-display-name` | `isUnknown === false` |
| Sidebar tenant label (fallback) | `tenant-display-name-unknown` | `isUnknown === true` |
| Unknown-workspace banner | `tenant-unknown-banner` | `isUnknown === true` |
| Sign-out button | `logout-button` | Always in AppShell |
| User display name | `user-display-name` | Always in AppShell |

## Test Cases

### TC-TD-UI-01-01: Dashboard heading shows tenant `display_name` after login

**Given:** Admin user authenticated against `bpm-default` realm; tenant `default` exists in the database with `display_name = 'Default Tenant'`.  
**When:** User navigates to `/dashboard`.  
**Then:** The element `data-testid="tenant-dashboard-heading"` is visible and contains the tenant `display_name` fetched from `GET /api/v1/tenants/default`.  
**Layer:** e2e  
**Screenshot verdict:** Screen shows "Default Tenant" (or the actual `display_name`) in the page `<h1>` heading immediately after navigation to `/dashboard`. No "choose organisation" dialog is visible.  
**Acceptance criterion mapped:** TD-UI-01 AC1 — Playwright screenshot after OIDC login shows tenant `display_name` as a heading.

---

### TC-TD-UI-01-02: Unknown workspace fallback banner when `tenant_display_name` is absent

**Given:** Admin user authenticated, but session `tenant_display_name` field is `null` (simulating a tenant whose name cannot be resolved — e.g. incomplete provisioning).  
**When:** User navigates to `/dashboard`.  
**Then:** `data-testid="tenant-dashboard-heading"` contains `"Unknown workspace"` and `data-testid="tenant-unknown-banner"` is visible with a message indicating the name could not be loaded. `data-testid="tenant-display-name-unknown"` is visible in the sidebar (not `tenant-display-name`).  
**Layer:** e2e  
**Screenshot verdict:** Screen shows "Unknown workspace" heading and an amber warning banner — not a blank page or unhandled error.  
**Acceptance criterion mapped:** TD-UI-01 (implicit fallback requirement from the implementation's `isUnknown` guard).

---

### TC-TD-UI-02-01: Tenant `display_name` visible in sidebar on multiple authenticated routes

**Given:** Admin user authenticated with `tenant_display_name = 'Default Tenant'`.  
**When:** User navigates to `/instances`, then to `/definitions`.  
**Then:** On each route, `data-testid="tenant-display-name"` is visible in the sidebar and contains the tenant `display_name`.  
**Layer:** e2e  
**Screenshot verdict (per route):**
- Screen at `/instances` shows tenant name in sidebar.
- Screen at `/definitions` shows tenant name in sidebar.  
**Acceptance criterion mapped:** TD-UI-02 AC1 — Playwright screenshot from any authenticated route shows the tenant `display_name` in the nav/header region.

---

### TC-TD-UI-02-02: Tenant `display_name` cleared from sidebar after logout

**Given:** Admin user authenticated with `tenant_display_name` set and visible in the sidebar.  
**When:** User clicks `data-testid="logout-button"`.  
**Then:** The browser navigates to the Keycloak end-session endpoint (`openid-connect/logout`). After the navigation, the app's `data-testid="tenant-display-name"` element is no longer accessible (the BPM application shell is no longer rendered).  
**Layer:** e2e  
**Screenshot verdict:**
- Screenshot **before** logout: sidebar shows `data-testid="tenant-display-name"` with the tenant name.
- Screenshot **after** logout click: page is no longer the BPM app — no `tenant-display-name` element present.  
**Acceptance criterion mapped:** TD-UI-02 AC3 — After logout, the login screen screenshot does NOT show the tenant name.

---

### TC-TD-UI-03-01: No "choose organisation" prompt after login with known tenant context

**Given:** Admin token is obtained from `bpm-default` realm. The SwiftRoute tenant (`slug = 'swiftroute'`) exists in the database (fetched via `GET /api/v1/tenants/swiftroute`). A session is injected with `tenant_slug = 'swiftroute'` and `tenant_display_name` from the API response.  
**When:** User lands on `/dashboard`.  
**Then:** The tenant name is shown in the heading and sidebar. No "choose organisation", "select tenant", or "choose your workspace" prompt or dialog is visible at any point.  
**Layer:** e2e  
**Screenshot verdict:** Screen at `/dashboard` shows SwiftRoute's `display_name` as the page heading. No selection dialog or organisation-picker element is visible.  
**Acceptance criterion mapped:** TD-UI-03 AC1 — After OIDC login via a tenant realm, no manual tenant selection step is presented. TD-UI-03 AC3 — Correct tenant display name shown with no generic placeholder.  
**Prerequisite:** The `swiftroute` tenant must exist in `bpm_test`. If `GET /api/v1/tenants/swiftroute` returns 404, the test fails with a clear error (not a silent skip) indicating that the tenant onboarding must be run first.
