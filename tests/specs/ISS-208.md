## Test Cases

### TC1: cancel instance then complete task → 409, no events appended

**Precondition:**
1. Create a process definition and instance (ACTIVE status).
2. Create a task row with status=PENDING for that instance.
3. Cancel the instance: `UPDATE instance_projections SET status='CANCELLED'`.

**Action:** Call `InstanceStore.completeTask(task_id, output_variables_json)`.

**Expected:**
- Returns `CompleteTaskError.InstanceNotActive`.
- HTTP equivalent: `409 INSTANCE_NOT_ACTIVE`.
- No new rows in `events` table for this instance.
- Task row status unchanged (still PENDING).
- Instance remains CANCELLED.

---

### TC2: concurrent cancel + complete (two connections, one wins) → correct outcome

**Precondition:**
1. Create instance (ACTIVE) with one PENDING task.
2. Connection A: BEGIN; SELECT ... FOR UPDATE on instance_projections (hold lock).

**Action:**
- Connection B: attempt to complete the task (should block on FOR UPDATE, then see CANCELLED).
- Connection A: cancel the instance (UPDATE status='CANCELLED'); COMMIT.
- Connection B: unblocks, reads CANCELLED status → returns InstanceNotActive.

**Expected:**
- Connection B receives `InstanceNotActive`.
- No events appended by connection B.
- Instance is CANCELLED.

## Test Infrastructure

- Real PostgreSQL via `BPM_TEST_DB_URL`.
- Per-test UUIDs for instance_id, task_id, definition_id.
- Each test block creates its own fixtures and cleans up via `defer`.
- No mocks or stubs.
- TC2 uses two separate DB connections to simulate the race.
- If `BPM_TEST_DB_URL` is absent, all tests skip cleanly.
