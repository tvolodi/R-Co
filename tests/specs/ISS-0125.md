# Test Spec: ISS-0125 — FK cascade ordering

**Requirement:** ISS-0125 / GitHub #391 — deleting a process definition must cascade to definition snapshots, migration DDL must be re-applicable, and cleanup SQL errors must be visible.  
**Priority:** MUST  
**Test layer:** integration (real PostgreSQL via `BPM_TEST_DB_URL`)

## Test Cases

### TC-ISS-0125-01: FK catalog reports ON DELETE CASCADE
**Given:** Migration `1106_iss0125_instance_definition_snapshots_cascade.sql` has been applied to the active tenant schema by `TestHarness.init`.  
**When:** PostgreSQL `pg_constraint` is queried with a `pg_namespace` join for the foreign key on `instance_definition_snapshots`.  
**Then:** Exactly one foreign key is found in the active schema and its `confdeltype` is `c` (CASCADE).  
**Layer:** integration  
**Acceptance criterion mapped:** The migrated FK is schema-scoped and enforces cascading deletes.

### TC-ISS-0125-02: Parent deletion removes definition snapshot
**Given:** Per-test UUIDs identify a `process_definitions` parent and a referencing `instance_definition_snapshots` child inside the test transaction.  
**When:** The parent is deleted with a parameterised `DELETE FROM process_definitions WHERE id = $1::uuid`.  
**Then:** The delete succeeds without C23503 and the child count for `definition_id = $1::uuid` is zero.  
**Layer:** integration  
**Acceptance criterion mapped:** Database-level ownership removes dependent snapshots automatically.

### TC-ISS-0125-03: Migration ALTER body is idempotent
**Given:** The migrated foreign key exists in the active tenant schema.  
**When:** The migration's `DROP CONSTRAINT IF EXISTS` and `ADD CONSTRAINT ... ON DELETE CASCADE` statements are executed twice inside the isolated test transaction.  
**Then:** Both applications complete successfully and catalog introspection still reports exactly one CASCADE foreign key.  
**Layer:** integration  
**Acceptance criterion mapped:** The corrective DDL can reconcile schema drift repeatedly without duplicate-constraint failure.

### TC-ISS-0125-04: Cleanup helper propagates SQL errors
**Given:** `helpers.zig` exposes the ISS-0125 child-cleanup helper and a transaction-local trigger forces deletion from `instance_definition_snapshots` to fail.  
**When:** The helper attempts the child delete.  
**Then:** The PostgreSQL error is returned to the caller; it is not swallowed and execution cannot silently continue to parent cleanup.  
**Layer:** integration  
**Acceptance criterion mapped:** Cleanup failures are fail-fast and diagnosable.

## Isolation and security contract

- Each test initializes `TestHarness` and rolls its transaction back with `defer h.deinit()`.
- Fixture identifiers are generated per test with `std.crypto.random`.
- Missing `BPM_TEST_DB_URL` returns the explicit `error.MissingTestDatabaseUrl`; no test is skipped.
- All fixture SQL uses PostgreSQL placeholders; no SQL values are interpolated.
- No mocks, stubs, in-memory database, or `error.SkipZigTest` are used.
