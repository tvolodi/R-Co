# Test Spec: EE-12 — Concurrent Instance Safety

**Requirement ID:** EE-12  
**Requirement text:** Multiple process instances SHALL execute concurrently without interference.  
All instance state transitions MUST be isolated by row-level locking; cross-instance
contention MUST NOT occur. Concurrent task-completion requests on the same instance MUST
result in at most one success and exactly one `ConcurrentModification` (HTTP 409) response.

**Priority:** MUST  
**Test layer:** integration (real PostgreSQL via `BPM_TEST_DB_URL`)  
**Source file:** `tests/integration/concurrent_instances_test.zig`

---

## Acceptance Criteria

| # | Criterion |
|---|-----------|
| AC-1 | 100 instances running simultaneously produce no state corruption. |
| AC-2 | Row-level locking is per-instance; zero cross-instance contention. |
| AC-3 | Two concurrent completion requests on the same instance: exactly one succeeds and the other receives `ConcurrentModification`. |
| AC-4 | Load scenario: 100 concurrent completions across 100 distinct instances all succeed without deadlock. |

---

## Test Cases

### TC-EE-12-01: 100 concurrent task completions on distinct instances all succeed

| Field | Value |
|-------|-------|
| **ID** | TC-EE-12-01 |
| **Layer** | integration |
| **Criteria** | AC-1, AC-4 |
| **Setup** | 100 process instances created; each has one PENDING task inserted via raw SQL. |

**Steps:**

1. Create 100 distinct process instances via `InstanceStore.create()`.
2. For each instance, insert one token into `tokens` and one PENDING task into `tasks` via raw SQL.
3. Launch 100 threads; each thread calls `InstanceStore.completeTask()` for its own unique task.
4. Join all threads.

**Expected result:**

- All 100 `completeTask()` calls succeed (return without error).
- All 100 instances have `status = 'COMPLETED'` in `instance_projections`.
- No thread stores a non-nil failure.
- Test completes without deadlock (no indefinite blocking).

**Would fail if:** any instance's state transition corrupts another instance, or if locking
causes a deadlock across distinct rows.

### TC-EE-12-02: Concurrent completions on same instance — one succeeds, one ConcurrentModification

| Field | Value |
|-------|-------|
| **ID** | TC-EE-12-02 |
| **Layer** | integration |
| **Criteria** | AC-3 |
| **Setup** | 1 process instance with 1 PENDING task. |

**Steps:**

1. Create one process instance; insert one token and one PENDING task via raw SQL.
2. Main thread acquires a pool connection and holds an explicit `FOR UPDATE NOWAIT` lock
   on the `instance_projections` row (inside an open transaction).
3. Spawn a worker thread that calls `InstanceStore.completeTask()` for the same task.
4. Join the worker thread.
5. Assert that the worker received exactly `CompleteTaskError.ConcurrentModification`.
6. Main thread rolls back the open transaction (releasing the lock).
7. Main thread calls `InstanceStore.completeTask()` for the same task.

**Expected result:**

- Worker thread returns `CompleteTaskError.ConcurrentModification`.
- After rollback, main thread's `completeTask()` succeeds.
- Instance status is `COMPLETED`.

**Would fail if:** `FOR UPDATE NOWAIT` does not raise SQLSTATE 55P03, or the error is not
mapped to `ConcurrentModification`, or both calls succeed (double-complete).

### TC-EE-12-03: No deadlock — 100 concurrent distinct-instance completions finish within timeout

| Field | Value |
|-------|-------|
| **ID** | TC-EE-12-03 |
| **Layer** | integration |
| **Criteria** | AC-4 |

**Note:** This criterion is verified implicitly by TC-EE-12-01. A test that hangs would time
out and be reported as a failure, proving absence of deadlock. No separate test case is
required; TC-EE-12-01 covers it.

### TC-EE-12-04: `ConcurrentModification` is the exact error variant on lock contention

| Field | Value |
|-------|-------|
| **ID** | TC-EE-12-04 |
| **Layer** | integration |
| **Criteria** | AC-3 |

**Note:** This is the same scenario as TC-EE-12-02. The test explicitly
`expectEqual(CompleteTaskError.ConcurrentModification, worker_result)`, verifying that the
SQLSTATE 55P03 from PostgreSQL is mapped to the named error variant used by the API layer
(`tasks.zig handleComplete` maps it to HTTP 409 `CONCURRENT_MODIFICATION`). Covered by the
same test function as TC-EE-12-02.

## Implementation notes

- Tests skip automatically if `BPM_TEST_DB_URL` is not set (returns `SkipZigTest`).
- Each test creates and cleans up its own data in FK order:
  `tasks` → (tokens cascade from `instance_projections`) → `instance_definition_snapshots`
  → `instance_projections` → `process_definitions`.
- Thread-local `std.heap.ArenaAllocator` backed by `std.heap.page_allocator` is used for
  per-thread allocations to avoid races on `std.testing.allocator`.
- `InstanceStore.completeTask()` maps SQLSTATE 55P03 (`lock_not_available`) to
  `CompleteTaskError.ConcurrentModification` at the `FOR UPDATE NOWAIT` query site.
