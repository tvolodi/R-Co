## PD-UI-01 — Definition list

**Requirement:** The definitions view MUST display a paginated, searchable table of all process definitions showing: name, latest version, status badge (DRAFT / ACTIVE / DEPRECATED / ARCHIVED), and creation date.

---

### TC-PDUI01-01: Definition list shows definitions from the backend

**Given:** One or more process definitions exist for the current tenant
**When:** A PROCESS_DESIGNER user navigates to `/definitions`
**Then:** Screen shows a `DataTable` containing rows with definition name, version number, status badge, and creation date
**Layer:** e2e
**Acceptance criterion mapped:** Paginated table with name, version, status badge, and creation date

---

### TC-PDUI01-02: Empty state renders when no definitions exist

**Given:** No process definitions exist for the current tenant
**When:** A PROCESS_DESIGNER user navigates to `/definitions`
**Then:** Screen shows "No definitions found" empty message
**Layer:** e2e
**Acceptance criterion mapped:** Empty state handled gracefully

---

### TC-PDUI01-03: Search input filters definitions by name

**Given:** Multiple definitions exist with different names
**When:** The user types a search query in the search bar
**Then:** The definition list updates to show only definitions whose name matches the query; the search parameter is reflected in the URL
**Layer:** e2e
**Acceptance criterion mapped:** Searchable table

---

### TC-PDUI01-04: Pagination controls are present with many definitions

**Given:** More than `pageSize` definitions exist
**When:** The user navigates to `/definitions`
**Then:** Screen shows pagination controls (Next page) and definitions are split across pages
**Layer:** e2e
**Acceptance criterion mapped:** Paginated table

---

## PD-UI-02 — Status filter

**Requirement:** The list MUST support filtering by status (multi-select). The active filter MUST be reflected in the URL query string and survive page reload.

---

### TC-PDUI02-01: Status filter shows all options in the dropdown

**Given:** The definition list page is displayed
**When:** The user opens the status filter drop-down
**Then:** Screen shows four filter options: "Draft", "Active", "Deprecated", "Archived"
**Layer:** e2e
**Acceptance criterion mapped:** Multi-select status filter present

---

### TC-PDUI02-02: Selecting a single status filter shows only matching definitions

**Given:** Definitions with different statuses exist
**When:** The user selects "Draft" in the status filter
**Then:** Only DRAFT definitions appear in the table; the URL contains `?status=DRAFT`
**Layer:** e2e
**Acceptance criterion mapped:** Filter by status, URL-persisted

---

### TC-PDUI02-03: Selecting multiple statuses filters by all selected

**Given:** Definitions with DRAFT and ACTIVE statuses exist
**When:** The user selects "Draft" and "Active" in the status filter
**Then:** Both DRAFT and ACTIVE definitions appear; the URL contains `?status=DRAFT,ACTIVE`
**Layer:** e2e
**Acceptance criterion mapped:** Multi-select filter works with multiple values

---

### TC-PDUI02-04: Status filter survives page reload

**Given:** The user has selected "Draft" as the status filter
**When:** The user reloads the page
**Then:** The status filter is still set to "Draft"; only DRAFT definitions are shown; the URL contains `?status=DRAFT`
**Layer:** e2e
**Acceptance criterion mapped:** Filter survives page reload (URL-persisted)

---

### TC-PDUI02-05: Clearing all status filters shows all definitions

**Given:** A status filter is active
**When:** The user clears all selected statuses
**Then:** All definitions are shown; the URL no longer contains the `status` parameter
**Layer:** e2e
**Acceptance criterion mapped:** Clearing filter restores full list

---

## PD-UI-03 — Version history

**Requirement:** Clicking a definition name MUST expand an inline version history row showing all versions for that name, each with its status and a link to open that version.

---

### TC-PDUI03-01: Clicking a definition name expands its version history row

**Given:** A definition with at least one version exists
**When:** The user clicks the definition name in the table
**Then:** An inline version history row expands below the definition row, showing: the "Version history: <name>" heading, at least one version row with version number, status badge, creation date, and an "Open" link
**Layer:** e2e
**Acceptance criterion mapped:** Expandable version history row

---

### TC-PDUI03-02: Version history shows multiple versions for the same name

**Given:** A definition name has multiple versions (e.g., 1.0.0 and 2.0.0)
**When:** The user expands the version history for that name
**Then:** All versions are listed with their respective statuses; each row has a unique `data-testid="version-row-{version}"`
**Layer:** e2e
**Acceptance criterion mapped:** All versions for that name displayed

---

### TC-PDUI03-03: "Open" link navigates to the definition detail page

**Given:** A version history row is expanded
**When:** The user clicks the "Open" link for a version
**Then:** The browser navigates to `/definitions/{id}` for that version
**Layer:** e2e
**Acceptance criterion mapped:** Open link navigates to definition detail

---

### TC-PDUI03-04: Clicking the same name again collapses the version history

**Given:** A version history row is expanded
**When:** The user clicks the same definition name again
**Then:** The version history row is no longer visible
**Layer:** e2e
**Acceptance criterion mapped:** Toggle expand/collapse

---

### TC-PDUI03-05: Loading state shows skeleton rows

**Given:** The definition list page is displayed
**When:** The user clicks a definition name and versions are loading
**Then:** Skeleton/animated placeholder rows are shown while loading
**Layer:** e2e
**Acceptance criterion mapped:** Loading state visual feedback

---

## PD-UI-04 — Create definition

**Requirement:** A "New Definition" button MUST open a form modal for entering name, version string, and description. On submit, it calls `POST /definitions` and navigates to the Process Designer canvas for the new DRAFT.

---

### TC-PDUI04-01: "New Definition" button opens create dialog

**Given:** The definition list page is displayed
**When:** The user clicks the "New Definition" button (`data-testid="btn-new-definition"`)
**Then:** Screen shows a dialog (`data-testid="create-definition-dialog"`) with a title "Create New Definition", and form fields for Name, Version, and Description
**Layer:** e2e
**Acceptance criterion mapped:** New Definition button opens dialog

---

### TC-PDUI04-02: Dialog form validates required fields

**Given:** The create dialog is open
**When:** The user clicks "Create Definition" with an empty Name field
**Then:** Screen shows inline validation error "Name is required" on the name field
**Layer:** e2e
**Acceptance criterion mapped:** Client-side validation on required fields

---

### TC-PDUI04-03: Creating a definition succeeds and navigates to the editor

**Given:** The create dialog is open with valid form data
**When:** The user fills Name, Version, and optional Description, then clicks "Create Definition"
**Then:** The dialog closes; the browser navigates to `/definitions/{id}` (the new definition's editor page); a new DRAFT definition is created in the backend
**Layer:** e2e
**Acceptance criterion mapped:** POST /definitions succeeds and navigates to canvas

---

### TC-PDUI04-04: Duplicate name+version shows conflict error

**Given:** A definition with name "Test Flow" and version "1.0.0" already exists
**When:** The user attempts to create another definition with the same name and version
**Then:** Screen shows an inline error "A definition with this name and version already exists."
**Layer:** e2e
**Acceptance criterion mapped:** HTTP 409 handled gracefully with inline error

---

### TC-PDUI04-05: Cancel and Close buttons dismiss the dialog

**Given:** The create dialog is open
**When:** The user clicks the Cancel button (data-testid="create-cancel") or the dialog Close (×) button
**Then:** The dialog closes; user remains on `/definitions`; no definition was created
**Layer:** e2e
**Acceptance criterion mapped:** Dialog dismissible without action

---

### TC-PDUI04-06: Discard changes confirmation shown when form is dirty

**Given:** The create dialog is open and the user has started filling the form
**When:** The user clicks Cancel
**Then:** A browser confirmation dialog ("Discard changes?") is shown; if confirmed, the dialog closes; if cancelled, the dialog stays open
**Layer:** e2e
**Acceptance criterion mapped:** Unload prevention for dirty form
