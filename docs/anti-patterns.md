# BPM Platform — Anti-Patterns Catalogue

**Purpose:** A living record of mistakes encountered in pipelines and their correct alternatives.  
**Updated by:** `ISSUE-FIXER` and `DOC-UPDATER` after each resolved issue.  
**Format:** Each entry has the anti-pattern, what went wrong, and the correct approach.

---

## How to use this file

Before implementing anything, search this file for the module or pattern you are about to use. If your approach matches an entry in the **Anti-Pattern** column, use the **Correct Approach** instead without attempting the anti-pattern first.

## Automated checks

Several of the anti-patterns below are now enforced by linters under `tools/`. Run them as part of self-review or in CI:

| Linter | Catches |
|---|---|
| `python3 tools/lint_design_artefact.py <file>` | Schema-qualified table names, oversized code blocks, malformed requirement IDs, real assertions in CUSTOM blocks, migration-number collisions, Lego YAML schema violations |
| `python3 tools/lint_frontend_conventions.py` | Raw `fetch`/`axios` outside `web/src/api/client.ts`, MSW / `axios-mock-adapter` references, inline query keys, `test.skip` in Playwright specs, role-gated `disabled` instead of hidden |
| `python3 tools/lint_test_isolation.py` | Hardcoded UUIDs, module-level mutable `var` in integration tests, allocations without `defer` cleanup, `error.SkipZigTest` on tests that cover a requirement, missing `BPM_TEST_DB_URL` reference |

A linter emits BLOCKER for "design or test is broken" issues, MAJOR for "fix before merge", MINOR for "cosmetic". CODE-DESIGN-VALIDATOR and TEST-DESIGN-VALIDATOR run these gates before passing handoffs downstream.

See also `templates/lego-catalog.md` for the standard-pattern templates that lower-capability models should instantiate instead of re-deriving from prose.

## Backend (Zig)

| Anti-Pattern | Consequence | Correct Approach |
|---|---|---|
| `catch unreachable` on realistic failure paths (DB errors, I/O) | Panics in production on normal error conditions | Use typed error sets; propagate with `!` or return the error |
| SQL string interpolation (`std.fmt.allocPrint` + query) | SQL injection vulnerability | Always use `$1`, `$2` placeholders via `pg.zig` prepared statements |
| I/O inside `src/engine/transition.zig` | Breaks pure-function contract; untestable without a database | All I/O belongs in the handler layer; transition functions receive data, not connections |
| Global error set across all modules | Error types become meaningless; callers cannot match them | Per-module error sets defined in each module's root file |
| `zig build test` to validate a single module fix | Runs the entire test suite; slow feedback loop | `zig build test-<module>` for focused validation |

## Database / Migrations

### Anti-pattern: legacy table name in source/test after migration rename

- **Symptom:** PostgreSQL C42703 `column does not exist` or `relation does not exist` after a migration renames a table.
- **Detection:** `tools/lint_sql_table_refs.py` scans `src/**/*.zig` and `tests/integration/**/*.zig` for legacy table names.
- **Prevention:** When renaming a table in a migration, update every reference in `src/` and `tests/` in the **same commit**. The linter fails the build if any legacy reference returns.

| Anti-Pattern | Consequence | Correct Approach |
|---|---|---|
| Schema-qualified names in migrations (`public.table_name`) | Migration fails if `search_path` differs between environments | Use unqualified table names; let `search_path` resolve |
| `DROP TABLE` or `DROP COLUMN` in a migration without a matching data-preservation migration | Irreversible data loss in production | Only append-only migrations; schema removals require an explicit archival step first |
| Checking `information_schema.tables` without `AND table_schema = 'public'` | False positives from shadow tables in other schemas | Always filter by `table_schema` |
| Guarding a migration's `DO` block with `to_regclass('some_table') IS NULL` to detect a prerequisite, when that prerequisite only exists under a per-tenant schema (not `public`) | The guard's implicit `search_path` at migration-apply time may not include the tenant schema, so `to_regclass` returns NULL even though the table exists elsewhere — the guard silently no-ops and the migration is marked applied without ever running its body (see [GitHub #335](https://github.com/tvolodi/R-Co/issues/335) / ISS-0076: `GBL-100_exp501_secrets.sql` never created the `secrets` table because its guard checked `instance_projections`, which only exists under `tenant_default`) | Query `pg_tables`/`pg_namespace` explicitly with the target schema, or set `search_path` explicitly inside the `DO` block before calling `to_regclass`; never rely on the ambient search_path for a prerequisite check in a multi-schema (per-tenant) database |
| Writing unqualified SQL in an integration test that exercises a GBL-prefixed (public-only) migration's effect, while the test connection's `search_path` is `tenant_default,public` (the `TestHarness` default) | The unqualified table name silently resolves to the `tenant_default` copy of a same-named table instead of `public` — since GBL migrations never apply to tenant schemas, that copy never received the DDL under test, so the test fails with a missing-column/missing-behavior error that looks like a migration bug but is actually a test wired to the wrong schema (see [GitHub #338](https://github.com/tvolodi/R-Co/issues/338) / ISS-0089: `svc01_service_catalog_scope_test.zig` inserted into `tenant_default.service_catalog`, which lacks the `scope`/`owner_tenant_id` columns GBL-078 added only to `public.service_catalog`) | When a test's purpose is to verify a GBL-prefixed migration's effect, either open a direct `public`-schema connection or explicitly schema-qualify every reference (`public.<table>`) rather than relying on `TestHarness`'s tenant-first `search_path` |
| Hard-coding table names as string literals in test cleanup/reset tooling (`tools/clean_test_db.py`, `resetTestData()` in `tests/integration/helpers.zig`) with no validation against the live schema | A later migration renames or drops the table (e.g. TNT-01's `GBL-073` rename/drop pass) and the cleanup call silently starts failing with "relation does not exist" — caught by the same best-effort error handling meant to tolerate partial-migration states, so the stale reference produces log noise forever instead of a build-time or test-time failure, and the real intended cleanup silently stops happening (see [GitHub #337](https://github.com/tvolodi/R-Co/issues/337) / ISS-0088: `process_events`, `event_store`, and `dlq` referenced in cleanup code years after being renamed to `events`/`dead_letter_items` or removed entirely) | When a migration renames or drops a table, grep `tools/` and `tests/integration/helpers.zig` for the old name as part of that same change; consider a CI check that validates cleanup-script table names against the live schema |
| Writing `CREATE FUNCTION`/`CREATE TRIGGER` in a migration without `CREATE OR REPLACE` or an existence guard, on the assumption the target database is always in a pristine pre-migration state | Re-running the statement against a long-lived, never-reset test database (where the function/trigger was already created by a prior session) throws `already exists` instead of succeeding — accumulates as permanent noise/failures on any shared, long-lived `bpm_test` container instead of being idempotent like the rest of the migration (see [GitHub #339](https://github.com/tvolodi/R-Co/issues/339) / ISS-0090, formal filing of the previously-dangling `ISS-503-INFRA-01`) | Use `CREATE OR REPLACE FUNCTION`; guard `CREATE TRIGGER` with a `DROP TRIGGER IF EXISTS` first or a `pg_trigger` existence check, matching the idempotency already required of `CREATE TABLE`/`CREATE INDEX` statements elsewhere in this migration set |
| A content-scanning lint tool (e.g. `tools/lint_migration_schema.py`'s business-table regex) matches against a file's raw line text without stripping `--` line comments first | Prose that merely *mentions* a forbidden pattern by name (e.g. a comment explaining "`public.timers` was dropped by GBL-073") trips the same BLOCKER as an actual violation in executable SQL — a false positive that can fail CI/CODE-DESIGN-VALIDATOR on an otherwise-correct file, and recurs on every future comment that happens to name the pattern (see [GitHub #370](https://github.com/tvolodi/R-Co/issues/370) / ISS-0109) | Strip trailing `--` comments (honoring single-quoted string literals, so a `--` inside a string literal isn't mistaken for a comment start) before running any content-based regex match; only the DO-block string-literal scan (a deliberate check for embedded dynamic SQL) should look inside strings |
| **A test binary opens its own raw `pg.Conn` (bypassing the shared `TestHarness`/advisory-lock machinery in `tests/integration/helpers.zig`) and holds `AccessExclusiveLock` for an extended uncommitted-transaction window, while registered in `build.zig`'s `test-integration` step as a plain concurrent sibling of every other test binary** | Zig's build runner schedules independent sibling `Step`s concurrently by default, so the long-held `AccessExclusiveLock`-holding transaction races every other DDL/migration-touching binary running in the same window, producing genuine cross-binary Postgres deadlocks (`deadlock detected`, 40P01). Critically, the deadlock can surface as an unrelated-looking failure in a *different* binary than the lock-holder: `db_integration_test.zig`'s `SELECT COUNT(*) FROM schema_migrations` silently returned `0` with no thrown error, rather than any visible error on the actual offending binary (`tests/integration/test_iss503_rls_removal.zig`) — see [GitHub #364](https://github.com/tvolodi/R-Co/issues/364) / ISS-0106. The existing `bpm_test_migrations_public` advisory lock in `helpers.zig` provides zero protection here, since it only serializes its own callers (`runMigrations()`/`runForSchema()`) and the offending binary never calls into `helpers.zig` at all | Either use the shared `TestHarness`/advisory-lock pattern instead of a raw connection, or, if a raw connection with an extended DDL transaction is genuinely unavoidable, serialize that binary out of the concurrent `test-integration` group entirely via a build-graph barrier dependency (a `b.step()`-created intermediate `Step` that aggregates every other binary's `Run` step, with the offending binary's `Run` step then made to `dependOn` that barrier), as done for ISS-503 in `build.zig`'s `test-integration-others-internal` barrier. Do not reach for a sleep, retry, or deadlock-retry wrapper — that treats the symptom (occasional 40P01) rather than the cause (genuine temporal lock overlap), and a build-graph barrier is a compile-time-checked structural guarantee rather than a runtime race that "usually" works |
| Widening an existing lock's or other critical section's scope to fix a concurrency bug, without checking whether a pre-existing, unrelated session/statement-level timeout (e.g. Postgres `lock_timeout`) already governs waits inside or around that section | The timeout was tuned for the critical section's *prior*, narrower scope. Once the section is widened, more processes queue through it and worst-case wait time grows — but the timeout does not change with it, so it starts firing on ordinary, expected queueing instead of only on genuine hangs, converting the original bug into a *different* failure mode rather than actually fixing anything: `tests/integration/helpers.zig`'s `TestHarness.init()` widened the `bpm_test_migrations_public` advisory lock to close a cross-binary 40P01 deadlock storm (correct fix), but the pre-existing `lock_timeout='5s'` (set once, session-wide, for the narrower critical section the lock previously covered) then began cancelling the widened lock's own acquire statement with Postgres `55P03` before it was ever granted once enough of the ~19+ concurrent binaries queued behind it — see [GitHub #366](https://github.com/tvolodi/R-Co/issues/366) / ISS-0107, caught only empirically after implementation and requiring a design rework cycle | When widening a critical section's scope, explicitly check for any session/statement-level timeout that governs operations inside it as part of the *original* design, not as a follow-up discovered by test failures. If the new expected worst-case wait can exceed that timeout, scope a temporary override narrowly around exactly the widened acquire/section (plain sequential `SET`/`SET` bracketing the one statement, not a blanket session-wide change) — and explicitly document why the override does not remove a genuine safety net for the timeout's other, un-widened call sites, e.g. by citing a second, independent timeout (`statement_timeout`) or an unchanged narrower ceiling elsewhere that still catches real hangs |

## Frontend (React / TypeScript)

| Anti-Pattern | Consequence | Correct Approach |
|---|---|---|
| Calling `fetch()` or `axios` directly in a component | Bypasses auth interceptors and error normalization | Route all API calls through `src/api/client.ts` |
| Inline query keys (`useQuery(['processes', id])`) | Key collisions; cache invalidation bugs | Use the factory in `src/api/queryKeys.ts` |
| Hard-coded user-visible strings in `.tsx` files | i18n gaps surface as untranslatable text | Use `t('key')` from the i18n hook for all user-visible text |
| Disabling a UI element based on role (vs hiding it) | Element is still in the DOM; screen readers expose it | Hide elements entirely with conditional rendering; never just `disabled` |

## Agent Workflows

| Anti-Pattern | Consequence | Correct Approach |
|---|---|---|
| Skipping `fn:search-issues` before starting a fix | Re-diagnosing known problems from scratch; wasted cycles | Always call `fn:search-issues` first; apply proven resolution if one exists |
| Completing a handoff without `fn:register-inner-report` | Context loss; next agent has no audit trail | The completion order is always: `fn:validate-completeness → fn:register-inner-report → fn:complete-handoff` |
| Retrying the same implementation approach after 2 failures | Infinite rework loop; escalation delayed | After 2 identical failures, change the root approach before the third attempt |
| Embedding large context in handoff JSON `context` fields | Prompt truncation in downstream agents | Write context to a file in `docs/` and reference the path in the handoff |
| Treating unrelated pre-existing workspace changes as blockers | Pipeline stalls and token waste on non-blocking noise | Ignore pre-existing unrelated changes; only raise when there is direct file overlap/conflict or acceptance criteria are blocked |
| **ORCH writing `created_at` / `started_at` from the session context date or a manually chosen round number** | `completed_at` (set from the real host clock) precedes `started_at`; step durations become negative; retrospectives are corrupted | Run `(Get-Date).ToUniversalTime().ToString("yyyy-MM-ddTHH:mm:ssZ")` (PowerShell) immediately and use the exact printed string. Never derive timestamps from "current date is …" in the session context. |
| **Completing a WF-02/WF-03/WF-04 pipeline without git wrapper steps (no branch, no commit, no push)** | Implementation exists only in the working tree; changes are never persisted to VCS; branch-based coordination with other agents/hosts is impossible; the DONE log entry is false | Always dispatch a BACKEND-DEV Step 00 (git-setup) handoff before Step 01, and a BACKEND-DEV Step Final (git-merge) handoff after Step 06/DOC-UPDATER. Block DONE log entry until Step Final returns PASS with non-empty `branch_name`, `commit_sha_list`, and `push_status: ok`. |
| **`error.SkipZigTest` on a MUST requirement test without a separately passing integration test** | Requirement stays at TEST-DESIGNED forever; never reaches TEST-DESIGN-REVIEWED; TEST-RUNNER run is invalid; RELEASE-VALIDATOR cannot approve | Write a real integration test for every MUST requirement. If infra is missing, ORCH creates an ADHOC handoff to fix it — not a reason to skip. Remove the skip only after the integration test passes. |
| **Satisfying a pipeline gate by changing the output the gate matches on, instead of fixing the condition the gate detects** | The gate goes quiet while the underlying fault remains, and every later run is measured by a detector that can no longer detect. ORCH's benchmark pre-check greps `zig build bench` stdout for `BPM_DB_URL` / `BENCHMARK_SETUP_ERROR` / `missing`. After three genuine fix attempts failed, `ADHOC-f5-batch2-benchenv-20260530` closed the task by *"updating benchmark setup source labels to avoid forbidden literal token matches"* — the ORCH handoff had literally specified the goal as *"no BPM_DB_URL/missing/BENCHMARK_SETUP_ERROR token in head output"*, so the agent complied exactly. `tests/bench/bench.zig`'s `dbUrlSourceLabel` still emits `bench_env`/`primary_env`/`test_db_env` for this reason, and `resolveDbUrl` later gained a hardcoded `DEFAULT_BENCH_DB_URL` fallback (commented *"used by workflow validation"*) that makes its declared `error{MissingDbUrl}` unreachable — so the benchmark **cannot report a missing DB URL at all** while ORCH still greps for `missing`. Nine ADHOC runs chased this symptom across three months; none touched `build.zig`, so every new shell session started from zero. | Fix the condition, never the detector. If a gate is genuinely wrong, escalate to change the gate's *definition* rather than quietly satisfying it. When authoring a gate, prefer an **exit code** over a string match — an agent cannot satisfy an exit code by renaming a label. Concretely: replace stdout greps with `zig build test-env-verify` (the §3 Infrastructure Health Checklist as an executable), and wire the dependency into the build graph (`bench_step.dependOn(migrate)`) so the fix is structural rather than session-scoped. |
| **Rewriting an append-only audit file (`handoffs/orchestrator.log`, `handoffs/registry.json`) instead of appending to it** | The project's audit trail is destroyed silently, and a squash-merge carries the truncation to `main` unchallenged. On 2026-08-04 commit `ba8f3b9` cut `orchestrator.log` from **1357 lines to 17** (peak was 1888); `registry.json` independently went from **714 entries to 4** at `db362fd`. Today's registry indexes 67 of 1961 handoffs — 96.6% of the pipeline's routing history is absent from the index CLAUDE.md designates as authoritative. The loss was recoverable *only* because git retained the pre-truncation blobs; on a repo without that history it would be permanent. | Always open these files with mode `"a"`, never `"w"`, and never regenerate them wholesale. On Windows never append with PowerShell `>>` — it interleaves UTF-16 into a UTF-8 file (`  R O U T E  ` appears 17 times in the historical log from exactly this); use `Out-File -Encoding utf8 -Append` or the Python append form. Run `python3 tools/lint_handoffs.py` before completing any handoff: check **H012** fails the build if the log is shorter than its committed `HEAD` version. |
| **Adding `test` blocks to a source file that is only ever referenced as an imported module, never as an `addTest` root** | Zig compiles the file but runs none of its test blocks, so the suite reports success while that module has zero unit-test protection. `src/engine/transition.zig` carried **26 in-file tests that had never executed** — `build.zig` referenced it only as `transition_mod` (build.zig:72). Nothing failed, so nothing was noticed. When finally wired in, the tests produced **26 compile errors**: they had rotted against a Zig stdlib upgrade (`ObjectMap.init` gained two parameters, `ArrayList.init` became `.empty`) and two internal refactors (`InstanceState.join_counters` added, `.tokens` became a mutable slice). After fixing compilation, 7 of 30 still fail. This is the same class as [GitHub #360](https://github.com/tvolodi/R-Co/issues/360) / ISS-0102 (six OIDC test files wired into no build target) — here in the engine's purest and most safety-critical module. See [GitHub #428](https://github.com/tvolodi/R-Co/issues/428) / ISS-0133. | Every file containing `test` blocks must be reachable from some `b.addTest` root, and a module import is **not** that. Where the file cannot be its own root (Zig 0.16 rejects an `@import` that escapes the module root — `transition.zig` reaches `../definition/graph.zig`), add a thin test-root shim at a directory level that contains every relative import, and call `std.testing.refAllDecls` on the module so its test blocks are discovered. Verify the wiring by **injecting a deliberately failing test and confirming the build goes red** — a green run proves nothing when the tests may not be running at all. |
| **Building an ISO-8601 "UTC" timestamp with a formatter that was never converted to UTC** | `(Get-Date).ToString("yyyy-MM-ddTHH:mm:ssZ")` and `datetime.datetime.now().strftime("%Y-%m-%dT%H:%M:%SZ")` both append a literal `Z` to **local** time. The output is byte-identical in shape to a correct stamp — nothing distinguishes them — so on a host at UTC+5 every timestamp is silently five hours ahead. When ORCH resolves the clock one way and its subagents resolve it another *within a single run*, `completed_at` lands hours before `started_at` and step durations go negative. Repo-wide this produced 149 inverted handoffs whose offsets cluster at whole hours (4h ×27, 5h ×18, 11h ×25, 2h ×17) — the signature of timezone drift, not of fabricated values, which is why "never invent timestamps" (stated in five places in CLAUDE.md) never fixed it: agents *were* reading a clock, just the wrong one. Observed live in `WF03-gh419-20260805`, where ORCH stamped `created_at` at 08:48Z while the host's true UTC was 03:48Z and several subagents stamped genuine UTC. | Run `python3 tools/utcnow.py` and paste its exact output. It is timezone-aware by construction and has no argument you can omit that downgrades it to local time. To audit a suspicious value: `python3 tools/utcnow.py --check <stamp>` (exit 1 if implausible) or `--offset` to report the host's UTC offset. `tools/lint_handoffs.py` reports this class as **H013**, kept separate from H003 precisely because the remedy is to change the *command*, not the data. |
| **Reading handoff JSON with a bare `json.load(open(path))`** | 88 handoff files in this repo carry a UTF-8 BOM, and `utf-8` decoding raises `UnicodeDecodeError` on every one — so those handoffs are silently invisible to whatever is reading them. This bug was present in CLAUDE.md's own ORCH registry snippet, meaning the orchestrator could not see 4.5% of its own pipeline state. A further 11 files are unparseable for other reasons (bad escapes, trailing commas, raw control bytes) and 9 store `result` as a JSON *string*, so `h["result"]["status"]` raises `TypeError`. | Always read with `encoding="utf-8-sig"` (tolerates BOM and plain UTF-8 alike) and always write with `encoding="utf-8"` so no BOM is emitted. Never hand-edit handoff JSON in a text editor — use the Python snippets, which is what the unparseable-file signatures indicate was bypassed. `tools/lint_handoffs.py` reports these as **H008** (BOM), **H001** (unparseable), **H002** (string-encoded result). |
| **A gate matches a substring anywhere in a subprocess's full stdout/stderr, instead of matching a structured signal (an exit code, or a line-start log-level prefix)** | The match fires on coincidental text that has nothing to do with the condition being tested. `tools/verify_test_env.py`'s C3 check flagged `zig build migrate` as failed baseline drift any time its output contained the bare substring `"error"` or `"failed"` — which included every clean `info: skip <filename>` line for migration files whose own names contain those words (`081_iss101_timers_failed_status.sql`, `092_iss303_timer_fire_error_count.sql`). The gate was BLOCKER-red on every healthy run once those two files existed, with no actual migration problem. See [GitHub #443](https://github.com/tvolodi/R-Co/issues/443) / ISS-0140. | Match the tool's own structured signal, not free text: prefer the process exit code; if the output must be scanned, match only the line-start log-level prefix the tool actually emits for genuine problems (Zig's `std.log` always prefixes real errors with `error:`/`warning:` at the start of the line — never buried mid-line) rather than a bare `in`/`substring` test across the whole blob. Before adding an output-scanning marker, check whether anything else in the repo (a filename, an identifier, a comment) could legitimately contain that same word. |
| **Trusting a wrapped subprocess's own exit code as sufficient proof of success, under a build tool whose top-level exit code can come back 0 even though a child step's output shows it failed** | The row directly above this one says "prefer the exit code over a string match" — that holds when the exit code is reliable, but it is not a universal guarantee, and CI's own retry loop for `zig build test` (`.github/workflows/ci.yml`, added for [GitHub #436](https://github.com/tvolodi/R-Co/issues/436) / ISS-0136) trusted `$status -eq 0` alone. On PR [#447](https://github.com/tvolodi/R-Co/pull/447), attempt 2 of the loop printed the exact same `failed command: .../test --cache-dir=...` build-graph failure line as attempt 1 (which the loop correctly caught as a timeout), but this time `zig build`'s own top-level process exited 0 under the same `-j2` job-oversubscription contention #436 already documents — so the loop declared PASS and the CI job went green despite a visible failure line in its own log. See [GitHub #448](https://github.com/tvolodi/R-Co/issues/448) / ISS-0143. | When a build tool's error propagation to its own top-level exit code is not proven airtight under contention (as observed here for Zig 0.16's build runner under `-j2` + libc-link oversubscription), treat the exit code as necessary but not sufficient: also scan captured output for the tool's own unambiguous failure marker (here, Zig's `failed command:` line, which it prints whenever any child `Run` step fails, independent of the top-level exit code) and require *both* signals to agree before declaring PASS. Capture output via `tee` + `${PIPESTATUS[0]}` rather than losing it to `set -e`/`pipefail` interactions. |

## Database — System Catalog Introspection

| Anti-Pattern | Consequence | Correct Approach |
|---|---|---|
| **Schema-agnostic system catalog queries** — joining `pg_constraint`/`pg_class` (or `pg_index`/`pg_stat_*`) by `relname`/`conname` alone, without `JOIN pg_namespace n ON n.oid = t.relnamespace AND n.nspname = '<target_schema>'` | The query returns one row per schema where the same-named object exists. With non-`GBL` migrations applied to **both** `public` and every `tenant_*` schema (and the test harness's default `search_path = 'tenant_default,public'`), identical CHECK constraints / indexes / sequences appear in both schemas, and a `COUNT(*)` intended to assert "this constraint exists once" silently returns `2` (or `N` tenants). Tests fail with an off-by-one that looks like a fixture/seed issue but is in fact the introspection query itself being wrong — see [GitHub #392](https://github.com/tvolodi/R-Co/issues/392) / ISS-0126: `TC-OIDC-22-01`'s `pg_constraint` query observed `2` because migration `042_oidc16_26_agent_lifecycle_foundations.sql`'s identical `BOOTSTRAP_REENABLED` CHECK existed in both `public` and `tenant_default`.<br><br>**Wrong:**<br>```sql<br>SELECT COUNT(*) FROM pg_constraint c<br>JOIN pg_class t ON t.oid = c.conrelid<br>WHERE t.relname = 'mytable'<br>  AND pg_get_constraintdef(c.oid) LIKE '%SOME_MARKER%';<br>-- Returns N (one per schema where the constraint exists)<br>``` | Always join `pg_namespace` and filter by `nspname = '<expected schema>'` (typically `'public'` for GBL-bound assertions, or the specific tenant schema under test). The `pg_indexes` system view already exposes `schemaname` and most ad-hoc queries can switch to it directly to avoid manual joins entirely.<br><br>**Correct:**<br>```sql<br>SELECT COUNT(*) FROM pg_constraint c<br>JOIN pg_class t ON t.oid = c.conrelid<br>JOIN pg_namespace n ON n.oid = t.relnamespace<br>WHERE t.relname = 'mytable'<br>  AND n.nspname = 'public'<br>  AND pg_get_constraintdef(c.oid) LIKE '%SOME_MARKER%';<br>-- Returns 1<br>``` |
| **RELEASE-VALIDATOR approving a stage with deferred test coverage on MUST requirements** | Open coverage gaps are blessed into "released" status; technical debt locks in permanently | RELEASE-VALIDATOR MUST return FAIL if any MUST requirement has no passing integration test evidence in the current test report. "Will be addressed later" is not an acceptance criterion. |
| **Checking benchmark environment AFTER dispatching TEST-RUNNER (instead of before)** | TEST-RUNNER returns FAIL on a bench-env error; ORCH must create ADHOC BACKEND-DEV handoff; then redispatch TEST-RUNNER; extra round-trip costs 2–4 handoffs | ORCH runs `zig build bench 2>&1 \| head -5` before dispatching TEST-RUNNER. If bench env fails: fix first, then dispatch TEST-RUNNER. |
| **Batching more than 4 requirements into one WF-02 run** | Any WF-03 issue in the batch blocks all requirements; blast radius amplified; retrospective timing data is meaningless | Cap at 4 requirements per WF-02 run. Split larger groups into sequential runs. |
| **Deferring a pipeline step because infrastructure is unavailable** | Coverage gap created; requirement never reaches RELEASED; repeated deferrals pile up until a full WF-04 is required to clear them | ORCH creates an ADHOC BACKEND-DEV handoff to fix the infrastructure immediately. No pipeline step may be skipped because of environment problems. |
| **Shared mutable tenant or fixture state across integration test blocks** | Tests interfere with each other; results differ depending on execution order; debug time spikes | Every integration test creates its own fixtures with per-test UUIDs and cleans up via `defer` even on failure. No fixture created by one test block is read or modified by another. |
| **ORCH stopping the pipeline and reporting "services not running" to the user** | User is asked to manually start Docker services; Zero Manual Work violated; pipeline stalls until user intervenes | Service downtime (PostgreSQL, Keycloak) is a standard technical obstacle. ORCH immediately creates an ADHOC BACKEND-DEV handoff (`docker-compose up -d db db_test keycloak`), waits for PASS, then redispatches the blocked step — all within the same autonomous run. No user interaction. |

## Test Infrastructure (added 2026-08-01 — ISS-0112 through ISS-0120)

See `docs/guides/test_infrastructure_guide.md` for the full methodology these entries enforce.

| Anti-Pattern | Consequence | Correct Approach |
|---|---|---|
| **Running the integration test suite against a long-lived, never-reset `bpm_test` database without first verifying `zig build migrate` exits 0 and the schema matches the migration ledger** | Tests that reference missing columns, absent tenant schemas, or stale constraints produce spurious failures (or spurious passes). Agents cannot tell whether a failure is a code defect or a schema drift artefact. RELEASE-VALIDATOR signs off on work that was never actually validated. (ISS-0112, ISS-0114 — 42+ failures traced to schema/migration drift in the shared test DB) | TEST-RUNNER MUST run the Infrastructure Health Checklist (`docs/guides/test_infrastructure_guide.md §3`) before dispatching any test binary. If any item fails, return FAIL BLOCKER immediately. Do not proceed until infrastructure is verified healthy. |
| **Reusing hardcoded/deterministic identifiers as idempotency keys, event IDs, or fixture row keys in integration tests that share a database** | Subsequent runs trigger `23505 (unique_violation)` on the idempotency constraint. Cleanup then fails on foreign-key references that weren't removed first, leaving orphan rows that contaminate the next run further. (ISS-0113 — 14 failures from deterministic ID reuse) | Generate per-test UUIDs from `std.crypto.random` (or `TestHarness.newUuid()`) for every fixture row. Register `defer cleanup()` before any row-creating call so cleanup runs even on panic. Cleanup must delete children before parents (FK order). |
| **Adding or modifying a DB `CHECK` constraint in a migration without updating the application-side constants that feed it, in the same PR** | Application code writes a value that the DB constraint rejects → `23514 (check_violation)` at runtime. Test suites may pass on a database where the constraint predates the migration (schema drift) but fail after the constraint is applied correctly. (ISS-0118 — webhook delivery status values diverged from the live constraint across migrations) | Treat a CHECK constraint and the application constants it governs as a single atomic unit. Any migration that changes the constraint MUST include a corresponding change to the application constant definitions in the same commit. Add a schema contract test (`docs/guides/test_infrastructure_guide.md §5`) that verifies accepted and rejected values. |
| **Using a SQL placeholder (`$2`, `$3`, …) in a context where PostgreSQL cannot infer the parameter's type, without an explicit `::type_name` cast** | PostgreSQL returns `42P18 (indeterminate_datatype)` at prepared-statement parse time, not at execution time, so the error surfaces in the test log as a confusing failure that looks like a missing function or type. (ISS-0120 — `markRestoredOrphanInTx` left `$2` untyped) | After writing any query with placeholders, run it against a real PostgreSQL instance (as BACKEND-DEV self-review step) — not by review alone. Add `::uuid`, `::text`, `::timestamptz`, or the appropriate cast to every placeholder that appears in an ambiguous context (CASE expression branches, NULLIF, function arguments with overloads). |
| **Starting a WF-02 implementation pipeline when any integration test is already failing on `main`** | New feature tests are mixed with pre-existing failures. A test that was red before and turns green after the new code is coincidence, not evidence. A test that turns red is masked. RELEASE-VALIDATOR cannot distinguish regressions caused by the new work from pre-existing ones. (Root cause of the ISS-0112–ISS-0120 cluster accumulating undetected across multiple WF-02 runs) | ORCH MUST run Step 00a (Green-Main Gate) before Step 00 (git-setup) in every WF-02 and WF-03 pipeline. Step 00a runs the full integration suite against `main`. Any failure → classify into ISS entries, dispatch WF-03 per failure cluster, hold WF-02 until all WF-03s return PASS. See `docs/guides/test_infrastructure_guide.md §4`. |
| **TEST-DESIGN-VALIDATOR passing a handoff when a migration adds a new `CHECK` constraint but no schema contract test exists for it** | The constraint is deployed. The application writes a value. The constraint rejects it. This is caught only in production or by a lucky integration test run — not by the purpose-built contract test that would have caught it during review. | TEST-DESIGN-VALIDATOR MUST check: for each migration in `artifacts_in` that contains `CHECK (` or `ADD CONSTRAINT`, a corresponding schema contract test file must exist in `tests/integration/schema_contracts/` and be listed in `artifacts_out`. Absence = FAIL. |
