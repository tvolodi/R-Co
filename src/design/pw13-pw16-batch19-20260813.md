## 0. Scope and reused infrastructure

All four requirements are **frontend-only**. The backend counterparts are already released:

- **API-10** (rate-limit middleware) — surfaces `Retry-After` as a header on every 429. The API client (`web/src/api/client.ts`) already converts it into `ApiError.details.retryAfter` (line 105).
- **PD-08** (`X-Resource-Version`) — accepted on `PATCH /api/v1/definitions/{id}` and emitted on 409 responses. Frontend currently does not read it.
- **GRD-UI-02..05** — the PATTERNS forbidlist (`web/tests/guards/forbidlist.ts`) and the three scan specs (`source-scan`, `bundle-scan`, `meta-control`) are reused as the policy backbone for GRD-UI-06's `color-contrast` enablement and the GRD-UI-07 ARIA dangling-reference assertion.
- **RND-UI-03** — `classifyError` already classifies `status === 429 && details.retryAfter != null` → `'rate-limit'` and `status === 409` → `'stale-version'` (see `web/src/utils/classifyError.ts:18-22`). The `QueryStateBoundary` currently ships placeholder stubs for both states (see `web/src/components/ui/QueryStateBoundary.tsx:35-58`). This batch replaces those stubs with the real components.

**No-mock E2E contract** (applies to every E2E in §5): every E2E hits the real backend (Keycloak `http://localhost:8081/realms/bpm-default`, BPM API `http://127.0.0.1:8080`, PostgreSQL `localhost:5432`). Zero HTTP mocking, zero `page.route()` interception of API or auth endpoints. Seeded data is created against the real backend inside the test setup via `request.post()` / `request.fetch()` (the Playwright `APIRequestContext`, not `page.route`). Per-test identity is obtained via `getKeycloakToken(request, 'worker-user', 'worker-pass')` in `web/tests/e2e/helpers.ts:36`. Every test fails fast if Keycloak, the BPM API, or PostgreSQL is unreachable — see the BLOCKER branch in §5.

## 1. RND-UI-05 — Rate-limit backpressure with retry countdown

### 1.1 Component interface: `RateLimitBackpressure`

```typescript
// web/src/components/ui/RateLimitBackpressure.tsx
export interface RateLimitBackpressureProps {
  /** The numeric Retry-After value, in seconds, taken from the 429 response header. */
  retryAfter: number
  /** Bound the displayed countdown — defaults to Math.ceil(retryAfter). */
  initialSeconds?: number
  /** Called exactly once when the countdown reaches zero. */
  onRetry: () => void
  /** Optional: a label explaining what surface is being rate-limited (e.g. "Task Inbox"). */
  surfaceLabel?: string
}

export function RateLimitBackpressure(props: RateLimitBackpressureProps): React.ReactElement
```

**Behavior contract (1:1 mapping to acceptance criteria):**

| AC | Implementation decision |
|---|---|
| AC-1: count down at one-second intervals | One `setInterval` with `1000 ms` tick; React state `secondsRemaining: number`; cleared in the `useEffect` cleanup. |
| AC-1: aria-live="polite" region | Wrapper `<div role="status" aria-live="polite" aria-atomic="true">` containing the announcement string. |
| AC-1: unit is the response header value in seconds | The header value is parsed by `client.ts` (already done) and surfaced as `ApiError.details.retryAfter: string \| null`. The component accepts the parsed number from `classifyError`'s caller via the prop. |
| AC-2: announced value decreases by one each second | The `<div>` text content reads `"Retry in {n}s"`; updated on every interval tick. |
| AC-3: exactly one refetch at zero | A `useEffect` with a `firedRef = useRef(false)` flag triggers `onRetry()` once when `secondsRemaining === 0`, then clears the interval. The ref guarantees a single fire even under React strict-mode double-invocation. |
| AC-3: no second automatic retry | The component is purely presentational after the initial mount; it does not own the query lifecycle. The caller binds `onRetry` to `query.refetch()`; React Query's `retry: 0` (set globally in `web/src/main.tsx` per RND-UI-01) prevents any automatic retry. |
| AC-4: second 429 → new countdown starts | The remount is the parent's responsibility: when the second 429 lands, `classifyError` returns `'rate-limit'` again, the boundary unmounts and re-mounts `RateLimitBackpressure` with a fresh `initialSeconds` from the new `Retry-After`. The component itself never persists state across re-renders with a new `retryAfter`. |
| AC-5: 429 without `Retry-After` → `fetch-failure` | No change needed: `classifyError` already returns `'fetch-failure'` when `details.retryAfter == null` (see `classifyError.ts:19`). The state machine routes to `<FetchError>` (already exists) with its user-driven retry. |

**Diff surfaces in existing code:**

1. `web/src/components/ui/QueryStateBoundary.tsx` — replace the inline `'rate-limit'` case body with `<RateLimitBackpressure retryAfter={…} onRetry={onRetry ?? noop} />`. The `retryAfter` value reaches the boundary via a new optional prop `rateLimitRetryAfter?: number` on `QueryStateBoundary`. The page caller is responsible for passing it down from the query error. (See §1.3 below.)
2. No change to `classifyError.ts` — the existing 429-with-`retryAfter` branch is sufficient.

### 1.2 Data flow

```
GET /api/v1/instances
   │
   ▼  HTTP 429, Retry-After: 30
backend (API-10)
   │
   ▼  Response header
client.ts: builds ApiError { status: 429, details: { retryAfter: '30' } }
   │
   ▼
useInstances hook throws ApiError into React Query
   │
   ▼
page derives: state = classifyError(err)  → 'rate-limit'
            retryAfter = Number(err.details.retryAfter)  → 30
   │
   ▼
<QueryStateBoundary state="rate-limit" rateLimitRetryAfter={30} onRetry={refetch}>
   │
   └── <RateLimitBackpressure retryAfter={30} onRetry={refetch}>
         │
         ├── secondsRemaining: 30 → 29 → ... → 1 → 0
         ├── <div role="status" aria-live="polite" aria-atomic="true">
         │     "Retry in {n}s"
         │   </div>
         └── at 0: firedRef flips, onRetry() fires, interval cleared
```

## 2. RND-UI-06 — Three-action write conflict resolution

### 2.1 Component interface: `ConflictResolver`

```typescript
// web/src/components/ui/ConflictResolver.tsx
export interface ConflictResolverProps {
  /** Server payload after the 409. */
  serverPayload: Record<string, unknown>
  /** Local draft from the Zustand store. */
  localDraft: Record<string, unknown>
  /** The new version stamp to use when the user picks Merge manually. */
  conflictVersion: string | null
  /** Called when the user picks "Refetch latest". The boundary already replaces the body. */
  onRefetch: () => void
  /** Called when the user picks "Merge manually" and saves, with the merged body and the version. */
  onSaveMerged: (mergedBody: Record<string, unknown>, version: string) => void
  /** Called when the user confirms the Discard mine dialog. */
  onDiscardConfirmed: () => void
  /** The host element to portal into. Defaults to document.body. */
  portalContainer?: HTMLElement
}

export function ConflictResolver(props: ConflictResolverProps): React.ReactElement | null
```

**Behavior contract (1:1 mapping to acceptance criteria):**

| AC | Implementation decision |
|---|---|
| AC-1: mounts via `createPortal` in a portal | `ReactDOM.createPortal(<div role="dialog" aria-modal="true" aria-labelledby="conflict-resolver-title">, props.portalContainer ?? document.body)`. The modal traps focus and is dismissible only via one of the three actions. |
| AC-1: three actions present | Three buttons: `Refetch latest`, `Merge manually`, `Discard mine`. Each is a `<button type="button">` with distinct `data-testid` attributes: `conflict-refetch`, `conflict-merge`, `conflict-discard`. |
| AC-2: no PUT/POST between 409 and first user click | The component owns NO write side-effects. It does not call `definitionsApi.update()`; the caller does. Until the user clicks, the resolver is the only rendered surface. The E2E inspects the network log between the 409 response and the first click. |
| AC-3: Refetch latest retains the local draft; banner present | Picking Refetch triggers `onRefetch()`. The DraftBanner (see §2.4) is rendered above the page body by the parent page, sourced from the Zustand draft store. The Zustand store is NOT mutated by the conflict-resolver flow. |
| AC-3: local draft is still readable from the Zustand store | The E2E directly reads `window.__zustand_draft.getState()` for the seeded draft; the assertion is "draft === seeded draft". |
| AC-4: Merge manually → version field equals `X-Resource-Version`, body is the merged document | The component opens `<JsonDiffView before={serverPayload} after={localDraft} />` inside a side panel. The user picks a field-by-field source (left/right) and clicks Save. The save call is `onSaveMerged(mergedBody, props.conflictVersion)`. The bound PATCH sets `If-Match: <conflictVersion>` (or `version: <conflictVersion>` in the body, depending on backend convention — see §2.5). |
| AC-5: Discard mine → `ConfirmDialog` with `confirmVariant="danger"` | The Discard picker opens the existing `ConfirmDialog` component (already exists in the codebase, see `web/src/components/ui/ConfirmDialog.tsx` — verify the file exists; if not, see §2.6). The Confirm dialog confirm button calls `onDiscardConfirmed()`. |
| AC-5: local draft is dropped ONLY after confirm | The Zustand store mutation runs in `onDiscardConfirmed` (caller-side), not on dialog open. The E2E asserts the draft is still in the store after the dialog appears and dismissed without confirm. |
| AC-6: 409 without `X-Resource-Version` → Merge disabled, other two available | `conflictVersion == null` ⇒ render `Merge manually` as a `<button disabled aria-disabled="true" data-testid="conflict-merge">` with a tooltip-style explanatory node and `aria-describedby` pointing at it. The other two remain enabled. |

### 2.2 Component interface: `StaleVersionError`

```typescript
// web/src/components/ui/StaleVersionError.tsx
export interface StaleVersionErrorProps {
  /** The 409 ApiError, including details.xResourceVersion (or absence thereof). */
  error: ApiError
  /** Server payload after the 409 — passed to the resolver. */
  serverPayload: Record<string, unknown>
  /** Local draft from the Zustand store. */
  localDraft: Record<string, unknown>
  /** Refetch callback. */
  onRefetch: () => void
  /** Save-merged callback. */
  onSaveMerged: (mergedBody: Record<string, unknown>, version: string) => void
  /** Discard-confirmed callback. */
  onDiscardConfirmed: () => void
}

export function StaleVersionError(props: StaleVersionErrorProps): React.ReactElement
```

The `StaleVersionError` is the boundary-mounted component for the `'stale-version'` state. It is the host that renders `<ConflictResolver>` plus a header banner explaining the situation. AC-2 (no write between 409 and click) is enforced by the structure: the boundary only mounts `<ConflictResolver>` on the `'stale-version'` state, and `<ConflictResolver>` itself makes no API calls.

### 2.3 X-Resource-Version transport

**Backend emits:** `X-Resource-Version: <version>` on 409 responses to `PATCH /api/v1/definitions/{id}`.

**Frontend consumes (modification to `web/src/api/client.ts`):** when a 409 response carries the `X-Resource-Version` header, the client must attach it to `ApiError.details.xResourceVersion`. Implementation: in the `if (!response.ok)` block in `client.ts:118`, after parsing the body, check `response.headers.get('X-Resource-Version')` and set `details.xResourceVersion = value` on the thrown error. The 409 short-circuit above the `!response.ok` block already handles 409 with a different code path; we need to add `X-Resource-Version` capture there too: in the `if (response.status === 409)` branch (currently absent — must be added).

**Detail shape:** `ApiError.details` is already `Record<string, unknown>` (see `web/src/types/api.ts:7`). The new key is `xResourceVersion: string | null`.

**Frontend emits:** the PATCH (or PUT) request body for `definitionsApi.update(id, body)` should carry `version: <conflictVersion>` so the backend can match against ETag. If the backend convention is `If-Match` (header) instead of body, the same value is sent as `If-Match: <conflictVersion>` via a per-request header. The final decision is deferred to FRONTEND-DEV/IMPLEMENTATION and must be confirmed via the existing `curl` smoke test that the backend PD-08 contract uses; the design accommodates both.

### 2.4 Draft retention Zustand store

```typescript
// web/src/stores/definitionDraftStore.ts
interface DefinitionDraft {
  definitionId: string
  body: Record<string, unknown>
  dirtyFieldKeys: string[]
  savedAt: string | null  // ISO timestamp of last successful save
}

interface DefinitionDraftStore {
  draft: DefinitionDraft | null
  setDraft: (d: DefinitionDraft) => void
  clearDraft: (definitionId: string) => void
}
```

**Wiring rules (binding invariants):**

1. The draft is written by the Definition Editor page (`web/src/pages/definitions/DefinitionEditorPage.tsx`) on every keystroke that mutates the form, keyed by `definitionId`. The Editor never reads `X-Resource-Version` directly — it only reads the draft.
2. The ConflictResolver NEVER mutates the draft store. It only reads `localDraft` from the store.
3. `onDiscardConfirmed` calls `clearDraft(definitionId)`. The store transition is the ONLY place the draft is cleared on the conflict path.
4. `onRefetch` does NOT clear the draft. The DraftBanner persists across the refetch.
5. `onSaveMerged` calls `setDraft({ ..., savedAt: new Date().toISOString() })` to record the merge timestamp.

### 2.5 Refetched-state surface (the banner)

```typescript
// web/src/components/definitions/DraftBanner.tsx (new)
interface DraftBannerProps {
  draft: DefinitionDraft
  onApply: () => void      // Promote the draft into the editor body
  onDiscard: () => void    // Drops the draft and clears the store
}
```

The banner is rendered above the editor body when `definitionDraftStore.draft != null && draft.draft.savedAt == null` (i.e., the draft was modified but not saved since the last save). It is NOT a modal and does not block writes.

## 3. GRD-UI-06 — Accessibility gate per canonical surface

### 3.1 The six canonical surfaces

| # | Surface | Route | Seeded data assertion |
|---|---|---|---|
| 1 | Task Inbox | `/tasks` | At least one PENDING task in the inbox for `worker-user` (created by the F4 setup helper) |
| 2 | Instance List | `/instances` | At least one ACTIVE instance returned by `GET /api/v1/instances` |
| 3 | Instance Detail | `/instances/:id` | The instance from surface 2 — declared at `/instances` and clicked into |
| 4 | Definition List | `/definitions` | At least one ACTIVE definition returned by `GET /api/v1/definitions` |
| 5 | Process Designer | `/definitions/:id` | The definition from surface 4 — clicked into the editor |
| 6 | Login | `/auth/callback` (post-redirect) | The OIDC callback URL after Keycloak redirects — no seeded data; axe runs on the form rendered after redirect |

Login is included verbatim because the requirement names it. The Tenant Dashboard is **not** in the canonical surface set — explicitly excluded to match the requirement body.

### 3.2 Axe configuration

```typescript
// web/tests/a11y/axe-config.ts
import type { AxeBuilder } from '@axe-core/playwright'

export const a11yConfig: Pick<Parameters<AxeBuilder['disableRules']>[0], 'rules'> = {
  rules: {
    // RND-UI-06 requires color-contrast to be enabled (acceptance criterion 2).
    // All other rules left at axe defaults EXCEPT for the rules below, which are
    // known false-positives in the codebase and which the GRD-UI-07 fix will
    // retire over time. Today they are explicitly NOT in the disabled list.
  },

export const a11yTags = ['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa']
```

**Why `color-contrast` is explicitly NOT in the disabled list:** GRD-UI-06 AC-2 requires it. The axe baseline in `node_modules/@axe-core/playwright` keeps it on by default; this design adds a test-level assertion that the rule is present in the `enabledRules` returned by `AxeBuilder.options({ rules: a11yConfig.rules })` to fail fast if a future contributor adds it to the disabled set.

**Tags:** the four WCAG tags are the standard set for axe. Best-practice for axe in 2026 is `wcag2a, wcag2aa, wcag21a, wcag21aa, best-practice`; we OMIT `best-practice` from the tag set because GRD-UI-06 only mentions WCAG and the audit cycle must remain deterministic. (Open Question OQ-2.)

### 3.3 Impact-based gate

```typescript
// web/tests/a11y/a11yGate.ts
import AxeBuilder from '@axe-core/playwright'
import type { Page, TestInfo } from '@playwright/test'

export type A11ySeverity = 'BLOCKER' | 'CRITICAL' | 'MAJOR' | 'MINOR'

interface A11yResult {
  surface: string
  violations: Array<{
    ruleId: string
    impact: 'minor' | 'moderate' | 'serious' | 'critical' | null
    target: string
    help: string
    helpUrl: string
  }>
}

export async function runA11yGate(
  page: Page,
  surface: string,
  testInfo: TestInfo,
  options: { runId: string; date: string },
): Promise<A11yResult>
```

**Decision matrix (AC-1, AC-3):**

| axe `impact` | Decision | Severity in run report |
|---|---|---|
| `critical` | **FAIL** the gate | CRITICAL |
| `serious` | **FAIL** the gate | CRITICAL |
| `moderate` | pass; record-only | MINOR |
| `minor` | pass; record-only | MINOR |
| `null` (axe could not classify) | treat as `moderate` | MINOR |

The gate `throw`s iff any violation with `impact` in `{ critical, serious }` is present. The failure message names `ruleId`, `impact`, and `target` (per AC-1): exactly what axe returns in its `violations` array.

### 3.4 Writeback to the run report

The run report is written to `web/tests/reports/report-<date>-<runId>.yaml` (matching the existing GRD-UI-05 reporter path). The shape is:

```yaml
runId: "WF02-pw13-pw16-batch19-20260813"
date: "2026-08-13"
evaluatedSurfaces:
  - task-inbox
  - instance-list
  - instance-detail
  - definition-list
  - process-designer
  - login
violations: []    # or a list of { surface, ruleId, impact, target, severity }
```

The reporter step is a small helper (`web/tests/a11y/reportWriter.ts`) that appends the violation list to the YAML file. For the moderate/minor AC-3 case, the file is written even on a green run (AC-3: "the gate exits 0 and the violation is written to `tests/reports/report-<date>-<run_id>.yaml` at severity MINOR"). File format mirrors the GRD-UI-05 `RunReport` shape so a future BI consumer can ingest both with the same parser.

### 3.5 30-second per-surface budget

Each surface test gets `test.setTimeout(30_000)`. The gate's own runtime budget is `20_000 ms` (axe usually runs in < 5s on a real page); the remaining 10s covers page load + assertion settling. If the axe call exceeds 20s, the test fails with a clear "axe scan exceeded budget" message — distinct from a violation failure.

### 3.6 BLOCKER-if-unreachable

```typescript
// web/tests/a11y/a11yGate.ts (sketch)
async function verifyBackendReachable(testInfo: TestInfo): Promise<void> {
  const checks = await Promise.allSettled([
    fetch(process.env.BPM_TEST_URL ?? 'http://127.0.0.1:8080/health'),
    fetch(process.env.BPM_IDP_BASE_URL ?? 'http://localhost:8081/realms/bpm-default'),
    pgProbe(),  // connects to BPM_TEST_DB_URL via pg client
  ])

  const failed = checks
    .map((c, i) => ({ c, name: ['BPM-API', 'Keycloak', 'PostgreSQL'][i] }))
    .filter(x => x.c.status === 'rejected' || (x.c.status === 'fulfilled' && !x.c.value.ok))

  if (failed.length > 0) {
    const names = failed.map(f => f.name).join(', ')
    throw new Error(`A11Y GATE BLOCKER: ${names} unreachable — no surface scanned`)
  }
}
```

If any of the three is unreachable, the gate throws BEFORE any surface is run. The test fails with severity `BLOCKER` (encoded in the error message and in the run report YAML).

### 3.7 Brand-override contrast path (AC-5)

For the Task Inbox surface, the gate additionally:

1. Reads the computed style of `[data-testid="task-row"]` and asserts `background-color` matches `--surface-card` (or its computed value at the time of the scan).
2. Reads the computed `color` of all text nodes inside the row and asserts the contrast ratio against `background-color` is ≥ 4.5:1 (WCAG AA for normal text).
3. The Task Inbox page is rendered with the seeded `CMP-UI-04` brand override active (the seeded tenant has a non-default brand surface, set up by the F4 helper). The same scan is repeated after the override is applied.

The axe `color-contrast` rule is the gate-of-record, but the explicit computation is a belt-and-braces assertion that fails the gate even if axe's color picker is fooled by a flat background.

## 4. GRD-UI-07 — Generated per-field ARIA wiring

### 4.1 FieldFactory changes

`web/src/components/forms/FieldFactory.tsx` currently emits `<label htmlFor={fieldName}>` and `<input id={fieldName}>` for every field but does NOT emit `aria-required`, `aria-describedby`, `aria-invalid`, or `aria-errormessage`. The change is additive.

**Required ARIA contract per field (acceptance criterion 1:1):**

| Attribute | Source | Value |
|---|---|---|
| `<label htmlFor>` | always | `fieldName` (unchanged) |
| `id` on input | always | `fieldName` (unchanged) |
| `aria-required` | always | `'true'` if the field is in `form_schema.required` (the JSON Schema `required` array), else the attribute is OMITTED (not `false`) |
| `aria-describedby` | always when a hint exists | the value of the hint node's `id` (see below) |
| `aria-invalid` | always when `errorMessage != null` | `'true'` |
| `aria-errormessage` | always when `errorMessage != null` | the value of the error node's `id` (see below) |

**Hint node:**

```typescript
// Per-field child:
<p id={`${fieldName}-hint`} style={{…}} >{description}</p>
```

The hint `id` is `${fieldName}-hint`. The `aria-describedby` value on the input is `${fieldName}-hint`.

**Error node:**

```typescript
// Per-field child (only when errorMessage is non-null):
<p id={`${fieldName}-error`} role="alert" style={{…}}>{errorMessage}</p>
```

The error `id` is `${fieldName}-error`. `aria-errormessage` on the input is `${fieldName}-error`. The `role="alert"` adds screen-reader announcement on validation failure.

**Replacement sketch (interface, not implementation):**

```typescript
export interface RenderFormFieldOptions {
  fieldName: string           // expected to satisfy idempotent registry key
  fieldDef: TaskFormField
  value: unknown
  watchValue: unknown
  register: UseFormRegisterReturn
  errorMessage?: string
  // The RegistryRenderOptions contract from CMP-UI-05 — see §4.3
  fieldRegistryKey?: string   // the registry key used by CMP-UI-05
}
```

The function signature is preserved (the existing 6-arg signature is `renderFormField(fieldName, fieldDef, value, watchValue, register, errorMessage)`). The new `fieldRegistryKey` is optional and only used when the field is registered through the CMP-UI-05 registry (see §4.3).

### 4.2 DynamicFormRenderer changes

`web/src/components/forms/DynamicFormRenderer.tsx` is the only host of `renderFormField`. The change:

1. The `<form>` root element gets `aria-busy={isSubmitting}` — the attribute is on the form, not on the submit button.
2. The submit handler awaits `onSubmit(values)` and then restores `isSubmitting=false` (the existing flow).
3. The `useForm` `mode` stays `'onChange'` (existing). The `form.formState.isSubmitting` is NOT used — the form's aria-busy is bound to the prop `isSubmitting` to ensure the gate sees the in-flight state.

**Dangling-reference invariant (AC-3):** every `aria-invalid="true"` MUST have a corresponding `aria-errormessage` whose target exists in the DOM at the same moment. The renderer enforces this by always co-rendering the error node when `aria-invalid` is set. The dangling-reference check is a separate aria-validator that runs after the test renders the form (see §5.4).

### 4.3 CMP-UI-05 registry mapping

The requirement body references CMP-UI-05: "a field type registered per CMP-UI-05 after the built-in seed". The registry contract is:

```typescript
// web/src/components/forms/fieldRegistry.ts (new, owned by CMP-UI-05)
import type { ReactNode } from 'react'
import type { UseFormRegisterReturn } from 'react-hook-form'
import type { TaskFormField } from '@/types/forms'

export interface FieldTypeRenderer {
  /** Renders the field's input element(s) WITHOUT the label or hint/error wrappers. */
  renderInput: (args: {
    fieldName: string
    fieldDef: TaskFormField
    register: UseFormRegisterReturn
    ariaDescribedBy?: string
    ariaErrorMessage?: string
    ariaRequired?: boolean
  }) => ReactNode
  /** Returns the attribute set the builtin would set, so the FieldFactory can decorate it. */
  requiredAriaAttributes: ReadonlyArray<'aria-required' | 'aria-describedby' | 'aria-invalid' | 'aria-errormessage'>
}

export const fieldRegistry: Map<string, FieldTypeRenderer> = new Map([
  // Built-in seed (RND-UI-07): string, number, boolean, date, select, textarea, enum
  // Plus a sentinel 'string:email', 'string:date-time', 'string:date' for format-tagged strings.
  // Plus a sentinel 'object:*' that recurses into `properties` — no ARIA on the wrapper.
])
```

**FieldFactory routing (addition to the existing switch):**

```typescript
const renderer = fieldRegistry.get(fieldDef.type) ?? defaultBuiltinRenderer
const element = renderer.renderInput({ fieldName, fieldDef, register, ariaDescribedBy, ariaErrorMessage, ariaRequired })
```

**The AC-5 invariant:** a field type registered via `fieldRegistry.set('my-org.widget', { renderInput, requiredAriaAttributes: ['aria-required', 'aria-describedby', 'aria-invalid', 'aria-errormessage'] })` automatically receives the full attribute set when rendered by `FieldFactory`. No edit to any file under `web/src/pages/**` is required.

## 12. Error taxonomy

This section enumerates every runtime error mode the four requirements' components must handle, by requirement. Each entry names the trigger, the observable surface behaviour, and the test assertion (when applicable). Section 12 cross-references §1.1–§4.3 above and is what the FRONTEND-DEV implementation must wire.

### 12.1 RND-UI-05 (RateLimitBackpressure) error modes

1. **`classifyError()` classification failure (fall-through).** When the classifier cannot put the `ApiError` into `'rate-limit' | 'stale-version' | 'fetch-failure' | 'forbidden' | 'unauthorised' | 'ok'`, control falls through to `'fetch-failure'`. The boundary renders `<FetchError>` (RND-UI-03), which exposes a user-driven Retry button. The user must click it; there is no automatic countdown. **Test:** a synthetic `ApiError { status: 599, details: {} }` is fed into `classifyError`; expected return is `'fetch-failure'`.
2. **429 with no `Retry-After` header.** `classifyError` already returns `'fetch-failure'` when `details.retryAfter == null` (see §1.1, `web/src/utils/classifyError.ts:18-22`). `RateLimitBackpressure` is **not** mounted in this case; the user sees `<FetchError>` with no countdown rendered. **Test:** configure the BPM API fixture to strip `Retry-After`; assert the rendered output is `<FetchError>` and the page does **not** contain `[data-testid="rate-limit-backpressure"]`.
3. **Countdown reaches zero while user navigates away.** The `setInterval` registered in `RateLimitBackpressure`'s `useEffect` MUST be cleared in the cleanup function. When the component unmounts before zero, the interval is cleared and `onRetry` is **never** invoked — the next page owns its own refetch policy. **Test:** drive `<RateLimitBackpressure initialSeconds={5}>` with fake timers; at `t=2`, unmount the component; assert `setInterval` clear mock was called and `onRetry` was **not** called.
4. **Component unmount during countdown.** Same invariant as (3): the cleanup function clears the interval and **never** invokes `onRetry`. The `useRef<boolean>` fired-flag is garbage-collected with the component — it cannot fire across an unmount. **Test:** mount, advance the timer to `initialSeconds - 1`, unmount, assert no `setInterval` tick fires after unmount and `onRetry` is not called.
5. **Multiple `refetch()` invocations from a single countdown.** `firedRef = useRef<boolean>(false)` is consumed exactly once: when the tick handler observes `secondsRemaining === 0 && firedRef.current === false`, it flips the ref to `true`, fires `onRetry()`, and clears the interval. The next interval tick (if it ever lands — it should not) sees `firedRef.current === true` and returns without firing. **Test:** drive a countdown to zero; assert `onRetry` is called **exactly once** even when (a) React strict-mode double-invokes the effect and (b) two ticks both observe `secondsRemaining === 0` (the second sees `firedRef.current === true`).
6. **`Retry-After` value is non-integer (HTTP-date or malformed).** `client.ts` parses the header with `Number(details.retryAfter)`. When the result is `NaN` (HTTP-date like `Retry-After: Wed, 21 Oct 2026 07:28:00 GMT`, or any non-numeric string), the design treats the value as missing and falls back to a **60-second default countdown**. The implementation pattern: `const seconds = Number.isFinite(Number(details.retryAfter)) && Number(details.retryAfter) > 0 ? Number(details.retryAfter) : 60`. The fallback is logged at `console.warn` level so production observability can correlate "fallback fired" with a real misconfigured backend. **Test:** synthesise an `ApiError { status: 429, details: { retryAfter: 'Wed, 21 Oct 2026 07:28:00 GMT' } }`; assert `RateLimitBackpressure` mounts with `initialSeconds=60`.

### 12.2 RND-UI-06 (StaleVersionError / ConflictResolver) error modes

1. **409 without `X-Resource-Version` response header.** `ConflictResolver` receives `conflictVersion == null` (from `error.details.xResourceVersion`). The Merge button renders as `<button disabled aria-disabled="true" data-testid="conflict-merge">`; the two other actions (`Refetch latest`, `Discard mine`) remain enabled. The disabled button must have an `aria-describedby` reference to an inline explanatory node so a screen reader user understands why it is disabled. **Test:** strip `X-Resource-Version` from the backend fixture; assert `[data-testid="conflict-merge"]` is `disabled`, `[data-testid="conflict-refetch"]` and `[data-testid="conflict-discard"]` are enabled.
2. **409 on a non-definition endpoint (instance, task).** `StaleVersionError` is mounted by `QueryStateBoundary` for any `'stale-version'` state regardless of resource type. The `ConflictResolver` interface is identical, but the per-type semantics of `Merge manually` differ: for a `PATCH /api/v1/instances/{id}` 409, the merge saves the version via the same `If-Match`/`version` transport (see §2.3 OQ-3); for a `POST /api/v1/tasks/{id}/complete` 409, the backend treats the task as already-completed and Merge semantically means "acknowledge completion" — the resolver renders the same UI but `onSaveMerged` is wired to call `tasksApi.complete` again (the second 200 will succeed). **Test (per type):** seed two `instance` records and one `task`; drive a 409 against each; assert the same `ConflictResolver` surface mounts, and the merge call hits the correct per-type API.
3. **User dismisses `Discard mine` ConfirmDialog.** `onDiscardConfirmed` is **not** called when the user clicks Cancel. The local draft in `definitionDraftStore` remains intact. No PATCH/PUT is issued. **Test:** open the resolver, click `[data-testid="conflict-discard"]`, click `[data-testid="confirm-dialog-cancel"]`; assert `definitionDraftStore.draft.body.description === <seeded value>` and no `**/api/v1/definitions/**` request is observed between dialog open and cancel.
4. **Network failure during Refetch latest.** When `onRefetch()` throws (or its `refetch()` returns an error), `ConflictResolver` does NOT swallow the error: it surfaces the error via the existing `FetchError` banner (RND-UI-03) — the resolver component itself stays mounted and the local draft remains intact in Zustand. The error is shown above the resolver's modal (not inside it) so the user can read both. **Test:** simulate a network failure during refetch; assert `FetchError` is rendered and `definitionDraftStore.draft.body.description` is still the seeded value.
5. **Server returns 409 with a version BEHIND the current store version.** This is impossible in practice (the server's 409 is by definition a *newer* version than the client's), but the resolver must not crash if the upstream is misbehaving. The `ConflictResolver` shows a `data-testid="conflict-version-mismatch"` banner reading `"Server version is older than local — Discard mine recommended"`. Both `Refetch latest` and `Discard mine` remain enabled; `Merge manually` is **also** enabled (the user might still want to merge against an older version to inspect what changed). **Test:** synthesise an `error.details.xResourceVersion` whose numeric value is < the store's known version; assert the mismatch banner is rendered.

### 12.3 GRD-UI-06 (Accessibility gate) error modes

1. **Keycloak / BPM API / PostgreSQL unreachable.** `verifyBackendReachable()` runs in `beforeAll`. If **any** of the three `fetch` / `pg` probes fails, the gate throws with the message `A11Y GATE BLOCKER: <comma-separated names> unreachable — no surface scanned` — and the test fails with severity `BLOCKER` *before* any surface test runs. The error message names each unreachable service explicitly so the failure is self-explanatory in CI logs. **Test:** stop the BPM API container; assert the gate throws with `BPM-API` in the message; assert NO surface test ran (zero network requests after the probes).
2. **Per-surface 30-second budget exceeded.** Each surface test runs under `test.setTimeout(30_000)`. If the axe call (or any settling logic) exceeds 30s, Playwright aborts the test. The abort surfaces as a distinct `axe-timeout` failure on that single surface — the other surfaces in the run **continue** and their results are still recorded in the YAML report. The YAML report marks the timed-out surface as `{ surface: '<label>', status: 'BLOCKER', reason: 'axe-timeout' }`. **Test:** inject a `setTimeout(() => resolve, 35_000)` into a mocked axe call (test-only); assert the single surface fails with `axe-timeout` and the other five still appear in the report.
3. **Axe scan reports a `serious` violation naming an unknown rule ID.** The gate's failure message already prints `ruleId`, `impact`, `target` (per AC-1). If `ruleId` is one not in axe's known rule catalogue (e.g. a future rule version introduces a new ID that the local `@axe-core/playwright` does not know about), the gate still logs the unknown rule ID and fails the surface. The gate does **not** crash and does **not** swallow the violation. The test report includes the rule ID verbatim so a developer can update the local axe dependency to a version that knows the rule. **Test:** inject a synthetic violation with `ruleId: 'unknown-rule-2099-future'`; assert the gate throws with the ID in the message and the test report YAML contains the same ID.
4. **`color-contrast` rule disabled in axe config.** `a11yConfig.rules` MUST NOT contain `'color-contrast'`. If a future contributor adds it to the disabled set, the `a11yConfig.test.ts` unit test asserts `Object.keys(rules).indexOf('color-contrast') === -1` and fails with `E_CONFIG` severity — this is a CI-level trip-wire independent of the per-surface axe runs. **Test:** mutate `a11yConfig.rules['color-contrast'] = { enabled: false }` in a copy, run the assertion, expect `E_CONFIG` failure.
5. **`tests/reports/report-<date>-<run_id>.yaml` write fails (permission / disk full).** `reportWriter.ts` wraps the YAML write in a `try { fs.writeFileSync(...); } catch (e) { throw new Error(\`A11Y GATE BLOCKER: cannot write report to ${path} — ${e.message}\`); }`. The gate throws `BLOCKER` and **no partial report is written** (the write is atomic — the file is opened with `'w'` and the buffer is `fs.fsyncSync`-ed before close; on failure the file is removed). The surfaces that already ran are NOT re-run on the next attempt — the report YAML records which surfaces were scanned and which were skipped due to the write failure. **Test:** make the report path read-only (`chmod 444`); run the gate; assert `BLOCKER` is thrown and the file does not exist after the failed write.

### 12.4 GRD-UI-07 (FieldFactory ARIA wiring) error modes

1. **Dangling `aria-errormessage` (target id not in DOM).** When the form renders a field with `aria-invalid="true"` and `aria-errormessage="<id>"`, but no node with that `id` exists in the DOM at the same moment, the GRD-UI-06 axe scan fails the surface with the rule `aria-valid-attr-value`. The test additionally asserts the dangling-reference detector (`aria-validator.ts`) catches it before axe runs and throws an error naming the **field key** (e.g. `field 'description': aria-errormessage='description-error' has no target in DOM`). **Test:** inject a field with `aria-errormessage="does-not-exist"`; assert the aria-validator throws with the field key in the message and axe reports the same violation.
2. **`fieldRegistry` lookup miss for a registered type.** `FieldFactory` looks up `fieldRegistry.get(fieldDef.type)`; on a miss, control falls through to `defaultBuiltinRenderer` (the same renderer the existing FieldFactory uses for built-in types). The full attribute set (`aria-required`, `aria-describedby`, `aria-invalid`, `aria-errormessage`) is still emitted — the fall-through path calls the default renderer's `renderInput` with the same `ariaDescribedBy`, `ariaErrorMessage`, `ariaRequired` arguments. The miss is logged at `console.warn` level so an operator can spot a typo in a registered type name. **Test:** set `fieldDef.type = 'org.acme.unregistered'`; assert the rendered DOM carries the full attribute set and a `console.warn` was emitted with the missing type.
3. **`aria-busy=true` cleared after submit settles.** The submit handler in `DynamicFormRenderer` awaits `onSubmit(values)` inside a `try { ... } finally { setIsSubmitting(false); }`. The `aria-busy={isSubmitting}` attribute on the `<form>` is therefore cleared in the `finally` block regardless of whether the submit throws. This is the canonical pattern from React Query's `useMutation` `isPending` semantics. **Test:** mount the form, simulate a successful submit, assert `aria-busy` transitions `true → false`; repeat with a submit that throws, assert the same transition (`aria-busy=true` while pending, `false` in the `finally`).
4. **Field with `required=true` but `form_schema` omitted from the definition.** When the task definition does not carry a `form_schema` field for a given task key, `renderFormField` is still invoked with `fieldDef` whose `required` is `undefined`. Per RFC 8259 (JSON), missing is "not required" — the implementation MUST treat `fieldDef.required == null` as `false` and **omit** the `aria-required` attribute (per §4.1 the attribute is omitted when `required=false`, never set to `"false"`). **Test:** seed a task definition with no `form_schema` for a property; assert the rendered `<input>` does not have an `aria-required` attribute.
5. **Multiple hints on one field.** WAI-ARIA 1.2 §6.6.3 `aria-describedby` accepts a space-separated list of element IDs. When a field has multiple hints (e.g. a description hint + a constraint hint), `aria-describedby` MUST list all hint IDs in order, separated by single spaces — never commas. The implementation pattern: `aria-describedby={[...hints.map(h => h.id)].join(' ')}`. **Test:** render a field with two hint nodes (`description-hint`, `description-constraint`); assert the input's `aria-describedby` attribute value is exactly `"description-hint description-constraint"` (single space, order preserved).
