# ISS-0632 / GH-610 — Extend lint_sql_param_types.py: 42P18 Detection

**Type:** E (novel tool extension — no matching codegen template)
**Issue:** ISS-0632 / https://github.com/tvolodi/R-Co/issues/610
**Files in scope:** `tools/lint_sql_param_types.py`

---

## Module purpose

`tools/lint_sql_param_types.py` currently detects two C42883 patterns but has no rule
for PostgreSQL error **42P18** ("could not determine data type of parameter $N").

42P18 occurs when a `$N` placeholder appears as an argument to a **variadic-any** SQL
function — most commonly `jsonb_build_object()` or `json_build_object()` — and no
explicit type cast (`::text`, `::uuid`, etc.) is present. PostgreSQL cannot resolve the
type at `PREPARE` time and raises the error before the query executes.

This design extends the linter with a new `MAJOR` rule that performs a paren-depth scan
to find bare `$N` parameters inside `jsonb_build_object` / `json_build_object` call
blocks within `.zig` source files. Severity is MAJOR (not BLOCKER) to match the existing
`TEXT_COLUMNS_VS_INT_RE` rule's level and because the ISS-0632 candidate resolution
documents it as MAJOR.

---

## Public interface

The extension adds one new helper and integrates it into the existing `lint_file`
function. No changes to `main()`, `lint_tree()`, or the CLI interface.

```python
# New constant — variadic-any function names that require explicit $N casts
VARIADIC_ANY_FUNCS: frozenset[str]    # {"jsonb_build_object", "json_build_object"}

# New regex — matches bare $N not followed by ::
BARE_PARAM_IN_VARIADIC_RE: re.Pattern  # r'\$(\d+)(?!\s*::)'

# New helper called from lint_file()
def lint_variadic_params(content: str, path: Path) -> list[tuple]:
    """
    Paren-depth scan: find all jsonb_build_object / json_build_object call
    blocks in `content`, then search each block for bare $N params.

    Returns list of (severity, path_str, lineno, message) tuples,
    same shape as the existing lint_file() return value.
    """
```

The return type and format of each finding tuple are identical to the existing rules:

```
("MAJOR", str(path), lineno, "<message text>")
```

`lint_file()` appends the result of `lint_variadic_params(content, path)` to its
`issues` list before returning. All existing rules (`ASYMMETRIC_TEXT_CAST_RE`,
`TEXT_COLUMNS_VS_INT_RE`) remain unchanged.

## Data flow diagram

```
lint_tree(roots)
    └─ for each .zig file → lint_file(path)
           │
           ├─ existing: ASYMMETRIC_TEXT_CAST_RE  (line-by-line)   → BLOCKER findings
           ├─ existing: TEXT_COLUMNS_VS_INT_RE   (line-by-line)   → MAJOR findings
           └─ NEW:  lint_variadic_params(content, path)
                       │
                       ├─ re.finditer(FUNC_CALL_RE, content)
                       │      finds each "jsonb_build_object(" or
                       │      "json_build_object(" occurrence (start offset)
                       │
                       ├─ paren-depth walk from opening paren
                       │      tracks depth (+1 on '(', -1 on ')')
                       │      respects single-quoted string spans
                       │      stops at depth 0 → closing paren offset
                       │
                       ├─ extract block = content[open+1 : close]
                       │
                       └─ re.finditer(BARE_PARAM_IN_VARIADIC_RE, block)
                              for each match:
                                compute lineno from content[:match_offset]
                                append MAJOR finding
```

## Algorithm

### Step 1 — Locate variadic-any call sites

```python
FUNC_CALL_RE = re.compile(
    r'\b(jsonb_build_object|json_build_object)\s*\(',
    re.IGNORECASE,
)
```

Iterate over all matches in the file content. Each match gives the offset of the
opening paren.

### Step 2 — Paren-depth scan to extract the call block

```python
def _extract_paren_block(content: str, open_paren: int) -> int:
    """
    Walk from open_paren (index of '(') to the matching ')'.
    Returns the index of the closing ')' in content.
    Respects single-quoted string spans to avoid counting parens inside strings.
    Returns -1 if the block is unterminated (malformed source).
    """
    depth = 1
    i = open_paren + 1
    in_string = False
    while i < len(content):
        ch = content[i]
        if in_string:
            if ch == "'" and content[i - 1] != "\\":
                in_string = False
        else:
            if ch == "'":
                in_string = True
            elif ch == "(":
                depth += 1
            elif ch == ")":
                depth -= 1
                if depth == 0:
                    return i
        i += 1
    return -1
```

### Step 3 — Bare parameter detection inside the block

```python
BARE_PARAM_IN_VARIADIC_RE = re.compile(r'\$(\d+)(?!\s*::)')
```

Apply to the extracted block content. For each match, compute the absolute line number:

```python
abs_offset = open_paren + 1 + match.start()
lineno = content[:abs_offset].count('\n') + 1
```

Emit one MAJOR finding per bare `$N` occurrence.

### Step 4 — Integration into lint_file()

```python
# At the end of lint_file(), after all existing regex checks:
issues.extend(lint_variadic_params(content, path))
return issues
```

No other changes to `lint_file()`, `lint_tree()`, or `main()`.

## False-positive analysis

| Pattern | Is it flagged? | Reasoning |
|---|---|---|
| `jsonb_build_object('k', $1::text)` | **No** | `::text` is present; negative-lookahead `(?!\s*::)` excludes it |
| `jsonb_build_object('k', $1::uuid)` | **No** | Same — any `::type` suffix suppresses the match |
| `set_config('key', $1, false)` | **No** | `set_config` is not in `VARIADIC_ANY_FUNCS`; fixed-signature function; not scanned |
| `INSERT INTO t VALUES ('a', $1, 'b')` | **No** | Not inside a `jsonb_build_object` call; paren-depth scan does not reach it |
| `jsonb_build_object('k', gen_random_uuid()::text)` | **No** | No `$N` token |
| `ARRAY[$1, $2]` | **No** | `ARRAY[...]` uses brackets, not parens; not reached by paren-depth scan |
| `row($1, $2)` | **No** | `row` not in `VARIADIC_ANY_FUNCS` scope |
| `format('Hello %s', $1)` | **No** | `format` excluded from scope (see Open questions) |
| Nested call: `jsonb_build_object('k', jsonb_build_object('x', $1))` | **Yes** | Inner block is extracted as a separate match; bare `$1` found in inner block |
| Comment line containing `jsonb_build_object('k', $1)` | **No** | Existing comment-skip guard in `lint_file()` already strips `//` lines before the content reaches `lint_variadic_params` |

**Confirmed zero false positives on current codebase** — baseline scan (`scratch/_iss0632_scan.py`)
over `src/` + `tests/` returned zero findings. New rule will exit 0 on the clean codebase.

## Error taxonomy

This module (the linter extension) is a pure Python analysis tool. It does not interact
with PostgreSQL, Zig, or any external service. The only error conditions it can produce
are:

| Error | Handling |
|---|---|
| `OSError` reading a `.zig` file | Existing guard: `except OSError: return issues` (already in `lint_file`) |
| Unterminated paren block (malformed Zig) | `_extract_paren_block` returns `-1`; `lint_variadic_params` skips that occurrence silently |
| `re` module failure | Cannot occur with the patterns used (no back-references, no look-behind with variable width) |

No new exception types are introduced.

## Test cases

Five test cases are required, exercised via `pytest` or by calling `lint_file()` directly
with a temporary in-memory `Path`:

1. **Bare $N triggers MAJOR** — file containing `jsonb_build_object('key', $1)` → linter
   returns one MAJOR finding, `main()` exits 1.

2. **Cast $N is clean** — file containing `jsonb_build_object('key', $1::text)` → linter
   returns no findings, `main()` exits 0.

3. **Multi-line block, bare $N on a different line** — the call spans multiple lines and
   the bare `$N` is not on the same line as `jsonb_build_object` → linter still returns
   MAJOR (paren-depth scan captures the full block regardless of newlines).

4. **Unrelated INSERT is not flagged** — file containing only
   `INSERT INTO t (a, b) VALUES ('lit', $1)` → linter returns no findings.

5. **Regression — current codebase stays clean** —
   `python3 tools/lint_sql_param_types.py src tests` exits 0 (no MAJOR or BLOCKER on the
   existing, already-fixed codebase).

## Open questions

1. **`format()` scope** — The SQL `format()` function is also variadic-any, but it is
   rarely used with bare `$N` parameters in this codebase. Diagnosis confirmed zero
   occurrences in current `src/` + `tests/`. Recommend leaving `format` out of
   `VARIADIC_ANY_FUNCS` for this fix to avoid over-flagging; a follow-up ISS can add it
   if a future violation is found.

2. **`row()` constructor** — PostgreSQL `row($1)` is variadic-any but has no current
   usages with `$N` in this codebase. Leave out of scope for the same reason.
