## 1. Module purpose

This design extends three areas of the BPM Platform kernel:

1. **QRY-05** — Adds a field-level read-grant layer to the entity query surface. Fields a caller has no read grant for are absent (not null, not redacted) from serialised items. Ungranted fields are also excluded from the filter/sort surface for that caller.

2. **SBX-01 + SBX-02** — Introduces the `POST /api/v1/agent/task-specs` endpoint. The endpoint enforces a dual credential gate (scope `agent.submit_task_spec` AND realm role `tenant_orchestrator`), rejects tokens that carry both agent realm roles, and forces the `orchestrator_principal` to the verified token subject before canonicalisation and hashing.

3. **SBX-03** — Introduces `GET /api/v1/agent/sandboxes` (supervisory read) and the sandbox claim endpoint. Orchestrators are allowed supervisory read only; implementers see only their own sandboxes. Claim rejects orchestrator tokens and requires the implementer role.

This check happens inside `authenticate()` during the OIDC path, immediately after role extraction.

### 3.5 `src/api/routes/agent_task_specs.zig` (new module)

```zig
/// POST /api/v1/agent/task-specs
///
/// SBX-01: enforces orchestrator gate.
/// SBX-02: sets orchestrator_principal = auth.user_id before canonicalisation.
/// AGT-04: computes spec_hash = SHA-256 of RFC 8785 canonical JSON of merged doc.
/// AGT-05: rejects rng_seed == 0.
///
/// Successful: HTTP 201, body {"task_spec_id":"<uuid>","spec_hash":"<64hex>"}
/// Failure codes:
///   HTTP 403 "orchestrator_role_required"   (SBX-01: scope or role absent)
///   HTTP 403 "rng_seed_zero"                (AGT-05)  -- note: 400 per AGT-05 req body
///   HTTP 400 "rng_seed_zero"                (AGT-05)
///   HTTP 400 "malformed_json"               (body parse error)
///   HTTP 409 "task_spec_immutable"          (hash collision on existing row)
pub fn handleSubmitTaskSpec(
    allocator: std.mem.Allocator,
    pool: *db.Pool,
    auth: auth_mod.AuthContext,
    body_json: []const u8,
) HandlerResult;
```

**Internal call chain (SBX-02 ordering constraint):**

```
1. requireOrchestratorSubmit(auth)  → gate
2. parseTaskSpecBody(body_json)     → TaskSpecSubmitRequest (strips orchestrator_principal)
3. Validate rng_seed != 0           → HTTP 400 rng_seed_zero
4. Build merged_doc = spec_body_json with orchestrator_principal=auth.user_id injected
5. canonicaliseRfc8785(merged_doc)  → canonical_bytes
6. sha256Hex(canonical_bytes)       → spec_hash (64 lowercase hex chars)
7. upsertTaskSpec(conn, ...) or conflict check
8. appendAudit(TaskSpecSubmitted | TaskSpecSubmissionRejected)
```

Step 4 must overwrite any `orchestrator_principal` key present in the parsed body (SBX-02: silent discard). Step 5 must occur **after** step 4 so the hash covers the server-set principal.

```sql
-- Table: entity_field_restrictions
-- Declares which grant_name a caller must hold to read field_name on entity_key.
-- A field absent from this table is readable by all callers with entity.read grant.
CREATE TABLE IF NOT EXISTS entity_field_restrictions (
    id              UUID    PRIMARY KEY DEFAULT gen_random_uuid(),
    entity_key      TEXT    NOT NULL,
    field_name      TEXT    NOT NULL,
    required_grant  TEXT    NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT uq_efr_entity_field UNIQUE (entity_key, field_name)
);
CREATE INDEX IF NOT EXISTS idx_efr_entity_key
    ON entity_field_restrictions (entity_key);

-- Table: user_entity_grants
-- Records which grant_names a user holds for which entity_key.
-- A row (user_id, entity_key, grant_name) means the user holds that grant.
CREATE TABLE IF NOT EXISTS user_entity_grants (
    id              UUID    PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         UUID    NOT NULL,
    entity_key      TEXT    NOT NULL,
    grant_name      TEXT    NOT NULL,
    granted_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT uq_ueg_user_entity_grant UNIQUE (user_id, entity_key, grant_name)
);
CREATE INDEX IF NOT EXISTS idx_ueg_user_entity
    ON user_entity_grants (user_id, entity_key);
```

**`loadFieldGrants` query contract:**

```sql
-- Returns one row per restricted field for entity_key.
-- LEFT JOIN with user_entity_grants determines whether caller holds each grant.
SELECT
    efr.field_name,
    efr.required_grant,
    (ueg.id IS NOT NULL) AS caller_has_grant
FROM entity_field_restrictions efr
LEFT JOIN user_entity_grants ueg
    ON ueg.user_id = $1::uuid
   AND ueg.entity_key = efr.entity_key
   AND ueg.grant_name = efr.required_grant
WHERE efr.entity_key = $2
```

### 4.2 Migration 1170 — SBX task_specs and agent_sandboxes tables

File: `migrations/1170_sbx_task_specs_agent_sandboxes.sql`

```sql
-- Table: task_specs
-- Immutable once written (AGT-04). spec_hash is the identity key.
CREATE TABLE IF NOT EXISTS task_specs (
    task_spec_id        UUID    PRIMARY KEY DEFAULT gen_random_uuid(),
    spec_hash           CHAR(64) NOT NULL,   -- SHA-256 hex, 64 lowercase chars
    spec_body           JSONB   NOT NULL,    -- canonical spec document with server-set orchestrator_principal
    orchestrator_principal TEXT NOT NULL,   -- == token subject at submission time (SBX-02)
    rng_seed            BIGINT  NOT NULL,    -- uint64 stored as bigint; never 0 (AGT-05)
    created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT uq_ts_hash UNIQUE (spec_hash)
);
CREATE INDEX IF NOT EXISTS idx_ts_orchestrator
    ON task_specs (orchestrator_principal);

-- Table: agent_sandboxes
-- Represents sandbox slots provisioned for a tenant.
-- Ownership columns are null until claimed (SBX-04).
CREATE TABLE IF NOT EXISTS agent_sandboxes (
    sandbox_id          UUID    PRIMARY KEY DEFAULT gen_random_uuid(),
    status              TEXT    NOT NULL DEFAULT 'unclaimed'
                                CHECK (status IN ('unclaimed','claimed','released','failed')),
    owner_principal     TEXT,               -- null until claimed
    task_spec_id        UUID    REFERENCES task_specs(task_spec_id),
    claimed_at          TIMESTAMPTZ,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at          TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    -- SBX-04: one sandbox per (principal, task_spec) pair
    CONSTRAINT ux_sandbox_owner UNIQUE (owner_principal, task_spec_id)
);
CREATE INDEX IF NOT EXISTS idx_as_owner
    ON agent_sandboxes (owner_principal);
CREATE INDEX IF NOT EXISTS idx_as_status
    ON agent_sandboxes (status);
```

## 5. Data flow

### 5.1 QRY-05: Field-stripped entity query

```
POST /api/v1/entities/{entity_key}/query
  │
  ├─ [existing] authenticate()              → AuthContext (user_id, role, …)
  ├─ [existing] validateEntityKey()
  ├─ [existing] checkEntityRegistered()     → bool (deny → emptyEnvelope, QRY-04)
  ├─ [existing] parseRequest()              → EntityQueryRequest
  ├─ [existing] loadAllowlist()             → EntityAllowlist (all fields)
  │
  ├─ [NEW QRY-05] loadFieldGrants()         → FieldGrantSet
  │     reads entity_field_restrictions + user_entity_grants for caller
  │     produces: granted_fields[], denied_fields[]
  │
  ├─ [NEW QRY-05] narrowAllowlist()         → EntityAllowlist (caller-visible only)
  │     removes denied_fields from the allowlist
  │     filter/sort validation now naturally rejects ungranted fields
  │     with existing HTTP 400 filter_field_not_allowlisted path
  │
  ├─ [existing] query_compiler.compile()    → CompiledQuery (using narrow_al)
  ├─ [existing] conn.query()               → raw rows
  │
  ├─ [NEW QRY-05] serialiseRowsWithStripping()
  │     for each row: stripDeniedFields(row_json, denied_fields)
  │     denied keys are absent from output JSON (not null, not empty)
  │     record_id is never stripped regardless of denied list
  │
  └─ [existing] appendQueryAudit(), build response envelope
```

**Key invariants:**
- `loadFieldGrants` is called only after entity registration is confirmed (QRY-04 gate already passed)
- `narrowAllowlist` must be called before `compile` — the compiler uses the narrowed allowlist
- `stripDeniedFields` must be called after query execution, not before — it operates on the raw row JSON
- If `FieldGrantSet.denied_fields` is empty (no restrictions or all grants held), `serialiseRowsWithStripping` is a pass-through

### 5.2 SBX-01 + SBX-02: Task-spec submission

```
POST /api/v1/agent/task-specs
  │
  ├─ authenticate()
  │   ├─ Parse JWT realm_access.roles → populate auth.agent_realm_roles
  │   ├─ Parse JWT scope claim (space-split) → populate auth.token_scopes
  │   └─ [SBX-01 conflict gate] both tenant_orchestrator + tenant_implementer present?
  │         → HTTP 403 conflicting_agent_roles (before handler)
  │
  ├─ handleSubmitTaskSpec()
  │   ├─ requireOrchestratorSubmit(auth)
  │   │     scope "agent.submit_task_spec" present? AND role tenant_orchestrator present?
  │   │     either absent → HTTP 403 orchestrator_role_required
  │   │     → appendAudit(TaskSpecSubmissionRejected, principal, tenant, missing_credential)
  │   │
  │   ├─ parseTaskSpecBody(body_json)         → TaskSpecSubmitRequest
  │   │     silently discard orchestrator_principal key from body (SBX-02)
  │   │     extract rng_seed; reject 0 or absent → HTTP 400 rng_seed_zero
  │   │
  │   ├─ merge orchestrator_principal = auth.user_id into spec document
  │   │
  │   ├─ canonicaliseRfc8785(merged_doc)      → canonical_bytes
  │   │     RFC 8785: sorted keys, no insignificant whitespace, canonical numbers
  │   │
  │   ├─ sha256Hex(canonical_bytes)           → spec_hash (64 hex chars)
  │   │
  │   ├─ INSERT INTO task_specs … ON CONFLICT (spec_hash) DO NOTHING RETURNING task_spec_id
  │   │     conflict (same hash exists) → HTTP 409 task_spec_immutable
  │   │
  │   └─ appendAudit(TaskSpecSubmitted, actor=auth.user_id, orchestrator_principal, spec_hash)
  │         → HTTP 201 {"task_spec_id":"…","spec_hash":"…"}
```

**SBX-02 ordering constraint:** The merge of `orchestrator_principal = auth.user_id` (step 3 above) must precede `canonicaliseRfc8785` (step 4). No code path may hash a document that still carries a client-supplied principal.

### 5.3 SBX-03: Sandbox list and claim

```
GET /api/v1/agent/sandboxes
  │
  ├─ authenticate() (role + agent_realm_roles populated)
  │
  ├─ handleListSandboxes()
  │   ├─ has tenant_orchestrator? → SELECT all sandboxes WHERE tenant (no owner filter)
  │   ├─ has tenant_implementer?  → SELECT WHERE owner_principal = auth.user_id
  │   └─ neither role?            → HTTP 403 "agent_role_required"
  │   → HTTP 200 {items:[…], next_cursor:…}  (keyset cursor on created_at, sandbox_id)

POST /api/v1/agent/sandboxes/{sandbox_id}/claim
  │
  ├─ authenticate()
  │
  ├─ handleClaimSandbox()
  │   ├─ has tenant_orchestrator?         → HTTP 403 orchestrator_may_not_claim
  │   │   → appendAudit(SandboxClaimRejected, principal, sandbox_id, "orchestrator_may_not_claim")
  │   ├─ not has tenant_implementer?      → HTTP 403 implementer_role_required
  │   │   → appendAudit(SandboxClaimRejected, principal, sandbox_id, "implementer_role_required")
  │   ├─ parseClaimBody → task_spec_id
  │   ├─ UPDATE agent_sandboxes
  │   │     SET status='claimed', owner_principal=$1, task_spec_id=$2, claimed_at=NOW()
  │   │     WHERE sandbox_id=$3 AND status='unclaimed'
  │   │     ON CONFLICT (owner_principal, task_spec_id) → HTTP 409 sandbox_already_claimed
  │   │     (response body MUST NOT name current owner — no SELECT before UPDATE)
  │   └─ HTTP 201
```

**Orchestrator sandbox execution barrier (SBX-03 AC4):** Any route that performs a sandbox execution action (not just claim) must call `requireImplementerExecution(auth)` as the first gate. This applies to all future sandbox execution routes registered under `/api/v1/agent/sandboxes/{sandbox_id}/…` except `GET`.

## 6. Error taxonomy

### 6.1 QRY-05 errors

| HTTP | Code | Condition |
|------|------|-----------|
| 400 | `filter_field_not_allowlisted` | Filter or sort on a field the caller has no read grant for (reuses existing code from QRY-02 path) |

### 6.2 SBX-01 errors

| HTTP | Code | Condition |
|------|------|-----------|
| 403 | `orchestrator_role_required` | Either `agent.submit_task_spec` scope or `tenant_orchestrator` role is absent |
| 403 | `conflicting_agent_roles` | Token carries both `tenant_orchestrator` and `tenant_implementer` |

### 6.3 SBX-02 errors

| HTTP | Code | Condition |
|------|------|-----------|
| 400 | `malformed_json` | Request body is not valid JSON |
| 400 | `rng_seed_zero` | `rng_seed` is 0 or absent |
| 409 | `task_spec_immutable` | A `task_specs` row with the same `spec_hash` already exists |

### 6.4 SBX-03 errors

| HTTP | Code | Condition |
|------|------|-----------|
| 403 | `orchestrator_may_not_claim` | Caller holds `tenant_orchestrator` role at claim/execution endpoint |
| 403 | `implementer_role_required` | Caller holds neither agent realm role at claim/execution endpoint |
| 403 | `agent_role_required` | Caller holds neither agent realm role at list endpoint |
| 409 | `sandbox_already_claimed` | Unique constraint `ux_sandbox_owner` violation (body must not name current owner) |

## 8. Canonical JSON (RFC 8785) contract

SBX-02 requires `spec_hash` to be computed over the RFC 8785 canonical form. The canonicalisation function must be implemented in a new module or added to an existing utility:

**Module:** `src/crypto/canonical_json.zig` (new)

```zig
/// Produce the RFC 8785 canonical JSON serialisation of a parsed JSON value.
/// Rules:
///   - Object keys sorted lexicographically by Unicode code point
///   - No insignificant whitespace
///   - Numbers: integers as-is; floats per RFC 8785 §3.2.2.3 (no trailing zeros,
///     no exponent for values representable as integers)
/// Returns a heap-allocated UTF-8 byte slice. Caller frees.
pub fn canonicalise(
    allocator: std.mem.Allocator,
    value: std.json.Value,
```

## 10. Open questions

None — all ambiguities resolved against the requirement bodies as documented. The `sandbox_already_claimed` response body must not name the current owner (SBX-04 AC2); the claim handler achieves this by using a single `UPDATE … ON CONFLICT` without a prior `SELECT`, so the current owner is never read into the handler and cannot appear in the response.

**Note for BACKEND-DEV:** The `rng_seed` field is a `uint64` in the spec. PostgreSQL's `BIGINT` is a signed 64-bit integer. The handler must accept values up to `2^63 - 1` via standard JSON integer parsing and store them directly. Values between `2^63` and `2^64 - 1` are not representable in standard JSON integer form without loss; if the spec body carries such a value it will arrive as a float or number_string and the parser must reject it as malformed (not as `rng_seed_zero`). This edge case is not covered by the current acceptance criteria but may need a future clarification from REQ-ANALYST.
