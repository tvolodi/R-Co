## 3. Root causes fixed

### 3.1 TC-ADP-09-01 — pg_proc query not schema-qualified

`tests/integration/adp09_tamper_evident_audit_chain_test.zig`'s catalog query
for the three chain-hash functions filtered only by `proname IN (...)` with no
`pg_namespace` join. Since the migration runner creates a private copy of
these functions in every provisioned tenant schema (`tenant_default` and every
`tenant_<uuid>`), the query matched N×3 rows instead of exactly 3. Fixed by
joining `pg_namespace` and filtering `nspname = 'tenant_default'` (the schema
this test's harness actually operates against).

### 3.2 Stale UUID-typed function overloads (migration 1141)

`migrations/1107_fix_audit_chain_text_resource_id.sql` intended to drop the
UUID-typed overloads of `bpm_audit_compute_chain_hash` and
`bpm_audit_chain_canonical_payload` (originally created by
`035_adp09_tamper_evident_audit_chain.sql` with a 13th parameter
`p_trace_id TEXT DEFAULT NULL`) before recreating TEXT-typed replacements. Its
`DROP FUNCTION IF EXISTS ...(UUID,UUID,UUID,TEXT,TEXT,UUID,TIMESTAMPTZ,JSONB,
JSONB,UUID,JSONB,TEXT)` statements listed only 12 argument types, omitting the
13th `p_trace_id TEXT` — since `DROP FUNCTION` matches by exact parameter-type
list, this silently no-opped (`NOTICE: function ... does not exist, skipping`)
instead of dropping anything. The UUID-typed overload survived, producing
duplicate function matches on catalog queries and general signature ambiguity.

Fixed by `migrations/1141_iss0645_audit_chain_function_overload_cleanup.sql`,
which drops both stale overloads using the correct, complete 13-arg signature.
Unqualified/all_schemas scope, so it runs once per schema via the standard
migration-runner mechanism.

### 3.3 TC-ADP-09-02/03/04 and xc02's 5 tests — session_replication_role never restored

`TestHarness.init()` (`tests/integration/helpers.zig`) sets
`session_replication_role = 'replica'` session-wide (GH-402/ISS-0601) so
`resetTestData()` can `DELETE` from `audit_entries` without tripping the
immutability guard trigger. This setting is **never restored** before the
test body runs, so it also suppresses `trg_bpm_audit_apply_chain_hash` for
every direct `INSERT INTO audit_entries` a test performs — `chain_hash` and
`payload_full` never get computed by the trigger; they stay whatever the
`INSERT` explicitly set (typically `NULL`).

This is not a new defect class: `tests/integration/audit_chain_utf8_test.zig`
already documents and fixes the identical issue (ISS-0149/GH-465), and
`tests/integration/svc01_service_catalog_scope_test.zig` uses the same
pattern. The precedented fix — scope
`SET session_replication_role = 'origin'` around the specific `INSERT`(s) that
need the trigger, then restore `'replica'` immediately after — was applied to:
- `adp09_tamper_evident_audit_chain_test.zig` TC-ADP-09-02, TC-ADP-09-03, and
  the boundary-row insert in TC-ADP-09-04.
- `xc02_audit_immutability_test.zig`'s shared `insertAuditEntry()` helper
  (covers TC-XC-02-01/03/04/05/06).

### 3.4 TC-ADP-09-05 and xc02's TC-XC-02-02/07 — `::uuid` cast on a TEXT parameter

Both files called `bpm_audit_compute_chain_hash(...)` directly with the 6th
positional argument (`p_resource_id`) cast `::uuid`. Since GBL-081/1107 widened
`audit_entries.resource_id` (and the function's own parameter) to `TEXT`,
Postgres has no implicit UUID→TEXT cast, so this call matched no overload
(`function bpm_audit_compute_chain_hash(uuid, ..., uuid, ...) does not exist`)
once section 3.2's stale UUID overload was removed. Fixed by dropping the
`::uuid` cast so the literal resolves via Postgres's `unknown`-literal
coercion to the canonical TEXT-typed signature.

### 3.5 adp10's missing payload_full auto-population (migration 1142, layer 1 of 2)

`036_adp10_agent_io_capture_audit.sql` and
`059_fix_audit_chain_trigger_args.sql` both included this block in
`bpm_audit_apply_chain_hash()`, executed before the chain-hash computation:

```sql
IF NEW.payload_full IS NULL AND bpm_audit_is_agent_actor(NEW.tenant_id, NEW.actor_id) THEN
    NEW.payload_full := bpm_audit_build_agent_payload_full(...);
END IF;
```

`1107_fix_audit_chain_text_resource_id.sql` rewrote
`bpm_audit_apply_chain_hash()` from scratch to add UTF-8-safety guarding
around `NEW.resource_id`, carrying forward the pipeline_run_id backfill and
the advisory-lock/predecessor-lookup/chain-hash logic — but never re-added
the block above. Every schema whose trigger has run since 1107 silently
stopped populating `payload_full` for agent actors. Confirmed the CURRENT
active `bpm_audit_apply_chain_hash()` (via `pg_proc.prosrc`) has no reference
to `bpm_audit_is_agent_actor` or `bpm_audit_build_agent_payload_full` at all.

### 3.6 adp10's stale UUID-typed `bpm_audit_build_agent_payload_full` (migration 1142, layer 2 of 2)

Restoring 3.5's call site alone raises `42883 function ... does not exist`:
`bpm_audit_build_agent_payload_full`'s 5th parameter (`p_resource_id`) was
never updated from `UUID` to `TEXT` alongside the rest of the resource_id-TEXT
migration (section 3.2/GBL-081/1107). `NEW.resource_id` inside the trigger is
firmly TEXT-typed with no available implicit UUID coercion (unlike a bare
string literal in an ad-hoc call, which Postgres treats as `unknown` and
freely coerces). Fixed in the same migration: drop the stale UUID-typed
overload (verified against `pg_get_function_identity_arguments()`, not
1107's under-specified pattern) and recreate with `p_resource_id TEXT`, body
otherwise unchanged from 036.

`migrations/1142_iss0645_restore_adp10_payload_full_trigger.sql` applies both
fixes together, since TC-ADP-10-02 needs both layers to pass.

## 4. Known-incomplete: adp10's concurrent-suite reversion (forwarded, GH-651/ISS-0646)

Both 1142 layers are independently verified correct via direct `psql` against
freshly migrated, workspace-owned probe databases (multiple times). However,
under the full ~40-binary concurrent `zig build test-integration` suite,
`tenant_default`'s `bpm_audit_apply_chain_hash()` function body reverts to the
pre-1142 shape by the time TC-ADP-10-02 runs, with no corresponding new
`schema_migrations` ledger row. This is a distinct, deep, pre-existing
test-infrastructure race in the per-tenant migration-reconciliation path
(`tests/integration/helpers.zig` `runMigrationsForSchema` →
`Migrations.runForSchema(..., force_reconcile=true)`), not a defect in the
migration content itself. Full analysis and reproduction steps in
`docs/issues/ISS-0646.json` / GH-651. Not fixed in this pass — out of budget
and architecturally a separate, cross-cutting concern from ISS-0645's
file-triage scope.
