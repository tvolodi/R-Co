# Module: api-tracing

**Covers:** API-09 (Request tracing), OBS-01 (structured logging carries trace_id)
**Files:**
- `src/api/middleware/trace.zig` — trace middleware (new)
- `src/api/trace_context.zig` — thread-local trace ID store (new, shared by trace.zig and errors.zig)
- `src/api/errors.zig` — extend `ProblemDetails` with `trace_id` field; update `serialise()`
**Depends on:** `src/api/errors.zig`, `src/api/response.zig`, `src/api/api_mod.zig`, `src/api/middleware/auth.zig`

---

## Module purpose

Every platform request must be assigned a UUID v4 `trace_id` before any other processing occurs. This trace ID is:

1. Propagated from the incoming `X-Trace-Id` request header if present (any string value, no validation).
2. Otherwise freshly generated using `std.crypto.random`.
3. Stored in a per-thread context so all log entries and error responses within that request carry the same value.
4. Returned in the `X-Trace-Id` response header on every response, including HTTP 401 auth failures.
5. Embedded in the `trace_id` field of every RFC 9457 error response body.

The trace middleware runs **first** in the middleware chain — before auth, content-type, validation, RBAC, and rate-limit — so that even authentication failures are traceable.

## Public types

### `src/api/trace_context.zig`

```zig
/// Thread-local storage for the current request's trace ID.
/// Owned by the trace middleware; reads are safe from any module
/// that imports trace_context.zig.
///
/// The slice points into a per-request heap allocation managed by
/// the trace middleware.  Accessing get() outside an active request
/// returns an empty slice.
pub threadlocal var _current: []const u8 = "";

/// Return the active trace ID for the current thread.
/// Returns "" if no request is in progress on this thread.
pub fn get() []const u8;

/// Set the active trace ID.  Called only by trace.zig at request start.
pub fn set(id: []const u8) void;

/// Clear the active trace ID.  Called only by trace.zig after response is sent.
pub fn clear() void;
```

> **Invariant:** `_current` always points to a valid (possibly zero-length) UTF-8 string. It is never a dangling pointer. The trace middleware must `clear()` before freeing the backing allocation.

## Public functions

### `src/api/middleware/trace.zig`

```zig
/// Extract the trace ID from the X-Trace-Id request header,
/// or generate a new UUID v4 if the header is absent or empty.
///
/// Rules:
///   - If x_trace_id_header is non-null and non-empty: propagate as-is.
///     No UUID validation is performed on the incoming value.
///   - Otherwise: generate a UUID v4 using std.crypto.random.
///
/// The returned slice is owned by the caller.
/// Caller must allocator.free(result.trace_id) when done.
pub fn extractOrGenerate(
    allocator: std.mem.Allocator,
    x_trace_id_header: ?[]const u8,
) error{OutOfMemory}!TraceIdResult;

/// Generate a UUID v4 string (36 chars) into the provided buffer.
/// No allocation.  buf must be at least UUID_V4_LEN bytes.
///
/// Randomness source: std.crypto.random.bytes() (CSPRNG).
/// Version bits  : bytes[6] = (bytes[6] & 0x0f) | 0x40
/// Variant bits  : bytes[8] = (bytes[8] & 0x3f) | 0x80
///
/// Output format: xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx
pub fn generateUuidV4(buf: *[UUID_V4_LEN]u8) void;
```

> **Note:** `apply()` (the actual middleware hook) is defined by the HTTP server framework convention. Its signature depends on the server integration layer (not yet designed). The functions above are the testable, framework-independent core of this module.

/// Serialise a ProblemDetails value to a JSON []u8.
/// The trace_id field in the output is resolved as follows:
///   1. If pd.trace_id is non-empty: use pd.trace_id.
///   2. Else: use trace_context.get() (the thread-local for the current request).
///   3. If both are empty: emit trace_id as "".

## State transitions

Not applicable. This module is stateless per-request; the only mutable state is the thread-local `trace_context._current`.

---

## Key invariants

1. **First in chain.** The trace middleware MUST be invoked before `auth.zig`, `content_type.zig`, `validate.zig`, RBAC, and rate-limit. Any 401 or 403 produced by a later middleware will find a valid trace ID in `trace_context.get()`.

2. **Trace ID always returned.** The `X-Trace-Id` response header is set even when auth fails (HTTP 401) or the server encounters an internal error (HTTP 500). The response-header injection happens in the trace middleware's post-response step, after `next()` returns.

3. **No validation on propagated IDs.** If the caller sends `X-Trace-Id: not-a-uuid`, the platform uses `"not-a-uuid"` as the trace ID. No rejection, no truncation.

4. **Thread safety.** `trace_context._current` is declared `threadlocal` — safe for a multi-threaded HTTP server where each connection is handled on a dedicated thread.

5. **No sensitive data in trace IDs.** The trace middleware MUST NOT log the incoming token or any request body while setting up the trace context.

6. **Clean-up on every path.** `trace_context.clear()` and `allocator.free(trace_id)` MUST be called in `defer` (or `errdefer`) immediately after `set()`, so the thread-local is never stale if the request panics or returns an error.

## Integration notes

### 1. Middleware chain registration order

The HTTP server assembly (future `src/api/server.zig`) MUST register middlewares in this order:

```
1. trace.zig      ← NEW — must be first
2. auth.zig
3. content_type.zig
4. validate.zig
5. rbac.zig       (future)
6. ratelimit.zig  (future)
7. audit.zig      (future)
```

### 2. Changes to `src/api/errors.zig`

Two changes required:
- Add `trace_id: []const u8 = ""` to `ProblemDetails` (backward-compatible default).
- Update `serialise()` to append `,"trace_id":"<value>"` using `trace_context.get()` (or `pd.trace_id` if explicitly set).

No changes needed to the constructor helpers (`problemBadRequest`, etc.) — they all use the default `trace_id = ""` and `serialise()` will substitute the thread-local automatically.

### 3. `src/api/api_mod.zig` exports

Add:
```zig
pub const trace_context = @import("trace_context.zig");
pub const trace_middleware = @import("middleware/trace.zig");
```

### 4. OBS-01 logging integration

The future `src/obs/logger.zig` MUST import `trace_context.zig` and call `trace_context.get()` for the `trace_id` field of every log entry. Background tasks (scheduler, timer poller) MUST generate their own trace ID at task-start and call `trace_context.set()` / `trace_context.clear()` around the task body (per OBS-01 edge case).

### 5. X-Trace-Id response header injection

Since `HandlerResult` currently only carries `status_code` and `body`, the HTTP server layer must be responsible for writing the `X-Trace-Id` response header from `trace_context.get()` after calling the middleware chain. The trace middleware does NOT need to modify `HandlerResult`. This keeps `HandlerResult` unchanged and avoids adding a `headers` map.

> **Open question 1 (see below):** If `HandlerResult` later grows a `headers` map, the trace middleware should populate it instead. Coordinate with BACKEND-DEV.

## Open questions

1. **HandlerResult headers map.** The current `HandlerResult` struct has no `headers` field. The `X-Trace-Id` response header must be written by the HTTP server layer reading from `trace_context.get()` after the handler returns. If a `headers` map is added to `HandlerResult` in the future (e.g. for `Location` headers on 201), the trace middleware should be updated to set `X-Trace-Id` there instead. No blocker for initial implementation.

2. **Maximum propagated trace ID length.** The requirement says propagated `X-Trace-Id` values are accepted as-is (no validation). The design uses a heap-allocated copy of the incoming header value. BACKEND-DEV should impose a reasonable upper bound (e.g. 256 bytes) on the accepted header length to prevent memory exhaustion from malicious callers. Flag for security review.

3. **Background-task trace IDs.** OBS-01 requires background tasks (scheduler, timer poller) to carry a trace ID. The current design does not specify who generates these IDs or how the scheduler passes them to `trace_context.set()`. BACKEND-DEV should resolve this when implementing OBS-01 / the scheduler.
