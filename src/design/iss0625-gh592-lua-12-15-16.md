## 1. Module purpose

This artefact closes three MUST requirements that ISS-0169 tranche 1 (PR #505)
explicitly deferred:

- **LUA-12** — `platform.call_service` becomes a real function: in simulation
  it goes through the simulation interceptor (unchanged surface) **after** the
  service id is validated against the catalog; outside simulation it performs
  a real HTTP call against `RegisteredService.endpoint_url` and returns a
  single response table per design §17.1.
- **LUA-15** — `platform.fail` writes its reason/details/explicit-failure
  discriminator into `LUA_REGISTRYINDEX` (the channel host_context.zig uses for
  the ExecutionContext pointer), never into `_G`. The executor reads the
  discriminator back in the failed-pcall branch and stamps
  `ScriptResult.error_kind = .ExplicitFailure` (vs `.RuntimeError`).
- **LUA-16** — Uncaught runtime errors (after the LUA-15 discriminator has
  classified them as **not** explicit failures) are walked through
  `lua_getstack`/`lua_getinfo` to build a stack-trace string; an
  `events.ScriptErrorPayload` is constructed **conditionally** on the LUA-08
  instruction-count source being installed in the same run, and surfaced on
  `ScriptResult.script_error` (a new optional field).

## 2. Public interface

### 2.1 `ScriptResult` (modified) — `src/lua/executor.zig`

```zig
pub const ScriptResult = struct {
    success: bool,
    value: ?ScriptValue,
    error_message: ?[]const u8,
    /// LUA-07: verified manifest hash, null on plain `executeScript`.
    manifest_hash: ?[32]u8 = null,
    /// LUA-15: discriminator between runtime Lua errors, explicit
    /// `platform.fail` calls, and load-time compile failures. `.Success`
    /// is the only kind that has `value` set; the others have
    /// `error_message` set.
    error_kind: ErrorKind = .Success,
    /// LUA-16: populated only when `error_kind == .RuntimeError` AND the
    /// LUA-08 instruction-count source was installed in this run. Null
    /// otherwise (the executor records the skip reason in the payload's
    /// `capabilities_at_failure` slot — see §6).
    script_error: ?events.ScriptErrorPayload = null,

    pub fn deinit(self: *ScriptResult, allocator: std.mem.Allocator) void {
        if (self.error_message) |msg| allocator.free(msg);
        if (self.value) |val| val.deinit(allocator);
        if (self.script_error) |*payload| payload.deinit(allocator);
    }
};

/// LUA-15 / LUA-16 discriminator.
///
/// The order matters: `.Success` first because that is the common path,
/// and the switch in `executeSource` must be exhaustive over all four
/// without a fallthrough. `.CompileError` covers both bytecode rejection
/// and `luaL_loadbuffer` failures; `.RuntimeError` covers everything
/// `lua_pcall` reports; `.ExplicitFailure` is set only when the LUA-15
/// discriminator reads `__explicit_failure__` truthy from the registry.
pub const ErrorKind = enum {
    Success,
    CompileError,
    RuntimeError,
    ExplicitFailure,
};
```

**Compatibility note (D-2):** `ScriptResult` gains two new fields, both with
defaults. Existing callers that destructure `success` / `value` /
`error_message` are unchanged. Existing callers that pattern-match on
`ScriptResult` exhaustively (none in the current source tree per
`grep_search`) will need to add `.ExplicitFailure` and `.CompileError`.

### 2.2 `ExecutionContext` (extended) — `src/lua/executor.zig`

```zig
pub const ExecutionContext = struct {
    allocator: std.mem.Allocator,
    capabilities: *const capabilities.CapabilitySet,
    instance_id: []const u8,
    actor_id: []const u8,
    /// LUA-07. Set by `executeScriptWithManifest` to the verified hash of the
    /// manifest that granted `capabilities`. Null on the plain `executeScript`
    /// path.
    manifest_hash: ?[32]u8 = null,
    /// LUA-12 (D-1). The catalog a real (non-simulation) `call_service`
    /// consults. Caller-owned, must outlive the context (CTX-1 invariant).
    /// `.lookup(svc_id)` is the only call site this introduces on this
    /// field. The simulation path also reads it (defense-in-depth — §3.3).
    service_catalog: ?*const service_catalog.ServiceCatalog = null,
    /// LUA-16 (D-3). Pointer to the limiter the executor reads after a
    /// failed pcall to populate `ScriptResult.script_error.instruction_count`.
    /// If null, the payload's `instruction_count` is 0 and the executor
    /// stamps `capabilities_at_failure` with a literal `skip_reason`
    /// describing why. The pointer is set by `executeScript` itself, not
    /// the caller, because `executeSource` is what installs the hook
    /// when LUA-08 lands in the same run.
    instruction_limiter: ?*const instruction_limiter.InstructionLimiter = null,
};
```

**Backward compatibility:** all new fields have defaults (`null`). Existing
test sites that construct an `ExecutionContext` continue to work without
change. The sibling batch (ISS-0624 / GH-591) may add its own fields
(`pending_writes`, `StructuredLogger`, `trace_id`); those are out of scope
here and will be merged when both branches land.

### 2.3 New private API on `host_context.zig` — failure-channel helpers

```zig
/// Private registry keys for LUA-15. Same channel as REGISTRY_KEY: not in
/// `_G`, not in upvalues, not script-reachable (no debug/package). Each key
/// holds a Lua string (reason/details) or boolean (explicit flag) on the
/// registry table.
pub const FAILURE_REASON_KEY: [*:0]const u8 = "bpm.failure_reason";
pub const FAILURE_DETAILS_KEY: [*:0]const u8 = "bpm.failure_details";
pub const FAILURE_EXPLICIT_KEY: [*:0]const u8 = "bpm.explicit_failure";

/// Set the explicit-failure discriminator. Called by `platform.fail` before
/// raising.
pub fn setExplicitFailure(
    L: *bindings.LuaState,
    reason: []const u8,
    details_kind: DetailsKind,
) void;

/// Read back the discriminator. Called by `executeSource` in the failed-pcall
/// branch. Returns `.None` if no value is set (script raised without going
/// through `platform.fail` — a genuine runtime error).
pub fn readExplicitFailure(L: *bindings.LuaState, allocator: std.mem.Allocator) ExplicitFailureView;

/// Clear the discriminator. Called by `executeSource` immediately after
/// reading, so a subsequent `platform.fail` from the same script does not
/// inherit stale state. (pCalls inside the script do not re-enter the
/// executor's failed branch, so this is mostly belt-and-braces, but the
/// invariant is cheap to maintain.)
pub fn clearExplicitFailure(L: *bindings.LuaState) void;

pub const DetailsKind = enum { None, Table };
pub const ExplicitFailureView = struct {
    kind: enum { None, Explicit },
    reason: ?[]const u8,        // owned copy; nil if kind == .None
    details: ?events.ScriptFailureDetails, // owned copy; nil if kind == .None
};
```

`events.ScriptFailureDetails` is a small `union` over the details kinds
currently supported (`nil`, `table`). Mirrors `executor.ScriptValue` for the
"details" sub-shape only; the `ScriptFailedPayload` in `events.zig` already
references `executor.ScriptValue` for `details` (kept).

### 2.4 `events.zig` extensions

```zig
/// LUA-15 payload. Already typed; what changes is **construction**, not
/// definition. `deinit` is unchanged.
pub const ScriptFailedPayload = struct {
    reason: []const u8,
    details: ?executor.ScriptValue,
};

/// LUA-16 payload. Already typed; what changes is **construction**.
pub const ScriptErrorPayload = struct {
    error_message: []const u8,
    stack_trace: []const u8,
    instruction_count: u64,
    memory_peak_bytes: u64,
    capabilities_at_failure: []const u8,

    pub fn deinit(self: *ScriptErrorPayload, allocator: std.mem.Allocator) void {
        allocator.free(self.error_message);
        allocator.free(self.stack_trace);
        allocator.free(self.capabilities_at_failure);
        // instruction_count and memory_peak_bytes are scalars.
    }
};
```

`EventRecord.deinit` already covers both payload variants — no change.

### 2.5 New `events.zig` constructor (LUA-15/LUA-16 surface)

```zig
/// LUA-15: build a `ScriptFailedPayload` from the explicit-failure view the
/// host_context helpers return. Owns the copies inside.
pub fn buildScriptFailedPayload(
    view: host_context.ExplicitFailureView,
    allocator: std.mem.Allocator,
) !ScriptFailedPayload;

/// LUA-16: build a `ScriptErrorPayload` from the captured stack trace and the
/// instruction limiter (if any). Owns the copies inside. If the limiter is
/// null, sets `instruction_count = 0`, `memory_peak_bytes = 0`, and writes
/// `capabilities_at_failure = "skip: instruction_count source not installed
/// (LUA-08 deferred)"` (D-3).
pub fn buildScriptErrorPayload(
    error_message: []const u8,
    stack_trace: []const u8,
    limiter: ?*const instruction_limiter.InstructionLimiter,
    capabilities_summary: []const u8,
    allocator: std.mem.Allocator,
) !ScriptErrorPayload;
```

The `executor.executeSource` raises these only on **its own** failed-pcall
path. The engine-side worker (outside the executor) reads
`ScriptResult.script_error` and emits the event — per transition.zig
precedent that `src/lua/` performs no I/O.

## 3. Data flow

### 3.1 LUA-15: structured failure flow

```
   Lua script                  platform.fail                executor.executeSource
   ───────────                  ──────────────                ────────────────────────
   platform.fail(                1. read reason (arg 1)
     "Insufficient              2. setExplicitFailure(
     balance",                     L, reason,
     {provider="stripe"})          DetailsKind.Table, details)
                                 3. raiseMessage(L, reason)
                                     └─► longjmp to nearest pcall
                                                  │
                                                  ▼
                                       call_status != 0
                                       1. readExplicitFailure(L, allocator)
                                          → ExplicitFailureView { .Explicit, reason, details }
                                       2. buildScriptFailedPayload(view, allocator)
                                          → ScriptFailedPayload
                                       3. clearExplicitFailure(L)
                                       4. ScriptResult {
                                            .success = false,
                                            .error_kind = .ExplicitFailure,
                                            .error_message = dupe(reason),
                                            .script_error = null,   // no stack trace
                                          }
```

### 3.2 LUA-16: runtime-error flow

```
   Lua script                  Lua runtime                  executor.executeSource
   ───────────                  ───────────                  ────────────────────────
   return 1/0                   arithmetic error
                                 raises on Lua stack
                                                   │
                                                   ▼
                                       lua_pcall returns LUA_ERRRUN
                                       1. error_message = lua_tostring(L, -1)
                                       2. readExplicitFailure(L, allocator)
                                          → ExplicitFailureView { .None, null, null }
                                       3. captureStackTrace(L, allocator)
                                          → "  at bpm_script:7\n  at bpm_script:4 in 'main'\n"
                                       4. if ctx.instruction_limiter != null
                                          instruction_count = limiter.getInstructionCount()
                                          memory_peak_bytes = 0   (LUA-09 deferred; same run branch)
                                        else
                                          instruction_count = 0
                                          memory_peak_bytes = 0
                                          capabilities_at_failure =
                                            "skip: instruction_count source not installed (LUA-08 deferred)"
                                       5. buildScriptErrorPayload(...)
                                          → ScriptErrorPayload
                                       6. clearExplicitFailure(L)   // belt-and-braces
                                       7. ScriptResult {
                                            .success = false,
                                            .error_kind = .RuntimeError,
                                            .error_message = dupe(error_message),
                                            .script_error = ScriptErrorPayload { ... },
                                          }
```

**Distinguishability (D-1 from the issue):** `error_kind` is the
authoritative discriminator. The engine-side worker reads it and routes
to `SCRIPT_FAILED` (`event_type = .SCRIPT_FAILED`) vs `SCRIPT_ERROR`
(`event_type = .SCRIPT_ERROR`). TC-LUA-15-07 and TC-LUA-16-15 both
exercise this branch and assert the two distinct event types from the
two distinct `error_kind` values.

### 3.3 LUA-12: service call flow (D-1)

```
   Lua script                  platform.call_service         executor
   ───────────                  ────────────────────          ─────────
   platform.call_service(        1. checkString(svc_id)
     "payment_svc",             2. serviceCallCapability(svc_id)
     "POST",                      → "service:call:payment_svc"
     "/charge",                 3. requireCapability(capability)
     {Content-Type=JSON},       4. ctx = host_context.contextFromState(L)
     '{"order_id":"42"}')          ctx.service_catalog required (D-1)
                                 5. service = ctx.service_catalog.lookup(svc_id)
                                                       │
                                       ┌───────────────┴───────────────┐
                                       ▼                               ▼
                                 lookup returns                 lookup returns null
                                 RegisteredService             raiseMessage(L,
                                 {endpoint_url,                   "platform.call_service: service
                                  auth_method, ...}                 '<svc_id>' not registered")
                                                            (this is a Lua raise → SCRIPT_ERROR
                                                             path; SCRIPT_FAILED only fires
                                                             from platform.fail, LUA-15)
                                 6. if simulation_runtime.get() != null
                                      simulation path: still call lookup first,
                                      then executeMockedServiceCall
                                      (the simulation interceptor does NOT do its
                                       own lookup — defense-in-depth per §3.3)
                                    else
                                      real path: build http request against
                                      service.endpoint_url respecting
                                      service.auth_method (NONE / BEARER / API_KEY / OAUTH2),
                                      push single response table:
                                        {status_code, headers, body}
                                 7. return 1   (single table)
```

### 3.4 Defense-in-depth: simulation validates svc_id first

The simulation branch previously skipped catalog validation. With D-1 it
calls `ctx.service_catalog.lookup(svc_id)` BEFORE handing off to the
simulation interceptor. A script calling `platform.call_service('not_in_catalog', ...)`
in simulation mode now receives the same `"service '<svc_id>' not registered"`
Lua error as the non-simulation path. The interceptor itself is unchanged
(does not need its own lookup). Tests:

- TC-LUA-12-04 (service not found) — runs against simulation context
- TC-LUA-12-15 (network error) — runs against real HTTP, fails to connect

## 5. State transitions

No new state machines. The three requirements add *fields* on existing
types (`ScriptResult`, `ExecutionContext`) and *channels* on existing
registry state. There is no new FSM.

What does change is the **classification of failed pcall results**:

```
                    ┌─────────────────────┐
                    │ executeSource        │
                    │ pcall failed         │
                    └─────────┬───────────┘
                              │
                              ▼
              ┌───────────────────────────────────┐
              │ readExplicitFailure(L, allocator) │
              └───────────────┬──────────────────-┘
                              │
                ┌─────────────┴─────────────┐
                ▼                           ▼
       ExplicitFailureView{        ExplicitFailureView{
         .Explicit,                  .None,
         reason,                     null, null,
         details                     }
       }
                │                           │
                ▼                           ▼
       ScriptResult{                captureStackTrace(L, alloc)
         .error_kind =              │
           .ExplicitFailure,        ▼
         .script_error = null,  ScriptResult{
       }                           .error_kind = .RuntimeError,
                                   .script_error = ScriptErrorPayload{...}
                                 }
```

## 7. Sequencing (the run's branch order)

The diagnosis recommends **LUA-15 → LUA-12 → LUA-16** for this branch:

| Order | Step | Rationale |
|---|---|---|
| **1** | **LUA-15** (registry migration + `ScriptResult.error_kind`) | `ScriptResult` gains the discriminator. LUA-12 does not need it but LUA-16 uses the same branch to distinguish `.Explicit` from `.None`. Doing LUA-15 first means LUA-16 lands onto a stable `ScriptResult` shape. |
| **2** | **LUA-12** (`ExecutionContext.service_catalog` + real HTTP) | Independent of LUA-15's branch. Lands cleanly because (a) `lookup()` is a synchronous Zig function, (b) the simulation branch already routes through `simulation_runtime.get()` and the catalog check is a single line above that branch. |
| **3** | **LUA-16** (`captureStackTrace` + conditional `ScriptErrorPayload`) | Depends on LUA-15 (shared failed-pcall branch). Depends on LUA-08/09 conditionally (D-3). Lands last because it touches the most files and has the most conditionality. |

| OQ-2 | D-3 means the `instruction_count` field can legitimately be `0` even when the LUA-08 hook is installed (e.g., a script errors on its first instruction). Do we document this? | YES. The skip-reason string in `capabilities_at_failure` is only written when `instruction_limiter == null`; a `0` with a working limiter is "the script failed immediately, instruction count was 0" — accurate. |
| OQ-3 | Does the HTTP client in the real-call path belong in this design or a follow-up? | The **HTTP client interface** is in scope (`httpRequestFn` is a function pointer the executor passes through to `call_service`). The **HTTP client implementation** is NOT — the engine instantiates it and passes the function pointer into `ExecutionContext`. This run does NOT add an HTTP client; tests use a stub function pointer (TC-LUA-12-01..06, 11..15 — see §9). |
| OQ-4 | The `ScriptResult.script_error` field is heap-allocated; should it live on the executor's return value or in an out-parameter? | On the return value. The executor already owns the `error_message` allocation; one more owned allocation for `script_error` is consistent. `deinit` is updated to free it. |
| OQ-5 | Are HTTP headers on the real-call path extracted from a headers table the script passes? | YES. Headers come from the 4th argument (Lua table); only string values are forwarded (any non-string value raises `InvalidArgument` — same convention as the existing `headers` table is treated as opaque). |

## 10. Implementation notes (forwarded to BACKEND-DEV)

### 10.1 `ScriptErrorPayload.deinit` (nils after free)

```zig
pub fn deinit(self: *ScriptErrorPayload, allocator: std.mem.Allocator) void {
    allocator.free(self.error_message);
    self.error_message = &[_]u8{};
    allocator.free(self.stack_trace);
    self.stack_trace = &[_]u8{};
    allocator.free(self.capabilities_at_failure);
    self.capabilities_at_failure = &[_]u8{};
}
```

Setting the field to an empty slice (instead of nil) preserves the type
(`[]const u8`, not `?[]const u8`) and makes a second `deinit` a no-op
(free on an empty slice is allowed but undefined — better to nil).
Implemented here, not in `ScriptResult.deinit`, because the executor
already calls `ScriptErrorPayload.deinit(allocator)` exactly once.

### 10.2 `EventRecord.deinit` currently calls `details_copy.deinit`

`events.zig:54-57`:

```zig
.SCRIPT_FAILED => |fail_payload| {
    self.allocator.free(fail_payload.reason);
    if (fail_payload.details) |details| {
        var details_copy = details;
        details_copy.deinit(self.allocator);
    }
},
```

This is correct *only if* `details` is owned by the payload. With
D-1+D-2+D-3, `buildScriptFailedPayload` makes the payload **own** the
details copy (allocated via the same allocator). `details_copy.deinit`
walks the `ScriptValue` union and frees each owned slice. This is
unchanged from the existing types; what is new is that BACKEND-DEV
actually constructs the payload. No change to `EventRecord.deinit`.

### 10.3 `executeScript` does not perform HTTP I/O

The `ExecutionContext` field `http_client_fn: ?*const fn (...) callconv(.c) ...`
is **NOT** introduced in this design. The HTTP client is a higher
concern; this run uses the function-pointer indirection only in
TESTS. In production the engine injects the real HTTP client; that
wiring is OUT OF SCOPE for this branch. (If the engine-side worker
already has a hook for this, fine; if not, it is a follow-up issue.)

**OQ-3 resolution:** The LUA-12 tests inject the function pointer
directly into the test's `ExecutionContext`. The production path's
field is left out of this design; the LUA-12 production call site
documents the missing client as a known limitation that becomes a
follow-up ISS.

### 10.4 Backward compatibility — `LUA-12` return-shape change

Scripts written against the current `(string, number)` tuple return
will need to switch to:

```lua
local response = platform.call_service("svc", "GET", "/path", {}, "")
if response.error then
    -- response.error is a string for transport failures
    -- response.status_code is 0 for transport failures, otherwise the HTTP status
elseif response.status_code >= 400 then
    -- response.status_code is the HTTP status, response.body is the body
else
    -- success: response.body has the response
end
```

The CHANGELOG entry reads:

```markdown
## Unreleased — LUA-12 (BREAKING)
`platform.call_service` now returns a single Lua response table
(`{status_code, headers, body}` on success, `{error, status_code}`
on transport failure) instead of the previous `(string, number)`
tuple. Scripts using `local body, status = platform.call_service(...)`
must migrate to `local response = platform.call_service(...); response.status_code / response.body / response.error`.
```
