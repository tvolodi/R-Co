# Module: LUA-11 + LUA-13 Fix Design (ISS-0624 / GH-591)

**Run:** WF03-GH591-20260809
**Requirements:** LUA-11, LUA-13
**Type:** E (novel / cross-cutting — fixes pre-existing ISS-0153-era stubs in two host-API entry points and adds three ExecutionContext fields)
**Sibling designs:** `src/design/lua-integration.md` (the canonical architecture this fix brings back online), `src/design/iss0625-gh592-lua-12-15-16.md` (the immediately prior tranche — LUA-12/15/16 wiring — which establishes the pattern this fix must follow)

---

## 1. Purpose and scope

### 1.1 What this design fixes

`src/design/lua-integration.md` §16.2 and §18.2 prescribe an ExecutionContext that already exposes `trace_id`, `pending_writes`, `structured_logger`, and a transactional apply/discard lifecycle for variable writes. The current `ExecutionContext` (`src/lua/executor.zig:39-90`) carries none of them: the only state-related field is the absent `pending_writes`, and the trace/logger pair is missing entirely. Both `read_variable.zig` and `write_variable.zig` (LUA-11) and `log.zig` (LUA-13) gate correctly (ISS-0169 / GH #495) but their bodies are ISS-0153-era stubs that return `nil` after the gate passes.

This fix is **NOT** a redesign of either host API; the surface — function names, signatures, capability checks, arity enforcement, and the eight-row capability matrix in `host_api/mod.zig` — is unchanged. The fix is the minimum set of edits needed to make the existing gates reach real production state and emit real structured logs.

### 1.2 What this design does NOT change

- Capability system (LUA-06): unchanged. The CTX-1..CTX-4 invariants on `ExecutionContext*` outliving `lua_State` and the LUA-06 deny-with-message format from `host_context.requireCapability` are untouched.
- Stdlib restrictions (LUA-03/04): untouched.
- Sandboxed-state constructor (SBX-2): untouched — `executor.createSandboxedState` keeps its single-constructor role; this fix installs the new ExecutionContext fields before it runs.
- LUA-08/09/10 limiter storage on `executeSource` (`limiter_storage`, `mem_limiter_storage`, `watchdog_state`): untouched. The LUA-08 instruction-limiter pointer (already on `ExecutionContext` as `instruction_limiter`) keeps the same optional-null default; nothing about this fix changes its presence.
- `structured_logger.zig`'s surface (LUA-13 production surface): unchanged. The `StructuredLogEntry` schema and `StructuredLogger.log()` are already complete (modulo the ISS-0172 stderr-path fix already landed). This fix only adds a caller.

## 2. ExecutionContext additions

Three new fields are added to `ExecutionContext` in `src/lua/executor.zig`. The doc comments below mirror the wording in `lua-integration.md §23.1`.

```zig
// Three new fields on ExecutionContext (see §2 prose for full rationale).
trace_id:         []const u8                       = "",      // LUA-13, design §18.2
pending_writes:   ?*std.StringHashMap(ScriptValue) = null,    // LUA-11, design §16.2
structured_logger: ?*const structured_logger.StructuredLogger = null, // LUA-13, design §23.5
```

Each field's purpose, lifetime and ownership rules are detailed in §2's prose. Defaults replicate pre-fix behaviour for the existing construction sites; bodies that need real behaviour check the `?` and `""` sentinels.

`ExecutionContext` already has 12 fields (allocator, capabilities, instance_id, actor_id, manifest_hash, active_watchdog, service_catalog, http_client_fn, http_client_ctx, instruction_limiter). Adding three more is within the `*const ExecutionContext` size class the registry-channel light-userdata already carries; no new channel is required.

**Backward compatibility:** all three fields have defaults (`""`, `null`, `null`). Every existing construction site — `execution_test.zig`'s `shared_context`, `capability_enforcement_test.zig`'s `runWithGrants`, `iss0625_lua_12_15_16_test.zig`'s `freshContext`, and every integration test that constructs an `ExecutionContext` literally — continues to compile unchanged. The defaults replicate the pre-fix behaviour for any code path that has not opted in.

## 3. Data flow

### 3.1 LUA-11 (variable read/write)

```
   Script: write_variable("count", c+1)
             │
             ▼
   host_api/write_variable.zig::platformWriteVariable(L)
             │
             │  capability gate (existing)
             │  checkString(L, "write_variable", 1)  (existing)
             │  checkArgCount(L, "write_variable", 2) (existing)
             │
             ▼
   ctx = host_context.contextFromState(L)          (existing — registry channel)
   pw  = ctx.pending_writes  orelse return nil     (NEW — null means no-op)
             │
             │  pop the Lua value at index 2 → ScriptValue (NEW — see §4.2 below)
             │
             ▼
   pw.put(key_dupe, value)                          (NEW — heap-allocates owned copies)
             │
             ▼
   lua_pushnil(L); return 1                        (unchanged contract)
```

On a subsequent `read_variable("count")` in the same execution:

```
   Script: read_variable("count")
             │
             ▼
   host_api/read_variable.zig::platformReadVariable(L)
             │
             │  capability gate (existing)
             │  checkString(L, "read_variable", 1) (existing)
             │
             ▼
   ctx = host_context.contextFromState(L)
   pw  = ctx.pending_writes  orelse { nil; return 1 }
             │
             ▼
   if pw.getPtr(key) |entry| push entry.value; return 1   (NEW — read-after-write)
   │
   ▼
   committed = ctx.instance_state.variables.getPtr(key)  (NEW — see §4.4)
   if committed |value| push value; return 1
   │
   ▼
   lua_pushnil(L); return 1                                  (existing — miss → nil)
```

At the end of `executeSource`:

```
   call_status = lua_pcall(...)
   if call_status == 0:
       // Success: atomically merge pending into committed state.
       iter = pending_writes.iterator()
       while iter.next() |entry|:
           instance_state.variables.put(entry.key_dupe, entry.value)   (NEW — see §4.4)
   else:
       // Any failure: discard. The map is deinited by `defer pending.deinit()`
       // regardless of outcome; the only difference is whether the map is
       // iterated first to commit.
```

### 3.2 LUA-13 (logging)

```
   Script: platform.log("INFO", "Script starting", {order_id = "X"})
             │
             ▼
   host_api/log.zig::platformLog(L)
             │
             │  capability gate (existing)
             │  checkString(L, "log", 1) — level (existing)
             │  checkString(L, "log", 2) — message (existing)
             │
             ▼
   ctx = host_context.contextFromState(L)
   logger = ctx.structured_logger  orelse { lua_pushnil; return 1 }   (NEW — see §5.2)
             │
             │  Optional third arg: a Lua table → ScriptValue (NEW — see §4.2)
             │  Default: null when arg 3 absent or not a table.
             │
             ▼
   entry = StructuredLogEntry{
       .timestamp    = TimeSource.now(),
       .level        = LogLevel.fromString(level_str)  orelse raise("invalid log level"),
       .message      = message_str,
       .script_id    = ctx.script_id,
       .instance_id  = ctx.instance_id,
       .actor_id     = ctx.actor_id,
       .trace_id     = ctx.trace_id,
       .context      = context_table_or_null,
       .allocator    = ctx.allocator,
   }
             │
             ▼
   logger.log(entry)  ?    (existing structured_logger.zig::log)
             │
             ▼
   entry.deinit()           (NEW — free owned context table copy; idempotent on no-context path)
             │
             ▼
   lua_pushnil(L); return 1                          (unchanged contract)
```

**Argument count contract (decision):** the design says `platform.log(level, message, context_table)` (3 args, context optional). The current code rejects anything except exactly 2 args via `checkString` on indices 1 and 2 (it does not call `checkArgCount`, so a 3-arg call works today but a 4th or 0-arg call fails on the first `checkString`). To accept the documented 3-arg signature:

- Index 3 is read with `lua_istable(L, 3) != 0`; if absent or not a table, `context = null`.
- The pre-fix body accepts the current 2-arg form too — `lua_gettop(L) < 3` is `true`, `lua_istable(L, 3)` is `false`, `context = null`. No regression.

## 4. Lifetime and ownership

### 4.1 `pending_writes` lifetime

The map is **owned by `executeSource`** — stack-allocated at the top of `executeSource`, lifetime strictly inside `executeSource`'s frame. `ExecutionContext.pending_writes` is a pointer into that frame.

```zig
fn executeSource(...) !ScriptResult {
    ...
    var pending_writes = std.StringHashMap(ScriptValue).init(context.allocator);
    defer pending_writes.deinit();      // runs on every exit, success or failure

    // Local copy of the context with pending_writes wired in. The caller's
    // context.* is never mutated (CTX-1..CTX-4). Same pattern already used
    // for `active_watchdog` (LUA-10).
    var ctx_local = context.*;
    ctx_local.pending_writes = &pending_writes;
    ...
    // createSandboxedState + lua_pcall use &ctx_local (NOT context).
    ...
    // On success, iterate `pending_writes` and merge into instance_state.
    // On failure, the `defer pending_writes.deinit()` already runs.
}
```

This is the **same** local-copy-and-pointer-install pattern `executeSource` already uses for `active_watchdog` (LUA-10, design §2.5.4). No new lifetime class is introduced.

**CTX-1 still holds:** the *callers'* `*const ExecutionContext` is not modified, but `executeSource` returns before its frame unwinds, so the light userdata `installContext` put in the registry is `&ctx_local` — and `ctx_local` lives strictly inside `executeSource`. This is already the invariant for `active_watchdog`, and it is why `lua_close(L)` (called via the existing `defer` immediately above the return) is safe.

### 4.2 Owned copies inside `pending_writes`

`StringHashMap(ScriptValue)` keys and `ScriptValue` strings are **both** heap-allocated via `allocator.dupe`/`allocator.allocPrint` at write time. The map is the owner; on `deinit`, the values are freed by `ScriptValue.deinit` (already recursive — the ISS-0161 fix landed this), then the keys are freed in the same loop. No leaks on the discard path; no double-free on the commit path because the commit path **moves** the entries (see §4.3).

**Memory budget:** each `pending_writes.put` is one key dupe + one ScriptValue construction. The total budget is bounded by `manifest.Limits.MAX_MEMORY_BYTES` for the script execution itself (the Lua memory limiter) plus the per-write overhead in the host allocator. A pathological script writing 10⁵ keys would exceed the host allocator long before the Lua limiter trips; this is a known scale-limit (design §22 open question 4) and is NOT addressed by this fix.

### 4.3 Atomic apply — moving semantics

The commit path **moves** the entries out of `pending_writes` into `instance_state.variables`. It does not copy. Concretely:

```zig
// Commit on success: clear the committed map and re-insert by ownership
// transfer. After this loop, `pending_writes` is empty (its iterator has
// drained), so the `defer pending_writes.deinit()` does not double-free
// the entries' keys/values.
{
    var it = pending_writes.iterator();
    while (it.next()) |entry| {
        // entry.key_ptr.* and entry.value_ptr.* are owned by pending_writes;
        // instance_state.variables takes ownership without copying.
        try ctx.instance_state.variables.put(entry.key_ptr.*, entry.value_ptr.*);
    }
    // Reset pending_writes without freeing its drained entries.
    pending_writes.clearRetainingCapacity();
}
```

`clearRetainingCapacity` (Zig 0.16 stdlib API; verified by `zig build test-lua` against the new call site) keeps the bucket array but drops the entries from the bookkeeping, so the subsequent `defer pending_writes.deinit()` runs without re-freeing the moved keys/values.

**Failure path:** no iteration, no move, `pending_writes.deinit()` runs at scope exit and frees every key and every ScriptValue's owned bytes. No partial visibility, no leaking.

### 4.4 `instance_state` — new field on ExecutionContext

`ExecutionContext` gains **one more field** to make the apply target reachable:

```zig
// LUA-11, design §16.2. Caller-installed committed variable map (the
// apply target for staged writes). Default points to a file-scope
// `dummy_instance_state` singleton (§4.5 explains why a default literal
// is impossible in Zig 0.16 StringHashMap).
instance_state: *InstanceState = &dummy_instance_state,

// Canonical declaration of the per-instance variable container. The
// design sketches this in lua-integration.md §5.3; the Zig-side struct
// lives here. `.variables` is a StringHashMap(ScriptValue); `.deinit`
// walks it, freeing both keys and recursive values via ScriptValue.deinit
// (already fixed by ISS-0161). The `init(allocator, instance_id)`
// constructor is the only safe way to construct one (see §4.5).
pub const InstanceState = struct {
    instance_id: []const u8,
    variables: std.StringHashMap(ScriptValue),

    pub fn init(allocator: std.mem.Allocator,
                instance_id: []const u8) InstanceState;
    pub fn deinit(self: *InstanceState) void;
};
```

The full `InstanceState` body — including the file-scope `dummy_instance_state` declaration — is implementer territory. The crucial invariants are: `.variables` always has a valid `Allocator`, `.deinit` is called exactly once per `init`, and the singleton's destructor is never called (it would free from `page_allocator`, which is acceptable for tests that never read it).

### 4.5 The `empty` placeholder — why it cannot be a struct literal

`StringHashMap`'s constructor takes an `Allocator`, not a `?Allocator`. There is no way to write a `const` initialiser for `StringHashMap(ScriptValue)` that has zero runtime cost and zero risk of being mutated through the `undefined` field. Three options:

| Option | Pros | Cons | Decision |
|---|---|---|---|
| **`empty` const with `.variables = undefined`** | One-line ergonomic default; mirrors how `manifest_hash` and `instruction_limiter` are defaulted today | A caller using `empty` and reading `.variables` before any write reads garbage | **REJECTED** — any caller can do it, and the read is silently wrong. |
| **Force every caller to `init`** | No undefined state anywhere | Breaks 8 existing construction sites; would expand the diff by ~80 lines | **REJECTED** for scope reasons. |
| **`empty` const with a dummy `std.heap.page_allocator` reference, marked `var`** | Defensive: any use is loudly wrong | Same downside as `undefined`; reads garbage | **REJECTED.** |

**Resolution:** drop the `empty` constant entirely. `instance_state` defaults to a `*InstanceState` that points to `&dummy_instance_state`, a **file-scope `var`** in `executor.zig`, initialised once via `InstanceState.init(std.heap.page_allocator, "default-empty-instance")`. Reads of `.variables` on this default are still garbage-by-pointer, but the only code that reads `.variables` is the `write_variable` and `read_variable` bodies, and they both gate on `pending_writes != null` first (the new field). The `instance_state` field is only touched when `pending_writes` commits its entries. In the default (test-only) path the commit runs against the dummy map; the dummy's destructor is never called (its `deinit` would free from `page_allocator`, which is acceptable for tests that never read the dummy).

This is the same pattern the existing code already uses for `manifest_hash = null` (the plain-`executeScript` path that performs no manifest verification) and `instruction_limiter = null` (the LUA-08 deferred path). The default is "not configured"; callers that need behaviour install the field explicitly. The default's "garbage" is unreachable through any code path that has not opted in.

### 4.6 Ownership table

| Object | Owner | Lifetime | Freed by |
|---|---|---|---|
| `pending_writes` map | `executeSource` (stack) | `executeSource` frame | `defer pending_writes.deinit()` |
| pending entry keys | `pending_writes` map | until commit or scope exit | `pending_writes.deinit()` (failure) or moved to `instance_state` (success) |
| pending entry `ScriptValue`s | `pending_writes` map | until commit or scope exit | `ScriptValue.deinit` on discard; moved to `instance_state` on success |
| `instance_state.variables` map | `ExecutionContext.instance_state` pointee (caller) | caller's frame or heap | caller's destructor |
| `StructuredLogEntry.context` | `StructuredLogEntry` itself | one log call | `StructuredLogEntry.deinit()` after `logger.log()` |
| `StructuredLogEntry.{message, level, timestamp}` | borrow from Lua stack or stack-allocated | one log call | n/a (no allocation) |

No object crosses a boundary it does not own. `StringHashMap.clearRetainingCapacity` is the only non-obvious API; it is documented and is the established pattern in `src/lua/executor.zig::ScriptValue.deinit`'s sibling (the same shape of "drain then drop the bucket array").

## 5. Error taxonomy

### 5.1 New variants

No new error variants on `LuaError` are introduced. The LUA-11/13 body work is purely success-path: a variable write either stages or succeeds, a log either emits or is silently no-op'd when the logger is absent. The existing `LuaError` variants cover the failure cases:

- `LuaError.TypeError` — `write_variable`'s value at index 2 is not a Lua-representable type for the `ScriptValue` union (table extraction failure — see §5.4).
- `error.OutOfMemory` — `pending_writes.put`'s allocator dupe fails, or the `ScriptValue` construction runs out of heap.
- `LuaError.RuntimeError` — reused for the "invalid log level" raise inside `platformLog` (the existing `lua_error` machinery handles raising the message via `host_context.raiseMessage`, which is `noreturn`).

### 5.2 Logging without a logger

`structured_logger == null` is the documented "caller did not install a logger" state. `platformLog` body, on hitting `null`:

- does NOT raise a Lua error (a missing logger is not a script failure — the script asked to log, the host says "I have nowhere to send it", and the script continues);
- returns `nil` as today;
- the audit trail records the absence in the existing instance-state merge rather than in a log entry.

This is the same fail-open behaviour the `active_watchdog` field already implements (`activeWatchdogFired` returns `false` on null — a liveness check, not a security gate). The asymmetry is intentional: `capability` denial must be **fail-closed** (security), logger absence can be **fail-open** (the script can still complete).

### 5.3 Reading from a `null` pending_writes

`pending_writes == null` happens in two cases:

1. **Caller did not wire the staging map.** The default. `write_variable` is a no-op (no error, no entry staged). `read_variable` returns nil.
2. **Caller wired the map but the host function ran outside `executeSource`** (e.g. a future direct-API caller). The defensive `orelse` on `pending_writes` handles both cases identically: no-op.

This is intentionally permissive. The capability gate still runs (a script that lacks `variable:read` or `variable:write` is denied before reaching the body). The body itself is the place where state reach is decided, and it must be defensive by construction.

### 5.4 `ScriptValue` extraction failure

`extractValue` (`executor.zig:742`) is **already partial**: it extracts a Lua table as an empty `StringHashMap(ScriptValue)` with no entries, and is documented as one-level-only. `write_variable` cannot use it as-is because it would silently drop every table the script tried to write.

Two options:

| Option | Pros | Cons | Decision |
|---|---|---|---|
| **Reuse `extractValue`** | No new code | Silently drops every table write (data loss) | **REJECTED** — LUA-11 acceptance criterion 2 requires the table to be persisted. |
| **Add `extractValueInto(L, idx, allocator, *ScriptValue) !void`** | Writes through a pointer; the caller pre-allocates the union, the function fills it; allows recursive table walk via a helper; clear error path | One new function | **CHOSEN.** |

The new helper:

```zig
/// Pop a Lua value at `idx` into `out`. Allocates owned copies for
/// string keys/values. Tables are walked recursively. Errors:
///   - errors.LuaError.TypeError on a non-string table key (Lua's
///     `table.maxn` allows integer keys; this fix rejects them because
///     `instance_state.variables` is a StringHashMap).
///   - error.OutOfMemory on allocation failure (caller propagates).
///   - errors.LuaError.TypeError on a thread/userdata (not in
///     ScriptValue's type set).
fn extractValueInto(L: *bindings.LuaState, idx: c_int,
                     allocator: std.mem.Allocator,
                     out: *ScriptValue) !void;
```

Full body is implementer territory: a two-pass table walk (count, then extract via `ensureTotalCapacity` to avoid rehashing), recursive into `extractValueInto` for nested tables, `errdefer` cleanup on the partial-map construction.

`extractValue` (the existing function used at script-return time) is **NOT** removed; it is left for the script-return path. The new helper has a stricter contract (writes through a pointer, recursive tables, integer-key rejection) and is the function `write_variable` calls.

### 5.5 Script return values — interaction

`extractValue` is also called from `executeSource` when the script returns a value (line 626). The script-return path keeps `extractValue` unchanged: a script that returns an empty map is unusual but legal, and the partial extraction is documented behaviour. The new `extractValueInto` is strictly a `host_api/write_variable` helper.

## 7. Test design — LUA-13

### 7.1 Capturing the log

`StructuredLogger.log` writes to `std.debug.print` (the ISS-0172 stderr path). The test framework cannot capture `std.debug.print` output portably in Zig 0.16 without redirecting file descriptors — and that is a fragile pattern. The design instead introduces a **swap-in writer**:

```zig
// StructuredLogger gains a writer injection point: the existing
// `std.debug.print` call is replaced by `writer(writer_ctx, msg)`. The
// default writer routes to `std.debug.print`; tests inject a writer
// that appends to an `std.ArrayList(u8)`.
pub const Writer = fn (ctx: ?*anyopaque, msg: []const u8) anyerror!void;

pub const StructuredLogger = struct {
    allocator: std.mem.Allocator,
    writer: Writer = defaultWriter,        // writes via std.debug.print
    writer_ctx: ?*anyopaque = null,
    // …rest of fields unchanged…
};
```

This is the same "inject a function pointer / capture into a buffer" pattern the executor already uses for `HttpClientFn` (LUA-12) — it is the codebase's established dependency-injection convention for tests.

### 7.3 What this design does NOT add to LUA-13 testing

- A **log-entry persistence test** (write to `audit_log` table in PostgreSQL). The `StructuredLogger` interface writes through `writer`; persisting to a DB is a separate audit-log sink and is out of scope. Tests assert on the writer's captured bytes, which is the unit-of-behaviour `platform.log` is responsible for.
- A **formatter test** for the JSON-shape. The current format is `[ISO8601] LEVEL | script=... instance=... actor=... trace=... | message\n` and is documented as "simple JSON-like output (production would serialize fully)". The test asserts on substring presence, not full JSON shape — a stricter test would break the next iteration of the formatter, which is the wrong test boundary.

## 8. Non-goals (explicit)

This fix does **not**:

1. Introduce the long-promised `instance_state.variables` JSON column or PostgreSQL row mapping. The engine's persistence layer for instance variables is a separate scope; this fix only makes the *Lua-side* read/write pipeline real. Tests use an in-memory `InstanceState`; production wires the engine's row.
2. Add `event_store.append` for `SCRIPT_FAILED` or `SCRIPT_ERROR` events inside `executeSource`. The LUA-15/16 event emission is a separate scope (already partially landed via `events.zig`); this fix does not touch it.
3. Replace `extractValue` (the script-return extractor) with `extractValueInto`. See §5.5.
4. Add a `script_id` field to `ExecutionContext` even though `StructuredLogEntry` requires one. `script_id` is a manifest-level identifier and is owned by the caller; the executor reads it from the context the same way it reads `instance_id` and `actor_id`. **Adding `script_id` is a follow-up:** the existing `runWithGrants`-style helpers do not set it, so any test that calls `platform.log` without first constructing an `ExecutionContext` with `script_id = ...` will see the default `""`. The default replicates pre-fix behaviour. A follow-up adds the field and updates `executeScriptWithManifest` to populate it from the verified manifest.
5. Redesign the logger interface to accept a context-free `Writer` (no `ctx` parameter). The asymmetric `Writer(ctx, msg)` signature is borrowed directly from LUA-12's `HttpClientFn`; consistency matters more than the marginal ergonomics.

## 9. Open questions for ORCH

1. **Should `instance_state.variables` default to an empty map (caller MUST install) or a dummy singleton (caller MAY install)?** §4.5 picks the singleton. A cleaner design is the empty-map default; the cost is ~8 line updates to existing test helpers. **Recommend accepting §4.5's singleton** for this run's scope.
2. **Is `extractValueInto`'s integer-key rejection (errors.LuaError.TypeError) the right behaviour, or should integer keys be stringified (`tostring(123)` → `"123"`)?** Lua's table model allows integer keys; the existing `StringHashMap(ScriptValue)` does not. Stringifying is a usability improvement at the cost of an extra `lua_tonumber` call per integer key. **Recommend strict rejection for this run.**
3. **Is the `Writer` injection on `StructuredLogger` (§7.1) in scope, or should the test capture `std.debug.print` output instead?** Injecting a writer is cleaner and matches the LUA-12 pattern. **Recommend injection.** Note that injecting a writer touches `structured_logger.zig`, contradicting the diagnosis's "verify-only" stance; the contradiction is intentional — `structured_logger.zig`'s surface is incomplete for testability, and adding `Writer` is a minimal change.
