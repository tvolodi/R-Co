# Fix design: ISS-0627 remaining categories (GH-596)

Resolves the four categories GH-596 explicitly left open after #598 handled
H003/H004/H005/H009: **H013**, **H001-structural**, **H006-CONDITIONAL**,
**H007**.

## H006 — CONDITIONAL status mapping

One finding: `handoffs/ADHOC-full-test-20260527/step-04-test-runner.json`'s
`result.status` was `"CONDITIONAL"`, not in the legal enum
`['BLOCKED', 'FAIL', 'PARTIAL', 'PASS', 'SKIPPED']`.

**Decision: `CONDITIONAL` → `PARTIAL`.** Read the handoff's actual content:
3 of 5 test layers (unit, E2E, benchmarks) passed cleanly; the 4th
(integration) had 37/827 failures (95.5% pass rate within that layer),
each with a diagnosed root cause and remediation. This is exactly the
established semantic of `PARTIAL` in this codebase — confirmed against a
precedent (`handoffs/WF02-ee10-20260522/step-04-test-runner.json`, itself
`PARTIAL` for an analogous "most tests pass, some skip/fail with reasons"
outcome). No new enum value was added; `CONDITIONAL` never appears
elsewhere in the corpus.

## H007 — schema-migration decision (`workflow_id`+`sequence` vs `run_id`+`step`)

53 findings — larger than the issue's stated "69 findings, ~10 distinct
files, all in WF02-api07-20260523" (that undercounted; the same field-name
pair appears across `WF02-api07/08/09-20260523`,
`WF03-integration-fix-20260523`, `WF04-full-20260523`, plus two isolated
files from a later run family).

**Decision: rename, not schema-recognition.** `workflow_id`/`sequence` are a
straightforward earlier-convention rename of today's `run_id`/`step` — same
data, same meaning, confirmed by cross-referencing `docs/agents/AGENT_SYSTEM.md`'s
schema (`run_id` = the run identifier string, `step` = the step-number
string matching the filename's step segment). This is a safe, mechanical,
meaning-preserving fix, not a reinterpretation.

**One correction made mid-fix:** `WF03-integration-fix-20260523` and
`WF04-full-20260523`'s `workflow_id` values were `"WF-03"` / `"WF-04"` —
the *workflow type* label, not the run identifier. A blind field rename
would have carried that wrong value forward. Fixed by deriving `run_id`
from the run's own directory name instead (`WF03-integration-fix-20260523`,
`WF04-full-20260523`), which is unambiguous and matches every other
handoff file's convention.

**Two files needed judgment, not renaming, because they are not simple
field-name drift:**

- `handoffs/WF03-gh387-20260802/step-07-doc-updater.json` — not a handoff
  at all. Its top-level shape (`id`/`title`/`status`/`root_cause`/
  `candidate_resolution`) matches `docs/issues/*.json`'s ISS-record schema,
  not the handoff schema — it was written into `handoffs/` instead of
  `docs/issues/` during `WF03-gh387-20260802`. Reformatting it into a
  handoff would fabricate `from_agent`/`to_agent`/`step` values that were
  never assigned, because it was never actually a routed handoff step.
  **Resolution: acknowledged in the baseline as a misfiled-document
  record**, content left exactly as-is (it remains a legitimate,
  informative historical record of ISS-0121's diagnosis).
- `handoffs/WF03-gh389-20260802/step-2b-code-design-validator.json` — a
  genuinely truncated handoff. Only `status`/`result`/`completed_at`
  survive; `handoff_id` (a UUID, unrecoverable), `run_id`, `step`,
  `from_agent`, `to_agent`, `created_at` were never recorded or were lost.
  **Resolution: acknowledged in the baseline** rather than fabricating a
  plausible-looking UUID and timestamps into a historical audit record.

## H013 — whole-hour clock-skew

53 findings, all sharing the `.ToUniversalTime()`-omission signature
(`completed_at` before `started_at` by an amount close to a whole number
of hours).

**Decision: REJECTED for correction, folds into the acknowledgment
mechanism** — per this issue's own acceptance criteria's explicit fallback
("If rejected, folds into #598's acknowledgment mechanism").

Rationale: the 53 offsets are **not** one consistent value — they cluster
near 1h, 2h, 4h, 5h, 7h, 8h, and one pair near 9.9h/0.1h, spread across
different dates. There is no way to recover the one true UTC value from
the file alone; any correction would require *guessing* which whole-hour
offset applies to which finding, which is exactly the fabricated-audit-trail
problem H003/H004's existing baseline reasoning already forbids for a
structurally identical defect (unrecoverable historical timestamps).

Spot-checked the two least-round-number outliers
(`WF02-obs04-20260525/step-03/04`, nominally "0.1h"/"9.9h" offset) directly:
the actual gap is 9h55m23s — not a clean whole-hour value at all — which
confirms a uniform "subtract N hours" script would be actively wrong for at
least this pair, reinforcing the decision to acknowledge rather than
correct.
