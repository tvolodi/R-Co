> **Extends:** SOL-02, which installs a solution pack into a target tenant. This requirement governs the case SOL-02 does not cover: a *later* version of a pack offered to a tenant that has since modified what the earlier version installed.

> The platform SHALL treat a solution pack update as a three-way comparison rather than an overwrite. When pack `P` at version `Vb` was installed into a tenant and version `Vn` is offered, the platform SHALL compute, per artefact in the pack closure, the difference between the **base** (the artefact exactly as `Vb` installed it, recorded at install time), **theirs** (the tenant's current active artefact), and **incoming** (`Vn`). Each artefact SHALL be classified `unchanged`, `clean_update` (only the pack changed), `local_only` (only the tenant changed), or `conflict` (both changed). A `conflict` artefact SHALL NOT be applied until a resolution of `keep_local`, `take_incoming` or `merged` is recorded against that artefact, with the resolving principal and timestamp. The update SHALL be delivered as a single `PRM-01` promotion plan, so an update reaching a tenant passes the same `PRM-05` gate as any other change.

**Acceptance Criteria:**
- GIVEN pack `P` at `Vb` was installed and the tenant has not modified any installed artefact, WHEN `Vn` is offered, THEN every changed artefact is classified `clean_update`, the plan lists them, and no per-artefact resolution is requested.
- GIVEN the tenant modified definition `D` after installing `Vb` and `Vn` also changes `D`, WHEN the update plan is computed, THEN `D` is classified `conflict`, the plan carries the base, local and incoming forms of `D`, and applying the plan without a resolution for `D` returns HTTP 409 `UnresolvedTemplateConflict` naming `D`.
- GIVEN a `conflict` artefact with a recorded resolution of `keep_local`, WHEN the update is applied, THEN the tenant's artefact is left byte-identical, `TEMPLATE_UPDATE_CONFLICT_RESOLVED` is appended carrying the resolution and the resolving principal, and the recorded base for that artefact advances to `Vn` so the next update compares against `Vn` rather than `Vb`.
- GIVEN an artefact classified `local_only`, WHEN the update is applied, THEN that artefact is not touched and it is reported in the plan as retained, so a tenant customisation is never lost to an update that did not concern it.
- GIVEN the install record for `Vb` is absent, so no base form exists, WHEN `Vn` is offered, THEN every artefact the tenant already holds is classified `conflict` rather than `clean_update`, because the platform cannot prove the tenant did not modify it.
- No code path applies a pack update to an artefact classified `conflict` without a recorded resolution; a plan carrying an unresolved conflict is rejected by `PRM-02` before any transaction opens.
